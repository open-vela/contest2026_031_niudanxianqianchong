## 一、应用背景与架构

### 1.1 应用背景

硬件侧 Route A 适配（competition/01~08：芯片与系统、DSI 屏、GT911 触摸、CSI 摄像头、C6 托管
WiFi、以太网、音频、LittleFS 存储）完成后，参赛作品的应用层运行在该真机上：openvela 应用
`demos/smart_home` 以原生 LVGL 承担中控面板，向下消费已验收的显示/触摸/网络/摄像头域，向上
提供三类智能能力——米家真实设备控制、云端大模型 Agent 对话（DeepSeek）、本地摄像头预览
（通路与 UI 预览均已验收）。产品定位来自《ESP32-P4X-智能家居中控面板UI设计方案》：
"以家庭空间为中心，以场景为主要交互方式，以设备控制为基础，以 AI 感知和 Agent 为智能核心
的 OpenVela 智能家居中控面板"。

### 1.2 分层架构与数据流

应用为"UI 层 → 业务服务层 → 外部服务"三层，UI 与业务之间一律经事件队列/快照接口交互，
worker 线程不触碰 LVGL：

```text
            GT911 触摸 (/dev/input0)          EK79007 屏 (/dev/fb0, LVGL)
                        \                        /
                         v                      ^
   ┌─────────────────────────────────────────────────────────────┐
   │  LVGL 中控 UI（仅 UI 线程持有 LVGL）                          │
   │  首页 / 设备 / 场景 / 安防 / 更多 + 屏保                       │
   │  Agent 聊天页 / 系统设置 / 米家绑定页                          │
   │  （事件回调 → pending queue → UI 线程回投）                    │
   └───────┬────────────────────┬────────────────────┬───────────┘
           │                    │                    │
           v                    v                    v
   ┌───────────────┐   ┌────────────────┐   ┌────────────────────┐
   │ cAGENT 装配    │   │ miloco service  │   │ camera service      │
   │ agent_run      │   │ 独立 worker 线程 │   │ 独占 /dev/video0    │
   │ ReAct + 工具    │   │ 5s 轮询设备列表 │   │ V4L2 RGB565 30fps   │
   │ 注册表/事件回调 │   │ spec 拉取/重试  │   │ → 512x300 预览缓冲  │
   └───┬───────┬───┘   └───────┬────────┘   └─────────┬──────────┘
       │       │               │                      │
       │       │         局域网明文 HTTP :1810           │ SC2336 → CSI → ISP
       │       │         /miot REST API                 │ → GDMA → V4L2 capture
       │       │         （家庭服务器 Miloco backend      │
       │       │          → 米家真实设备）                │
       │       v                                      v
       │   miot_device_list / miot_device_control  安防页预览区域
       │  （Agent 工具，复用同一 miloco service）   （UI 预览已验收）
       v
   OpenAI-compatible 模型适配器 + ov_tls (mbedTLS)
   → api.deepseek.com:443（云端大模型，HTTPS）
```

三条数据流：

1. **UI 手动控制**：设备卡片 → 控制抽屉（spec 解析出的可控项）→ miloco worker →
   LAN HTTP `/miot` REST → 米家真实设备；
2. **Agent 工具控制**：聊天页输入 → `agent_run()` ReAct 循环 → 模型生成 tool_calls →
   `miot_device_list` / `miot_device_control`（复用 miloco worker 下发）→ 工具结果回会话 →
   最终文本经事件队列回投 UI；
3. **摄像头预览**：`/dev/video0` 采集 → camera service 复制/缩小为预览缓冲 → LVGL 安防页
   按帧序号轮询刷新（UI 预览上限 15 FPS，已真机验收）。

### 1.3 离线/在线两种模式

- **在线模式（当前交付形态）**：真实 Wi-Fi（C6 ESP-Hosted，手工配网，凭据持久化
  `secrets.json`）+ 米家局域网链路 + DeepSeek 云端对话。
- **离线 bring-up 档**：`CONFIG_SMART_HOME_DEMO_OFFLINE_UI`（Kconfig 默认 n）——"Start the
  regular Smart Home agent and LVGL UI without initializing a network transport or compiling
  the default mbedTLS HTTP callback... Local device panels and settings remain available;
  cloud chat reports the model as unavailable"（`demos/smart_home/Kconfig`）。另有
  `src/net/smart_home_network_offline.c` 承担离线网络桩。P4X 两份配置（`smart_home`、
  `smart_home_local`）均未启用离线档，真机走在线模式。

## 二、核心模块设计

### 2.1 米家接入（miloco，路径 C）

`src/miloco/smart_home_miloco.h` 头注释明确接入路径："P4 不直接对接米家云，而是通过局域网
明文 HTTP 调用 Miloco 的 /miot REST API。设备列表轮询与控制请求都由独立 worker 线程执行，
LVGL 与 Agent 只接触本头文件导出的快照与提交接口。"关键常量：默认端口 1810、轮询间隔 5 s、
最多 16 台设备、每设备最多 8 条可控项（`SMART_HOME_MILOCO_MAX_CONTROLS=8`，即控制抽屉的
8 条控件）。网关 host/port/token 存 `secrets.json`，由设置页配置（当前因 flash 写冻结
workaround 走内存态，见第六章）。

- **设备卡片**：miloco worker 轮询 `/api/miot/device_list` 生成快照，UI 侧渲染为远程设备
  卡片；revision 变化驱动局部刷新（见第五章第 3 层修复）。
- **控制抽屉**：点击卡片弹出，内容由设备 spec 解析出的可控项统一驱动——BOOL（开关）、
  ENUM（多档带选项）、ACTION（无参动作）三类；可控项来自 spec 的可写属性/动作并经黑名单
  过滤。摄像机实测解析出 8 条控件：开关/夜视三档/时间水印/宽动态/微光全彩/人形检测/
  录制三档/云台动作。
- **spec 拉取**：`control_count==0` 的在线设备每轮重试、上限 12 次（第五章第 2 层修复）；
  17,426 B 的摄像机 spec 由零堆轻量扫描器 `smart_home_miloco_specscan.c` 一次线性扫描解析
  （第五章第 6 层修复），不经 cJSON 整树。

### 2.2 云端对话（cAGENT → TLS → DeepSeek 工具调用链）

应用只使用 `packages/cAGENT` 公共接口（`agent.h`）：`agent_create_simple()` 创建 Agent 与
系统提示词，`agent_model_openai_create()` 创建 OpenAI-compatible 适配器，
`agent_model_openai_set_backend/set_api_key/set_model()` 指向 DeepSeek（真机日志确认
`api.deepseek.com:443`），`agent_set_event_callback()` 将模型/工具事件转给 UI。每轮推理为
"context builder（系统提示 + 设备上下文 + skills）→ 收集 LLM_VISIBLE 工具 schema →
model.complete → 解析 tool_calls → tool_guard 检查 → execute → 结果回会话 → 继续 ReAct 或
生成最终文本"。米家工具在 `src/miloco/smart_home_miloco_tools.c` 注册：

- `miot_device_list`：向模型输出米家设备与可控项（iid 形如 `prop.2.1` / `action.2.1`）；
- `miot_device_control`：按 iid 下发控制，schema 内置提示 "iid must come from
  miot_device_list"——模型须先列后控，形成 LLM→设备真实执行的闭环。

工具描述/spec 中文 `desc` 进入请求 JSON 前经 UTF-8 字符边界安全截断（第五章第 7 层修复）。

### 2.3 LVGL 中控 UI（横屏面板 / 字体 / 图标）

1024×600 固定画布：顶栏 64 px（右侧网络/摄像头等只读状态）+ 主体 472 px + 底部导航 64 px
（五项：首页/设备/场景/安防/更多，单项有效触控区不小于 68×56 px）。页面文件按职责拆分
（`src/ui/lvgl/`）：`smart_home_lvgl_home.c`（首页卡片画布）、`smart_home_lvgl_panel.c`
（设备卡片/控制抽屉/米家卡片）、`smart_home_lvgl_pages.c`（安防/场景等页面）、
`smart_home_lvgl_chat.c`（Agent 对话）、`smart_home_lvgl_settings.c`（设置）、
`smart_home_lvgl_screensaver.c`（屏保）、`smart_home_lvgl_miloco_bind.c`（米家网关绑定页）、
`smart_home_lvgl_nav.c` / `smart_home_lvgl_style.c`（导航与统一样式）、
`smart_home_lvgl_agent.c`（Agent worker 事件回投）。

主题演进而后定案：设计方案阶段曾规划深色暖黑主题（`#161819` 系），后续《LVGL 横屏 UI 重构
方案》确定"以网页原型的柔和浅色为首期唯一主题"（`light-calm` 令牌），当前代码已落地——
`smart_home_lvgl_style.h` 逐项对应：`BG #F4F2EE`、`SURFACE #FBFAF8`、`TEXT #26312E`、
`BORDER #E5E1DA`、`PRIMARY_DARK #286A4B`、`DANGER #D64545`。中文字体（完整 MiSans
7,943,504 B 启动时 PSRAM 预加载、五个字号实例）与 PNG→A8 图标资源、`/data` 部署链路已在
**08-存储LittleFS与系统集成** 验收，本文不重复展开。复杂交互页性能目标为稳定 30 FPS。

### 2.4 摄像头预览（V4L2 通路引用 04 + UI 接入现状）

采集通路（SC2336 → MIPI-CSI → ISP RGB565 → GDMA 三缓冲 → V4L2 capture → `/dev/video0`，
1024×600/30 fps）已在 **04-MIPI-CSI摄像头SC2336适配** 完成 300 帧真机验收
（`app_fps=30.02`、`sequence_gaps=0`）。应用侧按《摄像头实时预览接入方案》实施：
`src/camera/smart_home_camera_service.c` 作为 Smart Home 自有的 `/dev/video0` 独占消费者
（Kconfig 描述："captures the SC2336 RGB565 stream in a worker and publishes a copied
512x300 preview to the LVGL security page at a maximum of 15 FPS. It is intentionally
independent of cAGENT and network services."），缓冲策略为"复制后立即归还"（DQBUF →
缩放复制到私有预览缓冲 → QBUF），不向 UI 暴露 USERPTR 原始指针；LVGL 安防页以约 66 ms
timer 轮询帧序号刷新固定图像对象。当前状态：`CONFIG_SMART_HOME_CAMERA_PREVIEW=y` 已入
`smart_home/defconfig`，UI 内实时预览已实现并真机验收（验收证据：演示视频）；
方案文档的 C2/C3 长稳项（安防页连续预览 10 分钟、20 次进出稳定性）并入长稳后续工作。

## 四、真机验收证据

### 4.1 米家闭环（主证据：2026-09-20 七层排障闭环）

摘自 `docs/开发日志/应用/2026-09-20-米家链路七层排障闭环.md`「背景与结论」：

> 米家（Miloco）链路此前停留在"网关在线、设备可见"，但 controls 恒空、控制抽屉弹不出、
> agent 无法控制。本日排障共拆解 **七层叠放的问题**，最终达成完整闭环：**UI 手动控制
> （抽屉 8 条控件）+ Agent 工具控制（LLM→miot_device_list→miot_device_control→摄像机
> 真实执行）**，且顺带验证了 cAGENT TLS 路径在真机上稳定（deepseek 握手/请求/响应全通）。

其中"抽屉 8 条控件"由第 6 层宿主黄金数据单测逐项核对（同文档「第 6 层」）：

> 把真实的 17,426B spec 喂给扫描器，逐项核对 8 条控件（开关/夜视三档/时间水印/宽动态/
> 微光全彩/人形检测/录制三档/云台动作），不可写项正确跳过。

第 4 层定位所用的真机日志对账表（同文档，逐字保留）：

| 响应 | 体积 | TCP 段数 | 结果 |
| --- | --- | --- | --- |
| /api/miot/status | 307B | 1 | 每轮成功 |
| /api/miot/device_list | 632B | 1 | 每轮成功 |
| 手环 spec | 186B | 1 | 成功 |
| **摄像机 spec** | **17,426B** | **~12** | **`no packet buffer`×2/轮，永不完成** |

### 4.2 cAGENT TLS 真机全通（DeepSeek）

TLS 链路的真机演进时间线（三份源文档互证）：

1. **2026-09-18**（`docs/开发日志/应用/2026-09-18-SmartHome-LVGL网络UI与图标交接.md`
   §3.1）：手机热点配网闭环——"C6 成功关联并打开 `wlan0` carrier，DHCP 统计为
   `tx_dhcp=2`、`rx_dhcp=2`、`tx_errors=0`、`rx_dropped=0`；随后 NuttX 获得 IPv4/网关，
   DNS 验证成功，cAGENT 已连接模型服务 `api.deepseek.com:443`"；当时边界如实记录：
   "串口在 TCP 建连及 TLS 上下文建立后报告 `FATAL: read zero bytes from port`"。
2. **HTTP 发送阻塞修复**（`docs/开发日志/ESP32-P4X-SmartHome-HTTP发送阻塞修复.md`）：发送
   方向打通——"真机已完成 DNS、TCP 和 TLS 握手，HTTP 请求头为 227 B，请求体为 5312 B；
   日志停在 `phase=http write-body`"（修复前）；修复后"5312 B 应显示最终进度 `5312/5312`，
   随后 `phase=http write-complete`"（该文档成文于真机验收前，真机验收章节标注"待执行"）。
3. **2026-09-20**（七层排障闭环）：全通结论——"顺带验证了 cAGENT TLS 路径在真机上稳定
   （deepseek 握手/请求/响应全通）"，且 Agent 二轮请求链路经受了 DeepSeek 对请求 JSON 的
   严格校验（第 7 层曾触发 `400 invalid unicode code point at messages[3].content
   column 4047`，修复后工具结果合规回传，闭环完成）。

### 4.3 主机侧回归

## 五、遇到的问题与解决

### 5.1 米家链路七层排障闭环（主体，2026-09-20 单日闭环）

问题总览表逐字摘自主证据文档：

| # | 层级 | 问题 | 根因 | 修复提交 |
| --- | --- | --- | --- | --- |
| 1 | UI | 米家卡片完全不可点 | if/else 之后一句无条件 `clear_flag(CLICKABLE)` 抹掉全部可点击性 | `de0cca5` |
| 2 | 服务 | spec"新设备一次性拉取且忽略返回值" | 首次失败（网络未稳窗口）即永久空 controls | `7c83d5e`（带重试） |
| 3 | UI | 抽屉弹出即被杀（0~5 秒） | worker 每 5s 无条件 revision++ → 1s 定时器先重建抽屉、再被 rebuild_device_cards 显式 close | `cc9fd2e` |
| 4 | 驱动 | 大响应整帧丢弃（`no packet buffer`×2/轮） | esp-hosted RX 配额硬编码 8，17KB spec=12 个 TCP 段撞墙 | `c09467b`（8→32） |
| 5 | 服务 | 17,426B 响应装不进 16KB 缓冲 | `MILOCO_RESPONSE_BYTES` 尺寸过小 | `c09467b`（16K→32K） |
| 6 | 内存 | spec 完整到达后仍冻死 | cJSON 整树 = 上千次 malloc/free 风暴（~130KB 瞬时树落 SRAM 堆区，与 LVGL 小分配竞争） | `56d4366`（零堆轻量解析） |
| 7 | 编码 | agent 二轮请求被 LLM 400 拒绝 | desc[24] 字节截断切半个汉字 → 非法 UTF-8 进入请求 JSON | `bf74693`（字符边界回退） |

辅助修复：IOB 池 96×256B/16 链 → 256/32（`1a3ebca`）——单独无效（瓶颈在配额不在池），
但为配额放开后的突发提供池深，两者互补。

逐层要点（现象→定位→根因→修复→复测）：

1. **卡片点击（de0cca5）**：现象为抽屉完全弹不出；定位到 `create_miloco_card` 在正确设置
   CLICKABLE 之后、第 1918 行一句无条件 `lv_obj_clear_flag(card, LV_OBJ_FLAG_CLICKABLE)`
   抹掉全部可点击性；一行删除修复。
2. **spec 重试（7c83d5e）**：原设计只在设备首次出现时拉一次 spec 且返回值被丢弃，首次恰逢
   网关刚连、网络未稳高危窗口；修复为 `control_count==0` 的在线设备每轮重试、上限 12 次，
   记账走 service 本地静态数组不动共享头文件。复测结论："重试救偶发，救不了确定性"——
   第 4/5 层确定性失败须配合修复才闭环。
3. **抽屉被轮询杀死（cc9fd2e）**：三方打架（无条件 revision++ / 1s 定时器重建 / 显式
   close）；关键事实是抽屉挂在 `screen_panel` 上、`lv_obj_clean(panel_grid)` 根本删不到它，
   那句显式 close 是唯一杀手——删掉该行而非重排刷新顺序。同提交 revision 改为真变才涨，
   消除每 5 秒全网格重建；controls 空的卡片也允许点击（抽屉显示"暂无可控项"占位）。
4. **esp-hosted RX 配额（c09467b）**：由 4.1 节对账表定案——`ESP_HOSTED_WLAN_RX_QUOTA`
   （驱动内 `#define`，非 Kconfig）=8，netdev 流控配额用尽后 `netpkt_alloc` 拒绝 → 丢包 →
   TCP 重传再撞墙，3 秒超时窗口内 12 段永远凑不齐；修复 8→32。注意
   `chips/esp32p4/.../esp_hosted_wlan.c` 与 `nuttx/arch/.../espressif/esp_hosted_wlan.c`
   是硬链接，改一份即两份生效。
5. **响应缓冲（c09467b）**：本机 curl 实测 spec=17,426B > `MILOCO_RESPONSE_BYTES`(16KB)，
   网络修好也会截断；32KB 走 PSRAM bulk 堆无压力——"先测量再修"的典型样本。
6. **cJSON 分配风暴（56d4366）**：网络与缓冲修好后冻点前移到 `done len=17426` 之后的解析
   窗口；根因为 cJSON 整树上千次小 malloc/free、~130KB 瞬时树与 LVGL 小分配
   （`LV_USE_CLIB_MALLOC=y` 共堆）竞争 SRAM；修复为新增零堆线性扫描器
   `smart_home_miloco_specscan`（输出直接写固定数组，提取规则与旧实现逐条等价；开发中补
   了 `value_range` 浮点 `[0.0,270.0,90.0]` 的小数与科学计数法扫描）。质量保证为宿主
   黄金数据单测（真实 17,426B spec 驱动，见 4.1 节）。
7. **UTF-8 截断（bf74693）**：agent 二轮请求被 deepseek 拒绝
   `400 invalid unicode code point at messages[3].content column 4047`；根因为 `desc[24]`
   字节截断把"摄像机控制 夜视功能"(28B) 切到 23B 恰断在"功"中间；属"潜伏 bug 首爆"——
   截断逻辑一直在，但此前 controls 恒空、desc 从未进过 agent 请求。修复为
   `copy_bounded`/`copy_text` 统一 UTF-8 字符边界回退，宿主验证全部干净回退。

方法论沉淀（同文档）：测量先于修复；黄金数据宿主单测优先于上板（十秒 vs 十分钟）；"错误
位置前移 = 进度"；共享头文件不动原则；从未运行过的代码不可信任；外部 AI 分析核实再吸收。

### 5.2 HTTP 发送阻塞（CMD53 512B 限制）

摘自 `docs/开发日志/ESP32-P4X-SmartHome-HTTP发送阻塞修复.md`：现象为 TLS 握手完成后日志
停在 `phase=http write-body`、界面持续 thinking（请求头 227 B、请求体 5312 B，切 1024 B
分块仍复现）。根因：`esp_hosted_transport_send_packet_locked()` 对所有长度都调 CMD53 字节
模式，而 `esp_hosted_transport_transfer_once()` 拒绝超过 512 B 的字节模式事务返回
`-EINVAL`，TLS 大以太网帧无法发出（接收方向已有块模式处理、发送方向遗漏）；且未启用
`NET_TCP_WRITE_BUFFERS` 时 `tcp_send_unbuffered.c` 发送中等 ACK，外层 poll 超时覆盖不了
底层 send 内部等待。修复：RX/TX 共用 FIFO 分段（整 512 B 块模式 + 尾部字节模式，每事务
最多 4096 B，地址为 FIFO_END 减剩余长度）；整包成功才递增发送配额；
`CONFIG_NET_TCP_WRITE_BUFFERS=y` + `CONFIG_NET_SEND_BUFSIZE=8192`；检查 fcntl/
SO_SNDTIMEO 返回值；header/body 共用写入截止时间；保留 1024 B 分块与进度日志
（`5312/5312` → `phase=http write-complete`）。该修复文档同时提醒：`write-complete` 只证明
数据被 TLS/socket 接受，仍须收到 HTTP 响应才能证明请求成功——该最终证据由 4.2 节
2026-09-20 的"握手/请求/响应全通"补齐。

### 5.3 IOB 池调优（1a3ebca）

IOB 池 96×256B/16 链 → 256/32（`1a3ebca`）。主证据明确其定位：单独无效——瓶颈在 RX 配额
不在池；与 `c09467b` 的配额放开（8→32）互补，为放开后的 TCP 段突发提供池深。当前仓库
`smart_home/defconfig` 实测 `CONFIG_IOB_NBUFFERS=256` / `CONFIG_IOB_NCHAINS=16`，与日志
备忘的"NCHAINS=32"存在出入（疑点已如实标注，不影响闭环结论）。

- LVGL 中控 UI 真机运行（五页 + 屏保 + 聊天/设置/绑定页，字体/图标资源链路见 08）。

**边界（如实）**：

- 摄像头 UI 内实时预览：已实现并真机验收（300 帧 30 fps 通路 + 安防页预览）——验收
  证据：演示视频；C2（连续预览 10 分钟）/C3（20 次进出稳定性）长稳项未测，并入长稳
  后续工作；

  硬冻结系统的 workaround：米家网关配置仅内存态、重启丢失，待根因后恢复 secrets.json 持久化；
- 天气外网连通未通（wttr.in connect timeout，属热点外网问题，不影响米家局域网链路）；
- 不支持附近热点扫描（C6 ESP-Hosted 接口未接入 scan 结果 RPC，不从 UI 伪造热点列表）；
- 长稳/弱网/多 AP 兼容性测试未系统开展；`smart_home_local` defconfig 含明文本地 Wi-Fi
  凭据，仅限本地复现使用；
