## 一、适配背景与目标（与 C6 WiFi 的关系：独立备选网络通路）

本项目以 Route A（custom chip + custom board）方式将 openvela（NuttX 内核）适配到
ESP32-P4X-Function-EV-Board。以太网域目标：为 `smart_home` 配置接入板载以太网，
应用启动时用 `eth0` 完成链路拉起、DHCP、DNS 解析和云端模型请求，作为摄像头预览、
运动检测和模型 Tool 联调的有线网络底座。本期验收 P4X 板端到云端模型的 IPv4 网络
闭环；摄像头数据不通过网络传输，视觉 Tool 只向模型返回受限的结构化结果。

与板载 ESP32-C6 WiFi 的关系（两条独立网络通路）：ESP32-P4 不具备片内 Wi-Fi，本期
不启用 `wlan0`、WAPI 或 `CONFIG_ESPRESSIF_WIFI`（后者依赖 ESP32-C3/C6，不适用于 P4）；
板载 C6 的 ESP-Hosted 接入是独立后续任务，另有方案文档
`docs/开发计划/网络与连接/ESP32-P4X-SmartHome板载C6-WiFi接入方案.md`；本域仅覆盖
板载 ETH 通路（P4 内部 EMAC + 外置 PHY），不依赖也不影响 C6 通路。

README 状态表中"以太网、DNS、TLS、cAGENT、MCP、Node、App Bridge"整体标记为
**待验证**：网络按独立阶段启用，避免干扰已验证的显示（DSI/LVGL）链路。

## 二、适配方案（方案文档的设计）

### 2.1 分层设计与现有基础

项目已有 EMAC 到 `eth0` 的驱动和板级装配，无需新增以太网硬件驱动：

| 层级 | 现有实现（均已核实存在） | 作用 |
| --- | --- | --- |
| 芯片层 | `chips/esp32p4/common/espressif/esp_emac.c` | 初始化 ESP-IDF Ethernet MAC/PHY 并注册 NuttX 网卡 |
| 板级层 | `board/esp32p4/esp32p4-function-ev-board/src/esp32p4_ethernet.c` 的 `board_emac_init()` | 先初始化高精度定时器，再调用 `esp_emac_init()` |
| bring-up | `board/esp32p4/esp32p4-function-ev-board/src/esp32p4_bringup.c` | 在 `CONFIG_ESPRESSIF_EMAC` 下调用 `board_emac_init()` |
| 配置基线 | 方案文档引用 `configs/webpanel/defconfig`；仓库另有独立 `configs/ethernet/defconfig`（见 3.2） | EMAC、PHY、DHCP、DNS 和 NSH 网络诊断配置 |
| 应用层 | `demos/smart_home/src/net/smart_home_network.c` | 非 Wi-Fi 平台选择 `eth0`，依次调用 `netlib_ifup()`、`netlib_obtain_ipv4addr()` 与 DNS 探测 |

### 2.2 启动与所有权

```text
esp_bringup() → board_emac_init() → esp_hr_timer_init() → esp_emac_init()
             → NuttX 注册 eth0 → DSI framebuffer、触摸、摄像头等后续板级初始化
```

Smart Home 不直接调用 `esp_emac_init()`，也不管理 PHY，只操作已注册的 `eth0`：
`smart_home_network_init()` → `netlib_ifup("eth0")` → `netlib_obtain_ipv4addr("eth0")`
→ `getaddrinfo(模型服务域名)` → TLS/HTTP 请求。网络初始化失败时保留 LVGL 本地 UI 和
摄像头本地功能，把 `ifup`/DHCP/DNS 失败状态显示在设置页，不得伪报为模型可用。

### 2.3 DHCP 策略与范围边界

- `smart_home` 由应用启动时显式执行 DHCP，不启用 `NETINIT_THREAD`/`NETINIT_DHCPC`
  第二套自动 DHCP，保证 `eth0` 状态由单一启动路径维护；NSH `renew eth0` 仅作排障。
- 本期不包含：ESP32-C6、ESP-Hosted、Wi-Fi、WAPI、AP 配网、图像上传、云端视觉模型、
  mDNS、Web 面板、Node gateway；不修改 `esp_emac.c`、PHY 寄存器或 RJ45 硬件设计
  （仅当 EMAC 基础验收失败时才进入这些层次）。

## 三、关键代码与配置

### 3.1 `esp32p4_ethernet.c` 职责（实测）

`board_emac_init()`（全文件仅此一个公开函数）：先调 `esp_hr_timer_init()`（注释
说明 `esp_eth_driver_install()` 依赖 esp_timer，须先初始化定时器子系统），失败则
`nerr` 打印并返回；再调 `esp_emac_init()` 完成网卡注册，返回 0 或负 errno。调用点
已核实：`esp32p4_bringup.c` 在 `#ifdef CONFIG_ESPRESSIF_EMAC` 下（约 L520-L524）
调用 `board_emac_init()`，失败时输出 `syslog(LOG_ERR, ...)`。

### 3.2 `configs/ethernet/defconfig` 关键 CONFIG（实测摘录）

`board/esp32p4/esp32p4-function-ev-board/configs/ethernet/defconfig` 为独立 NSH 基线
配置（`CONFIG_SYSTEM_NSH=y`、`CONFIG_INIT_ENTRYPOINT="nsh_main"`），以太网相关行：

```ini
CONFIG_ESPRESSIF_EMAC=y
CONFIG_ESPRESSIF_ETH_DMA_BUFFER_SIZE=512
CONFIG_NETDEV_LATEINIT=y
CONFIG_NETDEV_PHY_IOCTL=y
CONFIG_NET_TCP=y
CONFIG_NET_UDP=y
CONFIG_NET_ETH_PKTSIZE=1514
CONFIG_NET_BROADCAST=y
CONFIG_NET_ICMP_SOCKET=y
CONFIG_NETDB_DNSCLIENT=y
CONFIG_NETINIT_THREAD=y
CONFIG_NETINIT_DHCPC=y
CONFIG_FS_PROCFS=y
CONFIG_SYSTEM_DHCPC_RENEW=y
CONFIG_SYSTEM_PING=y
CONFIG_NETUTILS_IPERF=y
```

与方案文档的出入（以实际文件为准）：

1. 实际 defconfig 含 `CONFIG_NETINIT_THREAD=y`、`CONFIG_NETINIT_DHCPC=y`，而方案
   文档 4.2 针对 `smart_home` 明确选择应用层显式 DHCP、不启用这两项；两者分属不同
   配置目标——`configs/ethernet` 是无 smart_home 应用的独立 NSH 基线，自动 DHCP
   交由 netinit 线程完成。
2. 方案最小集合中的 `CONFIG_NET=y`、`CONFIG_NET_IPv4=y`、`CONFIG_NETUTILS_DHCPC=y`
   未显式出现（savedefconfig 只记录非默认值，派生符号以最终 `nuttx/.config` 为准）；
   实际 defconfig 另含方案未列的 `CONFIG_NETUTILS_IPERF=y`。

### 3.3 构建与烧录命令（按 README 统一入口，`configs/ethernet` 目标）

```bash
cd ~/openvela
./build.sh contest2026_031_niudanxianqianchong/board/esp32p4/esp32p4-function-ev-board/configs/ethernet -j2

esptool --chip esp32p4 --port /dev/ttyACM0 --baud 921600 \
  write-flash -fs 16MB -fm dio -ff 80m \
  0x2000 nuttx/nuttx.bin

picocom -b 115200 /dev/ttyACM0
```

## 四、验证计划与当前状态

### 4.1 当前状态（如实）

- 方案文档自述："方案阶段，尚未在'Smart Home + 摄像头 + 以太网'组合固件上完成实板
  验证"；README 状态表中以太网等网络能力为"待验证"，网络作为独立后续阶段启用。
- 板级驱动 `esp32p4_ethernet.c`、`esp32p4_bringup.c` 调用点、`configs/ethernet/defconfig`
  均已入库（本次已逐一核实存在），即"方案 + 代码就绪"；但 `eth0` 实板获得 IPv4、
  DNS/TLS 连通等验收证据尚无，**本域状态如实标注为：待真机验证**。

### 4.2 验证步骤（源文档给出的 P1~P3）

P1 独立 EMAC 基线：派生最小 EMAC 网络配置，编译烧录，接入 DHCP 网络的 RJ45 网线，观察
启动日志 `board_emac_init()` 是否成功，然后在 NSH 执行：

```text
nsh> ifconfig
nsh> ifup eth0
nsh> renew eth0
nsh> ifconfig eth0
nsh> ping <网关IPv4地址>
nsh> ping <公网IPv4地址>
```

验收：`eth0` 获得非零 IPv4、网关和 DNS；网关与公网 IP 连通。

P2 DNS 与 TLS 基线：确认 LittleFS 中存在 `/data/res/skills/` 和模型 endpoint 配置；
网络日志出现 `[smart_home_net] init-end if=eth0 ip=<IPv4> gateway=<IPv4> ... online=1`；
在不打印密钥的前提下发起一次只读 Tool 请求。验收：DNS 探测成功、TLS/HTTP 获得模型
响应、UI 不因网络初始化阻塞。

P3 摄像头共存：保持网线连接，确认 `/dev/video0` 存在，`video_test 300` 复核 30fps，
启动 Smart Home 复核 `eth0` 地址并执行一次模型请求。验收：网络、DSI/LVGL、摄像头
三者可共同启动，失败日志可明确归属到 EMAC、DHCP/DNS、显示或 CSI。

### 4.3 提交与证据要求（源文档第 9 节）

提交前至少需要：`smart_home` 配置编译通过；最终 `.config` 确认 EMAC、DHCP、DNS、
非离线 Smart Home 和 SC2336 配置；实板日志证明 `eth0` 获得 IPv4 且 DNS 探测成功；
声明云端模型可用时附一条脱敏的模型 Tool 调用日志；同时启用摄像头时附 `video_test 300`
复测结果。未通过验证的探索性变更不拆分为"尝试修复"提交。

## 五、遇到的问题与解决

暂无已记录问题：源文档与 README 均未记录以太网域已实际发生的故障或修复。方案文档
第 8 节提供"失败定位"对照表（预期风险排查指引，非已发生问题），真机验收时可按表
定位，例如：启动没有 `eth0` 时优先检查 `CONFIG_ESPRESSIF_EMAC`、`board_emac_init()`
返回值与 PHY 链路，而非打开 WAPI 或修改摄像头驱动；`eth0` 无 IPv4 时优先检查 DHCP
服务器、VLAN、网线与 `netlib_obtain_ipv4addr()` 日志，而非归因于模型 API Key。
