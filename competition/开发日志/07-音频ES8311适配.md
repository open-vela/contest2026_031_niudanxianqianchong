## 一、适配背景与目标（ES8311 codec + I2S 数据面 + 语音链路 TTS/ASR/KWS）

在 openvela/NuttX 中打通板载音频全链路，目标数据通路（摘自适配方案第 1 节）：

```text
板载麦克风
  -> ES8311 ADC -> I2S0 RX + DMA -> /dev/pcm_in0
  -> smart_home 采集线程 -> PCM16 单声道 -> ASR / KWS

TTS / 提示音 PCM
  -> /dev/pcm0 -> I2S0 TX + DMA -> ES8311 DAC
  -> NS4150B 功放 -> 板载扬声器接口
```

第一期只验收 16 kHz、16-bit、单声道 PCM 的稳定录音和播放；云端 ASR/TTS 协议、AEC、波束成形、常驻唤醒词模型不在本期范围。复用 NuttX 通用 lower-half（`nuttx/drivers/audio/es8311.c`），以 NuttX Audio upper-half/lower-half 架构注册 `pcm0`（播放）与 `pcm_in0`（采集）两个端点，不在应用层直接操作 I2S 寄存器。板级连接事实（SCL 8 / SDA 7 / BCLK 12 / MCLK 13 / WS 10 / DOUT 9 / DIN 11 / PA 53）来自乐鑫官方用户指南与 BSP API，I2C 地址以实板确认为 `0x18`。

## 二、适配流程

按实际阶段推进：**适配方案 → codec 装配与 I2S → GDMA 问题复盘 → 语音链路首次构建排障闭环**。

### 阶段 1：适配方案设计（docs/硬件适配/ESP32-P4X-Function-EV-Board-ES8311音频适配方案.md）

- 确认仓库能力边界：NuttX 已有 ES8311 lower-half、P4 I2S 驱动已含 TX/RX 与 DMA；缺的是 board glue 与 `esp32p4_bringup.c` 中的初始化调用。
- 设计 board 级 Kconfig 开关 `ESP32P4_FUNCTION_EV_BOARD_AUDIO_ES8311`（select 音频框架、I2S0、I2C0 master；不 select `AUDIO_I2SCHAR`），并规划 `esp32p4_es8311.c` 等 6 处文件改动。
- 明确 `configs/i2schar` 是通用回环/字符设备测试配置（DINPIN/DOUTPIN 均为 GPIO10），不得直接合并进 smart_home defconfig，也不得作为"板载麦克风、扬声器已经可用"的证据。
- 制定 A0（硬件复核）至 A7（Smart Home 接入）的分级验收阶梯与 PCM 质量标准。

### 阶段 2：codec 装配与 I2S 打通（docs/开发日志/ESP32-P4X-ES8311-Codec适配与GDMA问题复盘.md）

- 修正 ES8311 单字节寄存器读的 I2C 接收长度（`patches/nuttx/0001`）。
- 新增 Function EV Board 的 ES8311 glue：初始化 I2C0/I2S0，注册播放/录音节点；配置 I2S0 master RX/TX、MCLK、16 kHz、PCM16，GT911 与 ES8311 正常共享 I2C0。
- 新增 `audio_smoke` 验收命令：`play [seconds]` 输出低幅度 1 kHz 音调，`record [seconds] [path]` 写原始 PCM 文件。
- 解决 Kconfig 音频框架依赖与 `es8311_initialize` 链接缺失（详见第五章 5.1 前两条）。

### 阶段 3：GDMA 问题复盘与 codec 运行期排障（同上文档）

- 真机暴露 I2S0 RX GDMA 创建失败（257/-12）并引发全局 `-12` 连锁，最终以"全双工一次申请同一 GDMA pair"修复（提交 `8201995`），不改 `esp-hal-3rdparty`。
- 后续沿 `-ERANGE` 误报、启动边界、裸 PCM 解码、I2S 提交失败回收逐项排障，沉淀 `patches/nuttx/0003`~`0009`；`audio_smoke play 1` 运行期卡住收敛到"待非侵入式栈取证"，**进行中**。

### 阶段 4：语音链路（TTS/ASR/KWS）首次构建排障闭环（docs/开发日志/编译/2026-09-20-语音链路TTS-ASR-KWS首编排障闭环.md）

- 语音链路五阶段合入（`2390838`…`520c02b`）后，`smart_home_voice` 配置首次构建，历经 5 轮错误、11 个修复提交，最终构建成功：`nuttx.bin` 1.45 MB，六个 NSH 命令全部注册，内存占用安全（详见第四章）。
- 核心教训（逐字）："从未被编译过的代码"不可信任——无论它来自别的分支、别的 worktree，还是看起来正规的依赖配置集。

## 五、遇到的问题与解决

### 5.1 codec 装配与 GDMA/运行期（出处：GDMA 复盘）

1. **Kconfig 依赖未满足**。现象：`olddefconfig` 报 `AUDIO_ES8311` 直接依赖 `AUDIO && DRIVERS_AUDIO` 为 `n`。定位：选中 codec 驱动不等于音频框架已启用。修复：补齐音频框架、I2S0 RX/TX 与板级选项依赖。复测：检查最终 `.config` 而非仅看 defconfig 行。
2. **链接缺符号**。现象：`undefined reference to 'es8311_initialize'`。根因：ES8311 驱动对象未随音频框架进入 `libdrivers.a`（构建集成问题）。修复：补齐驱动与框架配置后链接产物包含 codec 驱动。
3. **I2S0 RX GDMA 创建失败 257/-12 并连锁**。现象（逐字）：`ERROR: I2S0 GDMA RX create failed: 257`、`ERROR: I2S0 DMA setup failed: -12`、`Failed to initialize ES8311 audio: -19`；随后 WLAN/DSI/GT911/MTD 出现 `-12`。定位：`257` 为 ESP-IDF `ESP_ERR_NO_MEM`；TX 成功后第二次 `gdma_new_ahb_channel(RX)` 进入已有 GDMA group/pair 路径，pinned HAL 在该路径预分配/释放，与 `CONFIG_MM_KERNEL_HEAP=y` 下 `heap_caps_calloc()` 跨堆释放存在兼容风险（失败前后内核堆已用量 5408 B→5488 B，未恢复原状）。根因：全双工两个方向拆成两次 GDMA 申请。修复：`i2s_dma_setup()` 中 TX/RX 同启用时一次申请同一 GDMA pair（提交 `8201995 fix(esp32p4): allocate duplex I2S GDMA pair atomically`）；不改 `esp-hal-3rdparty`（曾短暂保存的 HAL 补丁已由提交 `c38c949` 移除）。复测：重启日志 GDMA 初始化完成，`257`/`-ENOMEM` 未再出现。
4. **配置阶段误报 `-ERANGE`**。现象：`audio_smoke: play failed: -34 (Math result not representable)`，发生在 `AUDIOIOC_CONFIGURE`。根因：通用 ES8311 lower-half 中 `ret` 预置 `-ERANGE`，旧代码仅在下层返回 `-ENOTTY` 时改写成功，下层返回 `OK` 时仍保留旧值。修复：`es8311_setsamplerate()`/`es8311_setbitspersample()` 返回值直接赋给 `ret`，固化为 `patches/nuttx/0003-es8311-propagate-configure-errors.patch`。复测：待重新编译真机确认。
5. **裸 PCM 被 decoder 拒绝 + 错误路径不完整**。定位：`pcm0` 注册为 PCM decoder，而 `audio_smoke` 写无 WAV header 的裸 PCM16，首个 buffer 被当 header 解析拒绝；另 `file_mq_receive()` 负 errno 与无符号 `sizeof` 比较导致读取未初始化 `msg.msg_id`；I2S 提交立即失败时 `inflight` 不回退、drain 永久等待。修复：启用 `CONFIG_AUDIO_FORMAT_RAW=y`；`patches/nuttx/0008-es8311-recover-from-submit-and-mq-errors.patch` 修复负消息长度判断、提交失败回退/`AUDIO_CALLBACK_IOERR`/buffer 交还。诊断配套：`0004`~`0007`、`0009` 分阶段记录启动/worker/I2C 边界并降级成功路径日志，`WORKER_STACKSIZE` 2048→4096。
6. **`audio_smoke play 1` 仅打印开始提示后不返回（进行中）**。现象（逐字）：`audio_smoke: play 1 s, 16 kHz mono PCM16` 后无 `play complete`、错误码或提示符；重启日志确认 `/dev/audio/pcm0`、`/dev/audio/pcm_in0` 已注册、GDMA 无 `257`/`-ENOMEM`、WLAN/DSI/GT911/LittleFS 正常。定位：问题收敛到 `AUDIOIOC_START`、`AUDIOIOC_ENQUEUEBUFFER`、PCM decoder、ES8311 worker、`I2S_SEND`、DMA 完成回调之一；真机日志曾见 `AUDIOIOC_START` 已返回、`[audio_smoke] start OK` 被截断为 `[audio_`，`enqueue initial buffer` 未出现。下一步：后台运行 + `dumpstack` 采集应用与 worker 栈，按栈位置实施最小修复。复测：未完成。
