## 一、适配背景与目标

### 1.1 为什么选 ESP32-P4

ESP32-P4 相对 ESP32-S3 的硬件跨度（摘自 `docs/硬件适配/esp32p4-ev-board-adaptation.md` §1.2）：

| 特性 | ESP32-S3 | ESP32-P4 |
| --- | --- | --- |
| CPU 架构 | Xtensa LX7 双核 240MHz | RISC-V HP 双核 400MHz + LP 单核 40MHz |
| 内部 SRAM | 512 KB | 768 KB (HP) + 32 KB (LP) |
| 显示接口 | SPI LCD (320×240) | MIPI-DSI（最高 1080p） |
| 摄像头 | 无原生接口 | MIPI-CSI（最高 1080p） |
| USB | USB-OTG 1.1 | USB-OTG 2.0 HS |
| 以太网 | 无 | 内置 EMAC |
| WiFi/BLE | 内置 | SoC 无内置，本板通过板载 ESP32-C6 提供无线协处理能力 |
| NuttX arch | `boards/xtensa/esp32s3/` | `boards/risc-v/esp32p4/` |

适配动机：截至 2026 年 6 月，Apache NuttX 主线已包含 ESP32-P4 完整支持，
但 openvela 的 NuttX 分支（`dev-ai-contest-2026`）**尚未合入** ESP32-P4
（`nuttx/arch/risc-v/src/` 与 `nuttx/boards/risc-v/` 下均无 `esp32p4/` 目录），
需要从上游迁入（同文档 §2.1/§2.2）——这是"新芯片适配"技术难度的直接来源。

### 1.2 Route A 架构说明

openvela 有两种移植路线（`esp32p4-ev-board-adaptation.md` §10.3）：

| 路线 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Route A | 在项目目录提供 custom chip / custom board | 适合比赛项目，改动集中，不污染 openvela 主树 | 需要自己处理 Kconfig、Make.defs、路径兼容 |
| Route B | 直接把芯片和板级合入 openvela `nuttx/arch`、`nuttx/boards` 或 `vendor` | 更像正式 upstream port | 改动面大，冲突更多，比赛项目维护成本高 |

本项目选择 Route A 的原因（同节）：ESP32-P4 尚不在当前 openvela 分支原生存在；
比赛项目需要快速验证；custom chip/custom board 机制本就是为项目级移植准备的；
验证稳定后再考虑整理成正式 vendor/chip 目录。

### 1.3 本仓目录 → openvela 构建树位置映射

manifest linkfile 将本仓源码链接到构建系统可见的 vendor 位置
（`README.md`「目录与构建关系」；`esp32p4-ev-board-adaptation.md` §10.2）：

| 本仓目录 | OpenVela 构建树位置 | 用途 |
| --- | --- | --- |
| `chips/esp32p4/` | `vendor/espressif/chips/esp32p4/` | P4 custom chip、Espressif HAL 与 MIPI-DSI Host 适配 |
| `board/esp32p4/common/` | `vendor/espressif/boards/esp32p4/common/` | P4 板级共享代码和链接脚本 |
| `board/esp32p4/esp32p4-function-ev-board/` | `vendor/espressif/boards/esp32p4/esp32p4-function-ev-board/` | P4X 配置、bring-up、DSI framebuffer 与 GT911 装配 |
| `drivers/nuttx/` | 软链接到 `nuttx/drivers/` | EK79007、GT911 的竞赛维护源码 |
| `app/` | `apps/packages/demos/` | `dsi_probe`、`gt911_probe` 等独立硬件验证程序 |
| `demos/smart_home/` | `apps/packages/demos/` | P2 静态首页与 P3.2 正式离线 Smart Home LVGL UI |

配置完成后 openvela 在 nuttx 树内建立的链接（§10.2，"Route A 是否接通的
第一验收点"）：

```text
nuttx/arch/risc-v/src/chip  -> contest.../chips/esp32p4
nuttx/arch/risc-v/src/board -> contest.../board/esp32p4/common
nuttx/arch/risc-v/src/board/board -> contest.../board/esp32p4/esp32p4-function-ev-board/src
```

## 二、适配流程

以下按源文档记录的实际执行顺序整理（依据 `esp32p4-ev-board-adaptation.md` §10.4）：

### 阶段 1：源树定位

从上游 Apache NuttX 定位 P4 三层源码（Step 1，命令逐字摘录）：

```bash
ls ~/nuttx/arch/risc-v/src/esp32p4
ls ~/nuttx/arch/risc-v/src/common/espressif
ls ~/nuttx/boards/risc-v/esp32p4/esp32p4-function-ev-board
```

（另核对 `arch/risc-v/include/esp32p4` 与 `boards/risc-v/esp32p4/common`。）
NuttX/openvela 移植分三层：arch common layer（RISC-V trap、上下文切换）、
chip layer（ESP32-P4 clock/cache/irq）、board layer（引脚、外设初始化、
链接脚本）。ESP32-P4 既需要 chip layer 也需要 Espressif common layer，
"只复制 `esp32p4/` 目录是不够的"。

### 阶段 2：custom chip 芯片层落位（Step 2 / Step 4）

- 复制上游 `arch/risc-v/src/esp32p4/`、`arch/risc-v/include/esp32p4`、
  `arch/risc-v/src/common/espressif` 到 `chips/esp32p4/`（含 `common/espressif`）。
- 改造 `chips/esp32p4/Kconfig`：在 `ARCH_CHIP_CUSTOM` 下定义
  `ARCH_CHIP_ESP32P4` 并 select `ARCH_RV32`、`ARCH_RV_ISA_M/A/C`、
  `ARCH_CHIP_ESPRESSIF`、`ARCH_MINIMAL_VECTORTABLE`，提供
  `ESPRESSIF_CHIP_SERIES="esp32p4"` 与 `ESPRESSIF_SIMPLE_BOOT=y` 默认值；
  不重复定义 openvela common espressif 已有的 flash choice symbol。

### 阶段 3：板级 bring-up（Step 3 / Step 5）

- 复制上游 `esp32p4-function-ev-board` 与 `boards/risc-v/esp32p4/common`
  到 `board/esp32p4/` 下（P4 的 Make/CMake 依赖 board common，必须一并迁入）。
- 改造 `board/esp32p4/esp32p4-function-ev-board/Kconfig`：在
  `ARCH_BOARD_CUSTOM` 下提供 `ARCH_BOARD_ESP32P4_FUNCTION_EV_BOARD` symbol。

### 阶段 4：defconfig 改造为 Route A（Step 6）

对 `configs/*/defconfig` 统一改造（2026-07-04 记录 35 个已改造为 Route A custom
模式；当前 `configs/` 实测含 43 个子目录，含项目自增 `dsi_probe`、`smart_home`
系列等）。最小 `nsh` 配置关键项：

```ini
CONFIG_ARCH="risc-v"
CONFIG_ARCH_BOARD_CUSTOM=y
CONFIG_ARCH_BOARD_CUSTOM_DIR="../contest2026_031_niudanxianqianchong/board/esp32p4/esp32p4-function-ev-board"
CONFIG_ARCH_BOARD_CUSTOM_NAME="esp32p4-function-ev-board"
CONFIG_ARCH_CHIP_CUSTOM=y
CONFIG_ARCH_CHIP_CUSTOM_DIR="../contest2026_031_niudanxianqianchong/chips/esp32p4"
CONFIG_ARCH_CHIP_CUSTOM_NAME="esp32p4"
CONFIG_ARCH_CHIP_ESP32P4=y
CONFIG_ARCH_RISCV=y
CONFIG_RISCV_TOOLCHAIN_GNU_RV32=y
CONFIG_ESPRESSIF_CHIP_SERIES="esp32p4"
CONFIG_ESPRESSIF_SIMPLE_BOOT=y
```

（完整配置另含 `*_DIR_RELPATH=y` 等项与 flash 三项，见源文档 §10.6。）
`CONFIG_RISCV_TOOLCHAIN_GNU_RV32=y` 若缺失，构建会退回宿主 gcc 并在
`UINTPTR_MAX` 等宏处报错。

### 阶段 5：构建系统兼容修补（Step 7 / Step 8）

- `chips/esp32p4/Make.defs` 改用相对路径 include common（`mkdeps` 对绝对 VPATH 处理不稳定）。
- `common/espressif/Make.defs` 为 P4 HAL 补 flash CFLAGS 默认宏（`CONFIG_ESPRESSIF_FLASH_16M=1` 等），否则报 flash clock invalid。
- board `scripts/Make.defs` 补 `CONFIG_STACK_USAGE_WARNING ?= 0`。
- 迁入代码 `#include <nuttx/debug.h>` 替换为 `#include <debug.h>`（openvela 与上游头文件布局差异）。

### 阶段 6：最小系统 usbconsole/nsh 真机启动

- 2026-07-04 时状态（§10.1）：配置阶段已打通、HAL 拉取已验证可进行、
  `nsh` 完整编译尚未通过（构建被中断），板上启动未完成。
- 其后按 `docs/硬件适配/esp32p4-nsh-operation-and-test.md` 的构建、烧录、
  串口流程完成上板；README.md 记录截至 2026-08-24：USB Serial/JTAG 与
  NSH 通过（串口进入 `nsh>`，可执行内建命令），`nsh` 固件构建、烧录和启动通过。
- 差异对照文档 §3.2 亦记录：本项目"已支持 `ESP32P4_REV_MIN_301`，并已能
  烧录进入 NSH"、"USB console / NSH 已验证"。

### 阶段 7：ESP-HAL 治理

`chips/esp32p4` 下曾同时存在规范 HAL 检出与一份约 531 MiB 的旧本地副本，
2026-09-10 完成清理并固化当前 HAL 提交（详见第五章案例 1）。

为"已上板验证"。

### 4.2 证据分级：枚举成功 ≠ 数据有效

按 `ESP32-P4竞赛参考差异对照.md` §7 验收矩阵整理（同样约束本项目验收口径）：

| 阶段 | 必须观察到的结果（数据有效级） | 不应作为通过条件（仅枚举/活动级） |
| --- | --- | --- |
| SoC 基线 | NSH、USB console、重启、GPIO/IRQ、I2C 均稳定 | 单次能烧录 |
| DSI 像素流 | 真实屏幕可见并稳定显示 RGB565 色条 | DMA 计数增加、无 underrun |
| framebuffer | `/dev/fb0` 可枚举，应用写入后可见 | `up_fbinitialize()` 返回 OK |
| touch | `/dev/input*` 有稳定坐标、方向正确 | I2C probe 有 ACK |
| LVGL | LVGL 刷新、触摸、重绘持续稳定 | 静态首帧显示 |

数据有效级真机证据示例（逐字摘自 `README.md`，GT911 单指触摸，属显示/触摸
专题，仅作"数据有效"口径实例引用）：

```text
DOWN id=0 x=944 y=133 size=30x30 flags=0x59
MOVE id=0 x=944 y=133 size=30x30 flags=0x5a
UP   id=0 x=944 y=133 size=30x30 flags=0x5c
```

README 同时注明：按住不动时坐标相同的重复 `MOVE` 属于驱动保留完整有效帧的
策略，不代表触摸卡死；手指移动时坐标应连续变化，松开后必须出现 `UP`。

## 五、遇到的问题与解决

### 5.1 Route A 构建打通阶段已解决问题（摘自 `esp32p4-ev-board-adaptation.md` §10.5）

| 错误/现象 | 原因 | 处理 |
| --- | --- | --- |
| `chip/hal_.mk` 找不到 | `CONFIG_ESPRESSIF_CHIP_SERIES` 为空 | 在 custom Kconfig/defconfig 中提供 `esp32p4` |
| Kconfig duplicate / choice warning | custom Kconfig 重复定义 openvela common espressif symbols | 删除 custom Kconfig 中重复 flash choice 定义 |
| `fatal error: nuttx/debug.h: No such file or directory` | 上游 NuttX 与当前 openvela 头文件路径不同 | 改为 `#include <debug.h>` |
| `mkdeps` 找不到 common/espressif 源文件 | absolute VPATH 与当前 Make 流程不兼容 | 改为 `chip/common/espressif` 相对路径 |
| `SPI timing flash clock is invalid` | HAL 未拿到 flash mode/freq/size 配置宏 | 在 Make.defs 中补 P4 flash 相关 CFLAGS |
| `clean_bootloader` target 缺失 | distclean 调用了当前 bootloader 模式下未定义的目标 | 在 Bootloader.mk 中补 fallback target |
| `gcc: error: missing argument to '-Wstack-usage='` | `CONFIG_STACK_USAGE_WARNING` 无默认值但被 Make 判断为非 0 | board Make.defs 中补 `CONFIG_STACK_USAGE_WARNING ?= 0` |
| 使用宿主 `gcc` 编译出现 `UINTPTR_MAX` 等宏错误 | 未选择 RISC-V 工具链 | 35 个 defconfig 补 `CONFIG_RISCV_TOOLCHAIN_GNU_RV32=y` |

### 5.2 案例 1：ESP-HAL 旧副本清理（源：`docs/开发日志/ESP32-P4X-ESP-HAL旧副本清理记录.md`，2026-09-10）

- **现象**：`chips/esp32p4` 下同时存在 `esp-hal-3rdparty` 与
  `esp-hal-3rdparty.incomplete-local-copy` 两个 HAL 检出，后者约 531 MiB，
  易使开发者误用不匹配头文件或本地修改参与 P4 构建。
- **定位**：逐项比对——当前依赖提交 `b90b1837cb5ad24747deb4c895246037cc206ce5`
  （2026-07-01，受跟踪文件 9,787）与旧副本提交
  `9fc713a95b1ff150dd0b0647e465d3c624056bb1`（2025-06-18，4,551）不构成前后继
  关系，2,653 个同路径文件中 1,814 个内容不同；旧副本缺少 P4 构建所需的
  `nuttx/esp32p4` 和 `nuttx/src/platform/os.c`；构建侧无任何对旧副本的引用。
- **根因**：旧副本来自早期本地恢复过程，不是当前依赖的可替换缓存；其

- **复测**：执行 3.4 节所列验证命令；本次清理不改变参与编译的源文件、

### 5.3 案例 2：头文件结构体变更与陈旧对象蓝屏（源：`docs/开发日志/编译/2026-09-19-头文件结构体变更与陈旧对象蓝屏.md`，2026-09-18~19）

- **现象**：两轮 SmartHome UI 提交在真机出现无法用代码逻辑解释的"蓝屏"死机：
  控制台停在 `build settings` 打印中途，截断在 `[smart_home_lvgl] bui`；回退
  三需求仅保留首页修复（`fa35aaa`）后崩溃点**漂移**到 `build network begin`；
  行内截断、无 panic 转储、屏幕冻结为纯蓝、`nsh>` 无响应；崩溃点不在被改动
  代码的执行路径上。
- **定位**：二分排障（回退 `ea322e0` 稳定开机；仅保留 `0b479d3` 正常；
  仅保留 `fa35aaa` 必崩）；栈溢出假设被证伪（1.5 KiB 数组静态化后仍崩溃）；
  决定性证据是对象文件时间戳：`lvgl.h` 于 09-18 23:31 构建中含新增
  `home_miloco_sub_label` 字段（`smart_home_lvgl_t` +8 字节），09-19 11:54
  回退该头文件后只有 home.o/nav.o 重编，chat.o 等仍停留在前夜。
- **根因**：`apps/packages/demos/smart_home` 的增量构建对该应用事实上不跟踪
  头文件依赖；部分对象按"新/旧布局"访问同一结构体实例，两套偏移写入互相
  踩踏，症状在几屏之后随机引爆。
- **修复**：恢复 `fa35aaa` 代码后删除全部对象强制全量重编：

  ```bash
  find demos/smart_home/src -name "*.o" -delete
  rm -f demos/smart_home/Make.dep
  ./build.sh ... # 正常启动
  ```

- **复测与规矩**：全量重编后正常启动。开发约定：凡修改 `smart_home_lvgl.h`
  等被多个 .c 广泛包含的头文件后，必须先删除 `demos/smart_home/src` 下全部
  `.o` 与 `Make.dep` 再构建烧录；增量构建结果在此应用上不可信。
