# ESP32-P4X SMP 音频链路：排查结论与修复方案（v2.0）

> 2026-11-01 | 承接 [ESP32-P4X-SMP音频链路故障分析.md](ESP32-P4X-SMP音频链路故障分析.md)（v1.0）
> 本文只做两件事：把 v1.0 的候选根因逐条落到代码行，给出一次上板即可定性的定位矩阵，以及可直接落地的补丁。
> 前提断言：当前没有任何一次音频故障的板端日志，所以本文不宣称"根因已确认"，只给出"已核实的违规点 + 判读规则"。

---

## 一、现象与当前的构建状态

| 项 | 值 | 来源 |
|---|---|---|
| 现象 A | 音频链路不可用（播放/录音失败） | 用户反馈 |
| 现象 B | SMP=y 且 ES8311/I2S0=y 时进不去 NSH | 用户反馈 |
| 现象 B' | 同配置关掉 ES8311/I2S0 可进 NSH，其余子系统全通 | v1.0 已验证 |
| 当前 .config | CONFIG_SMP=y、SMP_NCPUS=2、ESP32P4_FUNCTION_EV_BOARD_AUDIO_ES8311=y | ~/openvela/nuttx/.config |
| 当前 defconfig | 音频相关 13 行被注释（**未提交**的工作区规避） | smart_home/defconfig |

结论：现在工作区就是"能复现故障"的配置，但 defconfig 里的音频被注释掉了，重新复现前必须先恢复（见附录 A）。

## 二、已核实的事实链

### 2.1 启动路径（AppBringUp 线程）

~~~text
nx_start()
  └─ nx_create_initthread()            nuttx/sched/init/nx_bringup.c:452
       AppBringUp, 内核线程, prio=240, stack=CONFIG_BOARD_INITTHREAD_STACKSIZE=2048
       └─ nx_start_task → nx_start_application
            └─ board_late_initialize()          nx_bringup.c:332
                 └─ esp_bringup()               esp32p4_bringup.c
                      ├─ board_i2c_init()                    (GT911 也用 I2C0)
                      ├─ board_es8311_initialize()   :348   ← 音频唯一入口
                      │    ├─ esp_i2sbus_initialize() → i2s_buf_initialize() → 4×i2s_buf_free()
                      │    │                           → i2s_configure() → i2s_dma_setup()
                      │    ├─ esp_i2cbus_initialize()
                      │    ├─ es8311_initialize() ×2 (寄存器初始化, 走 I2C)
                      │    ├─ pcm_decode_initialize() / audio_register("pcm0"/"pcm_in0")
                      │    └─ "INFO: ES8311 ready"
                      ├─ board_mipi_dsi_fb_initialize() / board_gt911_initialize()
                      └─ ...
~~~

关键点：音频是整个 bringup 里唯一"在 2048 字节的内核线程栈上做 I2C + 堆申请 + GDMA 申请 + 中断注册 + 多行 syslog"的子系统，也是它和"关掉音频就能起来"最直接的差异来源。

### 2.2 音频线程是"懒创建"的

es8311_workerthread 在 AUDIOIOC_START 才 pthread_create（nuttx/drivers/audio/es8311.c:1576-1592，SCHED_FIFO max-3，栈 CONFIG_ES8311_WORKER_STACKSIZE=4096）。

推论：**现象 B（进不去 NSH）不可能发生在 worker 里**——那时 worker 还不存在。B 只能发生在 board_es8311_initialize() 之内或其后。这条把 v1.0 的候选面砍掉一半。

## 三、代码级隐患（已逐条核实）

### D1【P0】自旋锁内做堆分配/释放 —— 每次音频缓冲都要走一次

chips/esp32p4/common/espressif/esp_i2s.c

| 行 | 动作 |
|---|---|
| 569 | flags = spin_lock_irqsave(&priv->slock);（关本核中断 + 拿 rspinlock） |
| 583 | kmm_memalign(alignment, size) **在临界区内**，循环 I2S_DMADESC_NUM=2 次 |
| 601-602 | 失败回滚时也在临界区内 kmm_free |
| 640 | i2s_buf_free() 同样 spin_lock_irqsave |
| 645 | kmm_free(bfcontainer->dma_link[i]) **在临界区内**，2 次 |
| 680-690 | i2s_buf_initialize() 上电时连做 4 次 i2s_buf_free() → **8 次 kmm_free 全程关中断** |

- 单核：堆无竞争，nxsem 立即返回，"能用"。
- SMP：堆锁是 rmutex，另一核持有时本核**在中断关闭状态下阻塞**；同时 priv->slock 是 rspinlock_t（os.h:86），HAL 的临界区也是"先 up_irq_save 再 rspin_lock"（os.c:1097）。两条路径一旦交叉（音频 vs HAL/GDMA/periph_rcc）就是**双核硬死锁，且关着中断，连看门狗喂狗都停**。
- 触发时机：正好是 bringup 里的 i2s_buf_initialize()，与"关音频就好了"吻合度最高。

### D2【P0】等待无超时

esp_i2s.c:561 用 nxsem_wait_uninterruptible(&priv->bufsem)；bfcontainer->timeout 只在 :3220 赋值，**全树无消费点**（已 grep：只有结构体定义、赋值和注释）。丢一次 DMA 完成 → 永久阻塞。

### D3【P1】上层 ioctl 跨越整个 switch 持锁

nuttx/audio/audio.c:935 取 nxmutex_lock(&upper->lock)，:1299 才释放，中间调用 lower 的 configure/enqueuebuffer。双核下 lower 的回调可以在另一核立刻进入 audio_callback 抢同一把锁 → 引用计数/DONE 与 STOP 交错。**这是现象 A（音频不可用）的最可能来源，与 B 无关。**

### D4【P1】亲和性靠"恰好"

esp_i2s.c:3534 priv->cpu = this_cpu()，GDMA 中断绑在 bringup 时那颗核（CPU0）；worker 继承 SMP_DEFAULT_CPUSET=0x1。现在"刚好都在 CPU0"，任何一次负载均衡调整都会变成跨核唤醒 + FIFO 优先级反转。

### D5【P1】APB 落在 PSRAM + Flash 关 cache

libs/libc/audio/lib_buffer.c:61 用 lib_umemalign() 走用户堆；本配置开了 PSRAM 用户堆。Flash 擦写会关两颗核的 cache，此时另一核碰 PSRAM 缓冲 → 取指/取数异常。潜伏项，音视频并发 + LittleFS 写时会暴露。

### D6【P0 触发条件】初始化时序

见 2.1/2.2：音频是 bringup 里唯一"重"的初始化；worker 尚未创建，所以 B 只能发生在 bringup 内。

### D7【待实测】AppBringUp 只有 2048 字节栈

在单核 + 音频的构建（out/smart-home-session-c7f1916/nuttx）上用 objdump 实测的栈帧：

| 函数 | 帧(B) |
|---|---|
| esp_bringup | 16 |
| board_es8311_initialize | 48 |
| board_es8311_log_kheap | 64 |
| esp_i2sbus_initialize | 144 |
| i2s_buf_free | 32 |
| gdma_new_ahb_channel | 64 |
| es8311_initialize | 32 |
| pcm_decode_initialize | 16 |
| audio_register | 64 |
| syslog / nx_vsyslog / vsnprintf | 64 / 64 / 48（其下还有 lib_vsnprintf 深调用） |

常驻帧合计约 500 B，看起来余量 1.5 KB；但 syslog 的格式化链是 NuttX 里最深的调用之一，加上 SMP 下中断上下文保存更大，**不能排除偶发溢出**。判定方法见 §4 的 A 步（栈提到 4096 只需一次烧录）。

### D8【需知悉】HAL 的取锁顺序是"先关中断、后拿锁"

chips/esp32p4/esp-hal-3rdparty/nuttx/src/platform/os.c:1097-1150：up_irq_save() → rspin_lock(lock)；且 if (OSINIT_OS_READY()) 才真正取锁——**调度器未启动时不互斥**。

- 影响 1：periph_rcc_enter()、gdma.c 的 esp_os_enter_critical(&pair->spinlock)（:130/:201）全是这套。
- 影响 2：任何"持 HAL 锁再调用会阻塞的 API"（含 D1 的堆操作）都退化成嵌套关中断 + 自旋。

### D9【需知悉】CONFIG_ESP_SYSTEM_SINGLE_CORE_MODE=1 在 SMP 构建里被硬置

chips/esp32p4/esp-hal-3rdparty/nuttx/esp32p4/include/sdkconfig.h:19，注释说明是为了防止 HAL 自己再拉一遍 CPU1。它**不**影响 OS_SPINLOCK（后者由 CONFIG_FREERTOS_UNICORE 决定，见 os.h:52-62），但会让 HAL 里按单核分支编译的代码路径在双核下运行，**排查时不要假设 HAL 行为与 ESP-IDF 双核文档一致**。

## 四、一次上板定位矩阵（按顺序做，每步只改一个变量）

> 目的：用最多 3 次烧录，把"进不去 NSH"从猜变成"看到停在哪一行"。
> 前置：恢复附录 A 的音频配置；串口用 picocom 全程记录；关掉 CONFIG_SYSLOG_BUFFER（缓冲会吞掉最后一行）。

### A 步：排除栈（1 次烧录，零代码改动）

CONFIG_BOARD_INITTHREAD_STACKSIZE: 2048 → 4096。

- 能进 NSH → **根因是栈溢出**（D7），转 §5 的 P0-4，其余不动。
- 仍进不去 → 栈不是根因，继续 B 步。

### B 步：加 stage 标记（1 次烧录）

在 5 个位置用 lowputc()（直写 UART，绕过 syslog 缓冲）打单字符：

| 标记 | 位置 |
|---|---|
| a | esp_bringup() 入口 |
| b | board_es8311_initialize() 入口 |
| c | esp_i2sbus_initialize() 返回后（i2s-before/i2s-after 之间） |
| d | es8311_initialize() 返回后 |
| e | board_es8311_initialize() 返回后 |

判读表：

| 最后看到 | 结论 | 下一步 |
|---|---|---|
| a 之后无 b | 死在 bringup 更早的地方，与音频无关 | 查 GT911/DSI/EFUSE |
| b 之后无 c | 死在 i2s_buf_initialize / i2s_configure / i2s_dma_setup | **D1/D8 坐实**，上 §5 P0-1 |
| c 之后无 d | 死在 ES8311 的 I2C 寄存器初始化 | 查 I2C0 与 GT911 的共享/锁 |
| d 之后无 e | 死在 pcm_decode_initialize/audio_register | 查 audio 上层初始化 |
| 见到 e 且看到 ES8311 ready，但没有 nsh> | 初始化已过，死在 bringup 之后或后续子系统 | 把音频移出 bringup（C 步）验证 |

### C 步：把音频挪出 bringup（1 次烧录）

board_es8311_initialize() 从 esp_bringup() 删除，注册成 NSH 命令 es8311_init。

- NSH 起得来、手动执行 es8311_init 也挂 → 是初始化路径本身（D1/D8），与"何时初始化"无关。
- NSH 起得来、手动执行能过 → 是 bringup 阶段的时序/栈/资源竞争，优先 P0-4（栈 + 移到工作队列）。
- NSH 起不来 → 音频只是把问题提前了，实际根因在 bringup 共通路径（重点查 D8 的 OSINIT_OS_READY() 之前不互斥）。

## 五、修复清单（按落地顺序）

### P0-1 预分配 DMA 描述符，让运行期不再碰堆（治 D1 的根）

i2s_buf_initialize() 一次性把 MAXINFLIGHT × DMADESC_NUM 个描述符分配好，之后 allocate/free 只换链表指针。

~~~c
/* esp_i2s.c：新增 */
static lldesc_t *g_desc_pool[CONFIG_ESPRESSIF_I2S_MAXINFLIGHT][I2S_DMADESC_NUM];

static int i2s_desc_pool_init(struct esp_i2s_s *priv)
{
  int alignment = sizeof(uint32_t);
  size_t size   = ALIGN_UP(sizeof(lldesc_t), alignment);

  for (int c = 0; c < CONFIG_ESPRESSIF_I2S_MAXINFLIGHT; c++)
    {
      for (int i = 0; i < I2S_DMADESC_NUM; i++)
        {
          g_desc_pool[c][i] = kmm_memalign(alignment, size);  /* 只在 init 里分配 */
          if (g_desc_pool[c][i] == NULL)
            {
              return -ENOMEM;
            }

          priv->containers[c].dma_link[i] = g_desc_pool[c][i];
        }
    }

  return OK;
}
~~~

然后 i2s_buf_allocate() 删除 :580-608 的分配循环，i2s_buf_free() 删除 :645-649 的 kmm_free（描述符属于容器，容器常驻）。改完这两个函数里只剩指针操作，临界区恢复到微秒级。

### P0-2 给等待加超时（治 D2）

~~~c
ret = nxsem_tickwait_uninterruptible(&priv->bufsem,
                                     MSEC2TICK(priv->timeout_ms));
if (ret < 0)
  {
    i2serr("buf alloc timeout\n");
    return NULL;                    /* -ETIMEDOUT 上抛 IOERR */
  }
~~~

并在 i2s_send/start 里真正消费 bfcontainer->timeout（当前是死字段）。

### P0-3 兜底：把 kmm_free 移出临界区（若暂不做 P0-1）

i2s_buf_free()：先 spin_unlock_irqrestore()，再循环 kmm_free()，最后挂回链表（挂链表那一步再取一次锁）。不合规但风险可控的过渡补丁。

### P0-4 音频初始化不要占 AppBringUp 的 2048 字节栈（治 D7）

二选一，推荐两个都做：

1. CONFIG_BOARD_INITTHREAD_STACKSIZE=4096（smart_home / smp_smart_home / smp / smart_home_voice 四个 config 都要同步）。
2. board_es8311_initialize() 挪到 work_queue(HPWORK, ...) 或独立线程执行，bringup 只做提交。

### P1-1 拆 audio 上层锁（治 D3，现象 A 的主因）

audio.c:935 的 upper->lock 从"覆盖整个 ioctl"缩到"只保护状态字段"；audio_callback 侧改用引用计数/原子标志，避免回调与 ioctl 抢同一把睡眠锁。

### P1-2 APB 放内部 SRAM（治 D5）

libs/libc/audio/lib_buffer.c:61 的 lib_umemalign() 改为内部堆分配（或把 PSRAM 用户堆从音频路径排除），并在文档里写死"APB 不得落 PSRAM"。

### P1-3 亲和性显式化（治 D4）

worker 与 GDMA 中断绑定同一核（pthread_setaffinity_np + esp_setup_irq 的 cpu 参数），把这个约束写进 docs/架构设计。

## 附录 B：本文未覆盖的部分

- 没有任何板端日志，§3 的 D1/D3 是"代码违规 + SMP 会放大"，不是"已观测到的现场"。
- es8311.c 内部寄存器时序（MCLK 未起时写寄存器是否 NAK）未展开；board_es8311_initialize 里 esp_i2sbus_initialize() 在 es8311_initialize() 之前，MCLK 时序有问题时会表现为 I2C 卡住 → B 步的 c/d 两个标记正好能区分。
- 与 v1.0 的差异：v1.0 列了 6 个候选；本文确认了每个候选的代码位置，新增 D7（栈实测）、D8（HAL 取锁顺序）、D9（单核宏），并把"音频 worker 懒创建"作为排除条件把 B 的候选面收敛到 bringup 内。
