# ESP32-P4X SMP 启动修复日志

记录日期：2026-10-28
修复提交：`4b4bf44e5f41e9702eed2adeae556b33c184611d`（分支 `contest2026`）
关联文档：[ESP32-P4X-SMP启动复位修复方案](ESP32-P4X-SMP启动复位修复方案.md)

## 1. 结论摘要

SMP 配置已在 ESP32-P4 Function EV Board（revision v3.2）上启动到 NSH，串口输出
`[CPU0] ESP32-P4 SMP: CPU1 ready`，`ps` 可见 CPU0/CPU1 两个 IDLE，`smp`、`atomic`、
`ostest` 均通过。

原始故障并非单一原因。关闭看门狗复位后，依次暴露了三个独立的早期启动卡点，加上
CPU1 启核顺序问题，共需四处修复：

| 序号 | 卡点 | 现象 | 修复 |
| --- | --- | --- | --- |
| 1 | ROM flashboot 看门狗 | 入口后反复 `HP_SYS_HP_WDT_RESET` | 入口关闭 TIMG0/LP flashboot 看门狗 |
| 2 | HAL 早期临界区 | `bootloader_init()` 内 REGI2C 访问永久挂起 | 调度器就绪前不取自旋锁，改用 `mhartid` |
| 3 | RTC 校准定时器 | `esp_clk_init()` 内校准死循环（间歇） | 首次校准前显式、幂等初始化 TIMG0 |
| 4 | UART 模块使能 | `esp_lowsetup()` 永久挂起 | `nx_start` 前改用关中断保护 |

另有 CPU1 启核顺序修正，以及构建层面的 HAL 补丁固化。

## 2. 故障现象与初始证据

初始串口日志：

```text
rst:0x7 (HP_SYS_HP_WDT_RESET),boot:0x10f (SPI_FAST_FLASH_BOOT)
load:0x30100000,len:0x44
load:0x4ff40000,len:0x64ac
load:0x4ff46500,len:0x1e40
SHA-256 comparison failed:
Calculated: 004419e4...
Expected:   00000000a05c0000...
Attempting to boot anyway...
entry 0x4ff46178
```

随后无任何应用输出，芯片再次复位，形成复位循环。

已排除的干扰项：

- `SHA-256 comparison failed` 不是根因。镜像由 `esptool elf2image --ram-only-header`
  生成，该选项不追加 SHA256 摘要（镜像头 `hash_appended` 字节为 0），ROM 仍会读取
  尾部 32 字节比较并提示，但明确打印 `Attempting to boot anyway...`，随后正常跳转
  到入口。最终镜像为 334000 字节，SHA256
  `84b362b34e0af8f2c2accf269815a730cde1a1c4bf2788231ba51740c063eb79`。
- `.text`/IROM 未映射不是原始根因，但会影响调试手段。应用 IROM 在
  `map_rom_segments()` 之前不可访问，此时调用链接到 `0x4000xxxx` 的函数会触发
  `Illegal instruction`（实测 `PC 0x40000c88`、`MTVAL 0x0000bad0`，调用的正是
  `riscv_lowputc`）。因此阶段标记必须放在 IRAM 内联代码中。

## 3. 定位方法

在 `__esp_start()` 及被调函数中插入单字符阶段标记，通过 USB Serial/JTAG FIFO 直接
输出（不依赖调度器、日志锁和动态内存），并保证标记函数位于 IRAM。每一轮只增加一组
标记、只改一处，然后重新构建、烧录、抓取串口。

标记序列随修复推进的变化：

```text
012a                       -> 卡在 bootloader_hardware_init 的 REGI2C 写
012a1234                   -> BIOS 偏置写入处挂起
...123456bcdefghijklmno    -> bootloader_init 完成
456789pqr                  -> 卡在 select_rtc_slow_clk
456789p q r ... c 3 s X Y Z W 7 -> 卡在 esp_lowsetup
456789UEABCDN + CPU1 ready -> 启动成功
```

调试标记在定位完成后全部删除，提交中不含任何临时打印。

## 4. 修复内容

### 4.1 关闭 ROM 遗留的 flashboot 看门狗

文件：`chips/esp32p4/common/espressif/esp_start.c`

在 `__esp_start()` 最前面、任何耗时初始化之前，按寄存器级关闭 TIMG0 WDT 与 LP WDT
的 flashboot 模式，并打开 LP SWD 自动喂狗：

```c
REG_WRITE(TIMG_WDTWPROTECT_REG(0), ESP32P4_WDT_WKEY);
REG_CLR_BIT(TIMG_WDTCONFIG0_REG(0), TIMG_WDT_FLASHBOOT_MOD_EN);
REG_CLR_BIT(TIMG_WDTCONFIG0_REG(0), TIMG_WDT_EN);
...
REG_SET_BIT(LP_WDT_SWD_CONFIG_REG, LP_WDT_SWD_AUTO_FEED_EN);
```

必须在 `bootloader_init()` 之前执行。原代码只在启动末尾关闭 RTC WDT，管不到
`HP_SYS` 域的 TIMG 看门狗。

### 4.2 HAL 临界区区分调度器就绪前后

补丁：`patches/0003-esp32p4-early-critical-sections.patch`

`nuttx_enter_critical()`/`nuttx_exit_critical()` 在早期启动阶段被 REGI2C、外设时钟等
路径调用。原实现无条件使用 `this_cpu()` 与 `rspin_lock()`，而每核数据和调度器尚未
初始化，导致 `bootloader_init()` 内第一次 REGI2C 偏置写入就永久挂起。

修复：

- 核号改用 `csrr mhartid` 读取，不再依赖尚未初始化的 per-CPU 数据。
- `OSINIT_OS_READY()` 为假时只保留关中断，不取自旋锁；调度器启动后行为不变，
  跨核互斥仍然有效。

### 4.3 RTC 校准定时器显式初始化

补丁：`patches/0004-esp32p4-smp-hal-strap.patch`

`rtc_clk_cal()` 依赖 TIMG0 总线时钟，而原 HAL 通过 `__attribute__((constructor))`
开启。NuttX flat 镜像不会执行 ELF 构造函数，校准可能返回 0，`select_rtc_slow_clk()`
的 `do { ... } while (cal_val == 0)` 变成死循环（表现为间歇性卡死，取决于 ROM 是否
恰好留下 TIMG0 时钟）。

修复：

- 将构造函数改名为 `rtc_clk_calibration_init()`，保留构造函数属性，同时允许显式调用；
  用静态标志保证幂等，避免重复复位正在使用的定时器。
- `__esp_start()` 在 `esp_clk_init()` 之前显式调用一次。

同一补丁还把 `CONFIG_ESP_SYSTEM_SINGLE_CORE_MODE` 固定为 1（SMP 下同样成立）：
CPU1 由 NuttX 启动，HAL 不应在 CPU1 仍处于 stall 状态时执行双核 cache/MMU/IPI 初始化。

### 4.4 UART 模块使能在无调度器环境下使用关中断

文件：`chips/esp32p4/common/espressif/esp_lowputc.c`

`esp_lowsetup()` 在 `nx_start()` 之前调用 `esp_lowputc_uart_module_enable()`，后者使用
`nxmutex_init()`/`_lock_acquire()`。此时没有当前任务和调度器，互斥量请求无法完成，
启动停在 `esp_lowsetup()`。

修复：以 `OSINIT_OS_READY()` 区分阶段。调度器就绪前只关闭本核中断来保护一次性总线
时钟使能（此时仅 CPU0 运行），就绪后继续使用原互斥量路径。

### 4.5 CPU1 启核顺序

文件：`chips/esp32p4/common/espressif/esp_smp.c`

原顺序为 `unstall -> 使能时钟/复位 -> 写入口地址`，CPU1 可能在入口地址发布前就开始
取指。改为：

```c
ets_set_appcpu_boot_addr((uint32_t)esp_cpu1_start);
UP_DMB();
cpu_utility_ll_enable_clock_and_reset_app_cpu();
cpu_utility_ll_enable_clock_and_reset_app_cpu_int_matrix();
esp_cpu_unstall(cpu);
```

与参考实现（359 队 v3 overlay）一致。

## 5. 构建固化

`build.sh` 在配置变化时会重置 `esp-hal-3rdparty` checkout，直接修改 HAL 源文件不可
复现。因此所有 HAL 修改都固化为项目补丁，放在
`chips/esp32p4/common/espressif/patches/`，由 `Make.defs` 在每次 checkout 后按文件名
顺序自动重放：

| 补丁 | 内容 |
| --- | --- |
| `0003-esp32p4-early-critical-sections.patch` | 早期临界区与 `mhartid` |
| `0004-esp32p4-smp-hal-strap.patch` | 单核 HAL 启动路径、RTC 校准初始化 |
| `0005-nuttx-ipc-serialize-smp.patch` | SMP IPC 串行化与 `nxtask_init` 新签名 |

`0005` 同时修复了干净构建失败：`esp_ipc.c` 仍使用旧的 9 参数 `nxtask_init`，配置变化
触发重编译后报 `too many arguments to function 'nxtask_init'`。此前该文件的对象是
旧构建残留，掩盖了问题。

NuttX 侧的 `patches/nuttx/0010-riscv-allow-custom-smp.patch` 仍需手工应用一次。

构建：

```sh
source myenv/bin/activate
./build.sh contest2026_031_niudanxianqianchong/board/esp32p4/esp32p4-function-ev-board/configs/smp -j4
```

烧录：

```sh
esptool --chip esp32p4 --port /dev/ttyACM0 --baud 921600 --after hard-reset \
  write-flash -fs 16MB -fm dio -ff 80m 0x2000 nuttx/nuttx.bin
```

板端结果（P4 rev3.2，USB Serial/JTAG 控制台）：

```text
ABCD[CPU0] ESP32-P4 SMP: CPU1 ready

NuttShell (NSH)
nsh> mount -t procfs /proc
nsh> ps
  PID GROUP CPU(AFFINITY)   PRI POLICY   TYPE    NPX STATE    EVENT   ... COMMAND
```

- `taskset 3 smp`：CPU0 与 CPU1 均出现，8 个线程全部 `completed with result=0`。
