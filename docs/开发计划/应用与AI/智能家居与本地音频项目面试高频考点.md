## 2. 60 秒项目介绍

### 2.1 智能家居

我做的是一个运行在 openvela/NuttX 上的嵌入式智能家居 Agent demo。架构上将 UI、Agent 编排、领域策略、工具执行和设备状态拆开：用户请求进入 cAGENT 后，模型依据设备上下文和 Markdown Skill 选择受控工具；工具以 JSON 返回结果并更新设备状态，最终结果和事件链回写到 Console 或 LVGL UI。当前设备层是可替换的虚拟状态实现，后续可以在保持工具 schema 不变的前提下接入 Matter、BLE、MQTT、网关 RPC 或真实驱动。项目同时考虑 Goldfish 模拟器与 ESP32-S3-BOX-3 真机的资源、网络和 UI 差异，并为 Node/MCP 远程工具保留动态注册能力。

### 2.2 本地音频事件检测

我做的是一个运行在 NuttX 上的离线音频事件检测应用。音频采集线程从音频设备持续读取 PCM，维护滑动窗口；DSP 将 1 秒、16 kHz、单声道 PCM 转换成与训练端一致的 log-mel 特征；TFLite Micro 使用 INT8 模型推理，后处理通过类别阈值、连续命中和冷却时间抑制误报，最后在本地告警，网络上报则是独立低优先级路径。核心设计目标是把实时采集与网络/UI 解耦，并用“模型契约 + 特征对拍 + 板端性能数据”确保部署结果可信。

## 3. 两个项目的架构图与核心价值

### 3.1 SmartHome：LLM 负责理解，工具负责确定性执行

```text
用户 / 触摸 / NSH
        │
        ▼
Console / LVGL UI ──事件队列──► UI 线程
        │
        ▼
cAGENT：system prompt + 设备 context + Skills + tool schema
        │                    │
        │                    └── 模型：OpenAI-compatible HTTP
        ▼

        │                       │
        ▼                       ▼
Device Manager / State ──── Node Gateway / MCP Bridge
```

关键价值不是“接了一个大模型”，而是把自然语言的不确定性限制在理解和工具选择层：实际控制由结构化 schema、参数校验、风险标志和设备层完成，状态以工具结果和设备回报为准。

### 3.2 audio_event：实时数据面与非实时控制面隔离

```text
I2S / codec / PCM 文件
        │
        ▼
采集线程 ──► 2 秒环形缓冲 ──► 最近 1 秒窗口（每 250 ms 滑动）
                                      │
                                      ▼
49×40×3 log-mel ──► INT8 量化 ──► TFLite Micro
                                      │
                                      ▼
类别阈值 + 连续命中 + 冷却时间 ──► 串口 / OLED / LED / 蜂鸣器
                                      │
                                      └──► 有界队列 ──► 低优先级 HTTP 上报
```

关键价值是：采集不等待网络，告警不依赖云端；输入格式、特征和量化参数受模型契约约束，避免“模型能加载但识别结果错误”的隐蔽问题。

## 4. SmartHome 高频问答

### Q1：为什么要把 Skill、Tool、设备状态分开？

Skill 是给模型的领域行为指导，例如安全边界、场景映射和何时调用工具；Tool 是可执行、可审计的动作；设备状态是业务事实来源。混在一起会导致模型提示词、执行逻辑和状态修改相互耦合，难以测试，也容易让提示词绕过控制规则。项目中 Skill 以 Markdown 从 `/data/res/skills` 加载，工具使用稳定名称和 JSON Schema，设备层则可以从虚拟状态替换成真实协议适配层。

追问可补充：工具注册表只做浅拷贝，因此工具的名称、schema 字符串和 `user_data` 必须在工具生命周期内有效；这是嵌入式 C 里容易被忽略的所有权问题。

### Q2：LLM 幻觉或生成危险参数时，如何保证设备安全？

不能相信模型输出。控制链路至少要有四层：

- 工具 schema 限制参数类型、枚举和范围；
- 工具根据 `READ_ONLY`、`SIDE_EFFECT` 等属性进入通用 guard/policy；
- 设备层再次校验设备在线、参数边界和业务安全策略；
- 高风险操作（如解锁、撤防）由原生服务二次确认，最终状态以设备回报为准。

类别或 UI 页面只用于展示，不能替代安全属性。对于本地确定性命令，例如“开灯”，也可以绕过 LLM，直接复用本地工具实现，以获得零 token、低延迟、可复现的行为。

### Q3：为什么需要 context provider，而不把状态全做成一个工具？

当前设备状态是每轮推理都需要的环境信息，作为 context provider 自动注入，可避免模型忘记先调用查询工具，也不占用工具槽位。操作型或按需详细信息才适合作为工具。两者结合能降低无效 tool call，并让状态读取与状态修改在语义上分离。

### Q4：ReAct 工具调用的完整链路是什么？

`agent_run()` 构建系统提示、设备 context、Skill 和可见工具 schema；模型返回文本或 `tool_calls`；框架解析调用，执行 tool guard/policy；工具生成 JSON 结果写回会话；模型再根据结果继续调用工具或生成最终回答。这样最终回答不是直接“猜”出来的，而是能够基于工具结果解释。

应诚实说明边界：框架的工具超时主要是执行后的测量，无法强行停止一个已经阻塞的 C 回调。因此 Node/MCP 等远程工具必须在自身实现连接和请求 deadline，不能把阻塞网络操作直接塞进工具回调。

### Q5：为什么 Agent 与远程工具注册要加锁？

Agent 运行时会访问工具注册表，而 Node/MCP 的发现、断连可能同时触发远程工具注册或注销。如果并发修改 registry，会出现悬空指针、迭代器失效或工具调用到已断开连接。项目用 `agent_mutex` 串行保护 `agent_run()` 与远程工具 mutation；动态目录由 worker 处理，不在网络回调线程直接修改 Agent。

### Q6：为什么 LVGL 不能从 Agent/网络线程直接更新？

LVGL 对象和渲染循环应由 UI 线程拥有。Agent worker 或网络线程直接碰控件会带来竞争、use-after-free 和偶发崩溃。正确做法是复制事件或状态，投递异步队列，再由 LVGL 线程使用 `lv_async_call` 或等价机制更新控件。这个原则同样适用于音频检测的 UI/OLED 状态更新。

### Q7：SmartHome 如何支持多个 LLM 后端而不把密钥写进固件？

模型层走 OpenAI-compatible 抽象，配置 host/path/port/model 等；API key 运行时从 `/data/smart_home/secrets.json` 读取，而不是硬编码或提交到仓库。UI 可以选择后端 preset，但 key 不应出现在日志和 UI 回显中。对 TLS 失败、网络不可达和鉴权失败应输出可区分的错误，便于排障。

### Q8：Node Gateway / MCP 的差异与共性？

二者的共同目标是把远程设备能力映射成受控工具，并处理发现、调用、断连和生命周期。Node Gateway 面向 WebSocket 和 OpenClaw-compatible Node，MCP Bridge 面向标准 MCP 的 `initialize`、`tools/list`、`tools/call` 及 HTTP/TLS。二者都不应该让远程元数据直接绕过本地策略：远程工具仍需要 schema、风险属性、来源标识、超时和断连处理。

### Q9：远程工具断线重连时，怎样避免旧断连事件误删新工具？

不能只以工具名或 node ID 判断。远程 descriptor 中应保留 `route_id`、来源和 `connection_gen`；调用时按路由和连接代次定位 peer。断线先进入 draining/unregister，旧连接的迟到事件如果 generation 不匹配，就不能删掉新连接同名工具。这是典型的异步生命周期竞态。

### Q10：为何虚拟设备层仍有工程价值？

它让 Agent、UI、工具 schema、场景、错误处理和回归测试可在没有真实家庭设备时闭环。替换真实设备时将改动收敛在 device/gateway adapter，不必重写提示词或页面。前提是虚拟状态不能被误宣传为真实协议已联调；面试时要主动区分 demo 能力与实板能力。

### Q11：双平台适配最容易踩哪些坑？

Goldfish 使用以太网和 ADB 推送资源，ESP32-S3-BOX-3 使用 Wi-Fi、LittleFS、LCD/触摸与更紧的内存；二者虽统一资源路径为 `/data/res/`，但资源部署方式、屏幕分辨率、TLS 熵源和内存预算不同。项目根据分辨率区分紧凑/标准布局，并把 UI、资源和网络初始化拆开，避免“模拟器跑通就认为真机可用”。

### Q12：QuickApp 为什么不应直接访问 GPIO、摄像头原始帧或 PCM？

JS UI 适合页面、主题、路由与展示状态；硬件、密钥、AI 推理和实时数据面应留在原生服务。暴露底层驱动会破坏权限边界、难以做版本兼容，也会让高频大数据跨语言复制，造成抖动和内存压力。快应用只消费版本化的快照、命令和语义事件；原生服务是设备状态单一事实来源。

## 5. 本地音频与端侧 AI 高频问答

### Q13：为什么选择 16 kHz、16-bit、单声道和 1 秒窗口？

这是当前模型的部署契约：输入为 16000 个 PCM 采样点，采样率 16 kHz、单声道、16-bit。音频格式不能因为“听起来也正常”而任意改变；采样率、声道、位宽、前端参数或类别顺序不一致，都会导致特征分布漂移并显著影响识别率。1 秒窗口覆盖敲击、咳嗽等短时事件的上下文，窗口每 250 ms 滑动，因此既保留上下文又降低检测等待时间。

### Q14：从 PCM 到模型输入的完整前处理是什么？

当前实现将 1 秒 PCM 按 30 ms 窗、20 ms 步长分帧，形成 49 帧；每帧做 Hann 窗、512 点 FFT、40 路 Mel 滤波、对数与归一化，再计算一阶和二阶时序差分，最终得到 `49×40×3=5880` 个浮点特征。推理前依据 input scale 和 zero point 量化为 INT8。模型输入元素数、量化参数、类别布局都要在初始化阶段检查，不能只假设模型文件正确。

### Q15：log-mel、MFCC 与 delta 特征有什么区别，为什么不能混用？

log-mel 是 Mel 频带能量的对数表示；MFCC 还会对 log-mel 进行 DCT，压缩谱包络；delta/delta-delta 描述特征随时间的一阶、二阶变化。它们各自都合理，但必须与训练时输入完全一致。当前模型期望的是 49×40×3 的 log-mel 加两阶差分，不能把旧的“13 维 MFCC 逐帧分类”结果直接送进模型。

### Q16：INT8 量化如何做？为什么能减少资源占用？

量化把浮点特征映射到 `[-128, 127]`：

```text
q = clamp(round(real / scale) + zero_point, -128, 127)
real = (q - zero_point) × scale
```

INT8 降低模型存储和张量带宽，也通常能利用 MCU 的整数优化算子；代价是量化误差。因此必须使用模型自己的 scale/zero point，而不是手写一个“乘 127”的通用公式，并在 Python/TFLite/固件三端对同一测试向量做类别和数值验证。

### Q17：TFLite Micro 初始化重点有哪些？

用 `GetModel()` 读取 FlatBuffer 后校验 schema；使用静态、对齐的 tensor arena 创建 `MicroInterpreter`；只注册当前模型需要的算子，然后 `AllocateTensors()`；检查输入输出张量的数据类型、维度、类别数量和量化参数。项目采用 `MicroMutableOpResolver`，而非 `AllOpsResolver`，因为后者会无谓扩大镜像、RAM 和攻击/维护面。

当前 4 类模型涉及 Shape、StridedSlice、Pack、Reshape、Conv2D、DepthwiseConv2D、Mean、FullyConnected、Softmax 等算子；算子列表变化必须随模型一起复核。

### Q18：tensor arena 应放内部 SRAM 还是 PSRAM？

内部 SRAM 延迟低，更适合实时推理和优化算子的 scratch；PSRAM 容量大，可给大模型或大音频工作区腾空间，但带来缓存与带宽代价。项目的 8 类配置允许将大工作区或 arena 放到 PSRAM，并检查返回地址确实属于 PSRAM；这不是“申请成功”就够了。选择依据应是实测 P50/P95 推理时延、掉帧、Wi-Fi 并发和剩余内部内存，而不是只看理论容量。

### Q19：NuttX 音频采集怎样避免阻塞或丢数据？

应用通过 NuttX Audio API 打开设备、reserve session、配置 PCM，并申请/入队多个 `ap_buffer_s`。驱动通过消息队列回收 `AUDIO_MSG_DEQUEUE` 缓冲，应用读取后立即重新入队；采集线程将数据写进环形缓冲。需要处理 `EINTR`、短读、`AUDIO_MSG_COMPLETE/STOP`、设备断开和初始化失败。采集与推理分开，才能防止特征计算或网络上报卡住 DMA 数据路径。

### Q20：INMP441 为什么需要 32-bit 转 PCM16？

部分数字麦克风以双声道 32-bit I2S slot 输出，有效音频位于某一个 slot 的高位。项目可配置 slot 和右移位数，将有效的 `int32` 样本算术右移、饱和裁剪成模型需要的 mono `int16`。若 slot、移位、字节序或声道配置错了，表面上设备仍能读到数据，实际却会得到极低音量、噪声或错误声道，因此要保存 PCM 回放并检查 min/max/RMS，而非只看 open 成功。

### Q21：为什么仅用 argmax 触发告警不够？

argmax 只说明“当前窗口中哪个类别最大”，不代表它足够可信。项目对事件类设置独立阈值，要求连续命中后才触发，并进入冷却期；背景和静音属于拒识类别。8 类模型中的关键词则采用独立阈值与更快的触发策略。阈值、连续次数和冷却时长要按类别及现场数据调优，不能用单一经验值覆盖所有声音。

### Q22：能量门控如何降低功耗？会不会漏检？

能量门控仍保持采集运行，启动阶段估计噪声底，使用 RMS/峰值阈值判断是否跳过后续 DSP/TFLM；静音时还会按周期强制 probe，避免长期不推理。它能减少安静环境下的计算，但可能漏掉低能量目标或因环境噪声变化失效。因此连续推理是 P0 精度基线，门控是 P1 优化；启用前后必须比较召回率、误报率、平均推理次数和功耗。

### Q23：如何定位“识别率低/误报高/爆音/静音段”？

先按数据链路拆分，而不是直接换模型：

| 现象 | 首先检查 | 常见根因 |
| --- | --- | --- |
| 识别率低 | 保存 PCM、核对采样率和前端对拍 | 增益、声道、前端参数与训练不一致 |
| 误报高 | 分类别统计置信度、背景样本和连续命中 | 阈值过低、环境噪声、拒识样本不足 |
| 静音段 | 零值比例、buffer 长度和重采样逻辑 | 未初始化、短读处理错误、帧大小计算错误 |
| 爆音/咔哒声 | 相邻样本跳变、DMA/缓冲切换 | 时钟不同步、并发覆盖、buffer 重入队异常 |
| 削波 | `±32767` 占比、增益与格式转换 | 模拟/数字增益过大、混音或移位溢出 |

离线 PCM 检查可量化削波、静音、突变、底噪和周期性失真；但必须提供正确的采样率、位宽和声道数，否则分析结论没有意义。

### Q24：如何验证模型与固件前端真的一致？

验证顺序应当从确定性到真实世界：黄金 INT8 特征能否 `Invoke` → 固定 PCM/WAV 的 Python 与 C log-mel 逐元素对拍 → 连续文件流验证滑窗和后处理 → Sim ALSA → 真机麦克风。每层记录模型版本、输入格式、特征误差、类别结果、arena 峰值、特征/推理/端到端耗时。这样发生问题时能知道是模型、前端、采集还是板级硬件，而不是只得到“真机不准”。

## 6. P4X SmartHome 与本地音频的结合问题

### Q25：KWS 与 ASR 的边界是什么？

KWS 用于常驻、离线、低延迟地识别有限的唤醒词或命令词；ASR 用于开放词表自由语句。合理分流是：唤醒词只改变本地状态机；确定性命令词直接映射本地工具；需要理解的自由语句才提交给云端 ASR/LLM。这样能减少 token、降低延迟，同时避免让小型 KWS 模型承担开放式语言理解。

### Q26：为什么 P4X 不能直接照搬 ESP32-S3 的音频/KWS配置？

板级麦克风类型、I2S/PDM 实例、引脚、时钟、codec 和 DMA 配置都可能不同；P4 也不能默认拥有 S3 的 ESP-NN 优化路径。迁移前先确认原理图/BSP，完成 I2C codec 响应、I2S 时钟与设备节点、固定格式录放音，再对拍特征并实测单帧推理 P95。通用 `pcm_in0` 节点只能证明一段 I2S 总线路径，不等于板载 codec、麦克风和实际音质已验收。

### Q27：语音事件与 SmartHome Agent 并发时如何处理？

当前 Agent run service 为单槽：已有排队请求或正在运行时会返回 `AGENT_ERROR_BUSY`。语音调用方必须明确提示“当前正在处理”，不能静默丢弃；如果产品需要语音与文本会话隔离，还要把 `session_id` 贯穿到实际 `agent_run`。KWS 线程不应直接抢占 UI 或修改工具注册表，而是产生受控事件，由应用服务统一调度。

## 7. 常被追问的工程能力

### 内存与性能

- 如何量化：分别记录模型大小、镜像增量、内部 SRAM/PSRAM 占用、arena 已用量、stack 高水位、特征耗时、推理耗时、端到端 P50/P95/P99。
- 如何优化：先 profile 定位；优先减少不必要的复制和大对象、精确注册算子、调整 arena 放置、降低 UI/网络对实时线程的干扰；不能未测先压缩模型。
- 如何防止内存碎片：长期存在的大块 arena/workspace 采用静态或一次性对齐分配；音频路径复用 buffer，不在每帧 malloc/free；生命周期清晰地释放可动态分配资源。

### 并发与可靠性

- 生产者/消费者：采集线程只做短路径写环形缓冲；推理读完整快照；网络上报进入有界队列，满时定义丢弃策略并计数。
- 线程优先级：采集优先于推理、UI 和网络；优先级不是万能解，仍需减少临界区和阻塞 I/O。
- 异常恢复：设备短读可重试；连续音频设备错误触发重新初始化；模型契约或 arena 分配失败则失败退出并打印明确原因；网络失败不应影响本地检测与告警。

### 测试与指标

- 功能：固定音频、背景、静音、连续事件、设备断连、网络故障、UI 重启。
- 算法：每类 Precision、Recall、F1、混淆矩阵、误报率/漏报率；明确数据集与现场环境。
- 实时性：窗口 hop、特征耗时、推理耗时、端到端时延、长时间丢帧率。
- 安全：非法 tool 参数、重复 `requestId`、断线重连、密钥不入日志、危险控制二次确认。

## 8. 鹿客岗位定制：C、RTOS、硬件与项目难点追问

本节的题目比通用八股更接近“智能门锁/网关团队会根据项目继续深挖什么”。每题先说
结论，再给出你做过的机制、验证方式和边界；不确定的寄存器位、芯片引脚或数字不要猜。

### Q28：你的 ESP32-C3 传感器任务为什么把定时器和 GPIO 中断都收敛到一个 task？

I2C 是共享、时序敏感的总线。若定时器回调、按键中断后的任务和其他业务任务各自直接
读写传感器，容易出现总线事务交叠、设备状态机错乱和难复现的偶发 NACK。我把 ISR 或
定时器回调只做“通知”，由一个 sensor task 串行完成 I2C 访问、采样、去抖和状态更新。
ISR 中不做 I2C、动态内存或长日志；跨 task 的共享状态用队列/通知或短临界区传递。这样
总线所有权明确，也便于统计采样延迟、失败次数和重试结果。

追问“为什么不用 mutex”：mutex 可以保护总线，但不能天然保证事件处理顺序；对于该
传感器流程，单消费者串行状态机更容易表达“中断、定时采样、状态变化”的顺序。若多个
独立模块确实要共用 I2C，再在驱动/总线层增加 mutex，并规定锁粒度和超时。

### Q29：GPIO 中断服务程序里能做什么，不能做什么？

ISR 只做确定、短时、不可阻塞的工作，例如读取/清除中断源、记录时间戳、使用
`xQueueSendFromISR` 或 task notification 唤醒任务，并在需要时触发 yield。不能在 ISR
里做 I2C/SPI 事务、等待 mutex、网络上报、`printf`、复杂计算或 `malloc`，因为会拉长
中断关闭时间、破坏实时性，甚至触发不可重入问题。按键抖动也不应在 ISR 中 `delay`；应把
时间戳交给 task 进行软件去抖。

### Q30：C 语言中如何防止驱动或 RTOS 项目的内存、指针和资源泄漏？

我会先做资源所有权表：谁创建 task、queue、semaphore、socket、I2C 设备句柄和动态 buffer，
谁在什么失败路径释放。初始化按依赖顺序，失败使用单一 `goto cleanup` 反向释放；停止时先
置 `stopping`，唤醒可能阻塞的 worker，再 `join`，最后销毁同步对象和内存。跨线程传递的
对象要定义“发送后谁拥有、消费者何时释放”，不能传递指向栈上临时变量的指针。

结合 SmartHome 的实证：早期 Bridge worker 在 4 KiB 栈调用链中放了约 6 KiB 请求、4 KiB
响应及 WebSocket 帧等局部对象，有明确栈溢出风险。修复不是盲目加大栈，而是将大 buffer
改为按连接短时堆分配；分配失败返回 `503 resource_unavailable`，请求结束显式释放。

### Q31：volatile 能解决多线程同步吗？环形缓冲如何设计？

不能。`volatile` 只约束编译器对该对象的读写优化，不提供原子性、互斥、顺序保证或缓存一致性。
单生产者/单消费者 PCM ring 可用单调读写索引，配合原子/临界区和明确的 overflow 策略；多生产者
或多消费者应使用锁、队列或拆分成单生产者路径。音频项目中采集路径持续写 ring，推理只复制最近
完整的一秒窗口；必须避免读到正在写的样本，并统计短读、覆盖和丢帧，而不是静默用不完整窗口推理。

### Q32：怎样解释 UART、I2C、SPI 在智能门锁/网关中的选型？

UART 简单、全双工，适合模组 AT 命令、调试串口或低速协处理器；I2C 用两根线挂多从设备，适合
传感器、RTC、codec 控制等低速寄存器访问，但要处理地址、上拉、电容和总线恢复；SPI 全双工、
吞吐高、片选明确，适合屏幕、Flash、高速 ADC 或无线芯片数据面，但设备增多会消耗片选和布线资源。
实际选型还要看实时性、DMA、供电域、EMI、软件成熟度和故障恢复，不能只用“哪个更快”。

可以结合你的项目补充：音频控制面经 I2C 配置 codec，数据面通过 I2S/DMA 连续搬运 PCM；两者的
失败模式和实时性要求完全不同。I2S 节点能注册不代表 codec 初始化、时钟匹配和实际录音质量均已验证。

### Q33：你如何排查 SmartHome 中的 TLS EOF/超时？最终结论是什么？

我没有把一次 TLS EOF 直接归咎为“内存不足”。日志表明 DNS 和 TCP 已成功，问题发生在 TLS
握手阶段；我做了 Bridge 开关、仅监听 socket、worker 不 accept、4 KiB/8 KiB worker 等 A/B，
并在 worker 创建、请求/响应 buffer 分配、TLS setup/handshake 前后记录 `mallinfo()`。结果确认了
旧 Bridge 大栈帧是必须修复的栈风险，也验证了重构后 Bridge 与一次 DeepSeek TLS 200 请求可共存；
但 A/B 尚不足以证明历史 TLS EOF 由 Bridge 栈或全局堆引起，WAN/CDN、Wi-Fi/TCP 接收路径仍需继续
用稳定局域网 TLS 服务和重复压力测试排除。

这道题的得分点是“用对照实验缩小范围、修复已证实风险、不给未证实问题下结论”。

### Q34：ESP-NN 移植时，为什么不能把所有 INT8 Conv 都替换为优化实现？

INT8 只是必要条件，不是充分条件。ESP-NN 内核还依赖卷积形状、通道数、stride/padding、dilation、
depth multiplier、filter 对齐等约束。项目初版全量委派后，真机出现 `EXCCAUSE=0023`、空地址访问；
回退一个分支后崩溃会转移到另一个 Conv/DW 分支，说明问题是“未经资格判断的全量委派”，不是单一算子。

最终采用薄 wrapper + `out_tensor` 逐算子白名单：每个节点先走 reference/ESP-NN 逐字节 VERIFY，
通过后再关闭 VERIFY 测性能；不满足条件的节点自动回退 reference。一个 `1×1` Conv 虽然形状合格，
仍发现 filter 地址未按 8 字节对齐，因此在 `Prepare()` 只为该节点复制 384 B 到对齐 persistent buffer，
不修改上游 ESP-NN 源码。

### Q35：为什么 VERIFY 固件接近 reference 耗时，不能据此说优化失败？

VERIFY 同时执行 reference、ESP-NN、逐字节比对和 trace，验证成本会抵消加速收益；它回答的是
“结果是否一致”，不是“性能有多快”。项目把流程固定为 `reference → verify → cycles`：先建立
reference 基线，再验证每个白名单节点/输出 hash，最后在关闭 TRACE/VERIFY 的正式 profile 上用
`--warmup 20 --repeat 100` 测 `MicroInterpreter::Invoke()` 的 min/P50/mean/P95/max 和 cycles。

对 8 类 S3-large 模型，在相同 ESP32-S3、240 MHz、固定 INT8 输入下，reference mean 是
2954.965 ms，ESP-NN mean 是 47.282 ms，`output hash` 相同，对应 62.4965×。这个数字只说明模型
阶段；端到端仍要加上约束条件下的特征、采集、检测、UI/网络耗时。

### Q36：音频项目中性能优化后，下一瓶颈是什么？如何继续做？

当 ESP-NN 将卷积/Mean 的模型阶段降下来后，float log-mel 前端约 60–70 ms，成为主要单项开销。
不能继续只优化模型或用“模型 47 ms”代替端到端结论。下一步应 profile FFT、Mel filterbank、`logf`、
内存访问和量化，优先消除重复计算与复制；任何近似、定点化或 SIMD 优化都要与 Python/reference
前端逐值对拍，再比较识别指标、P95 延迟与功耗。算法优化和模型正确性必须同步验收。

### Q37：日志显示 cough 误报和 knock 漏检，你先改阈值吗？

不应只抬高阈值。当前基线中一些非目标声音仍给出很高的 cough 概率，说明训练数据/类别边界存在
问题；同时共享冷却时间会让一次错误的 cough 告警压制后续真实 knock，严格连续两窗也可能伤害短时
敲击。我的处理顺序是：核对 PCM、特征和模型版本；按类别统计 TP/FP/FN、混淆和置信度；补充
`stop`、dog bark、yes/no、glass breaking 等 hard negative；再把 knock/cough 拆成独立候选与冷却，
评估 margin、EMA 或 2-of-3 窗策略。每次改动都登记为新 profile，避免把不同门控、阈值或数据集的
结果混在一起比较。

### Q38：在嵌入式研发中，你会怎样使用 AI Agent，又怎样验证它可靠？

我把 AI 当作“加速假设生成和文档整理”的工具，而不是代码和硬件事实的裁判。它可以帮助我把需求
拆成驱动、任务、接口和测试项；根据编译/串口日志列出可能根因；生成边界用例、寄存器检查清单和
代码审查关注点。随后我会回到芯片手册、现有驱动、编译器诊断、单测和实板日志逐项验证。对于生成
的 C 代码，要审查 ISR 上下文、栈与堆、错误码、并发、资源释放、对齐和 Kconfig 依赖；对于 Agent
工具调用，要让 schema、policy、权限和设备回报成为执行闸门。

这个回答直接对应岗位“AI 辅助设计/编码/调试，但验证输出可靠性”的要求，也能用 ESP-NN 排障中
“假设 → ELF 反查 → 回退 → VERIFY → benchmark”的实际闭环作证。

## 9. 面试中可直接使用的 STAR 示例

### 示例 1：解决嵌入式 Agent 的并发风险

“我发现 Agent 执行和 Node/MCP 的远程工具发现可能同时访问工具注册表。若网络回调直接注册或注销工具，模型执行期间可能引用无效 descriptor。于是我将动态目录变更转交 mutation worker，并用同一把互斥锁串行保护 `agent_run` 与 registry 变更；远程连接还用 generation 区分新旧会话。验证时重点覆盖断线重连、旧 disconnect 迟到、执行中工具变化三类场景。结果是把偶发的生命周期竞态收敛为可控状态转换。”

### 示例 2：定位端侧音频识别不准

“我不会先调阈值或换模型。我先保存原始 PCM，确认采样率、通道、位宽、RMS 和削波；再用同一 WAV 将 Python 和固件的 log-mel 逐元素对拍；特征一致后才检查 INT8 scale/zero point、类别顺序和后处理。这个顺序能把硬件采集、DSP、量化、模型和策略分层定位，避免用阈值掩盖前端不一致。”

### 示例 3：在资源受限设备上处理大模型工作区

“8 类音频模型的 tensor arena 与音频工作区会挤占内部 DRAM，而 Wi-Fi 也依赖内部内存。我将大块缓冲的放置做成可配置策略：默认评估内部 SRAM 的时延，必要时迁移到 PSRAM，并验证返回地址真实落在 PSRAM。最终用 P95 推理时延、网络并发稳定性和内存余量做取舍，而不是只根据‘PSRAM 更大’做决定。”

| 音频特征 | 30 ms 窗、20 ms 步长、49 帧、40 Mel bins、log-mel + 一阶/二阶差分，共 5880 个特征 |
| 4 类模型 | `knock`、`cough`、`background`、`silence`；后两类是拒识，不告警 |
| 后处理 | 类别阈值 + 连续命中 + 冷却；不要只用 argmax |
| P4X KWS | 复用方向明确，但麦克风通路、P4 性能和唤醒词模型都须实测验收 |

## 11. 建议反问面试官

1. 团队的端侧模型部署是否已有训练—量化—固件特征对拍的统一流水线？
2. 对实时任务，团队使用哪些指标定义音频丢帧、推理 P95 和长稳可靠性？
3. Agent 调用设备工具时，权限、幂等、审计和故障回滚由哪一层统一负责？
4. 设备状态是事件驱动、轮询，还是两者结合？断线重连和状态版本如何处理？

这些问题能体现你关注的不是单点功能，而是端侧 AI 与智能设备在真实产品中的可验证性、可靠性和安全边界。
