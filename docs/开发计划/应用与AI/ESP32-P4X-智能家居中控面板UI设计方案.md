## 1. 设计目标

本项目面向智能家居中控场景，基于 ESP32-P4X 与 OpenVela 构建一套横屏智能
家居控制面板 UI，体现简洁、自然、高级、弱打扰、以家庭空间为中心的理念，
同时结合端侧 AI、设备控制、场景联动与 Agent 能力，形成自身特色。

UI 不仅承担传统设备控制，也作为家庭状态展示、场景入口、语音交互、AI 感知
与智能服务的统一入口。

核心目标：

- 提供直观、统一的全屋设备控制入口；
- 以房间和场景为核心组织设备信息；
- 降低复杂设备参数对普通用户的干扰；
- 支持灯光、空调、窗帘、安防等常见设备快速控制；
- 支持设备二级页面进行精细参数设置；
- 支持语音助手与智能 Agent 交互；
- 建立“空间总览 → 系统控制 → 单设备精调”的三层路径，让常用控制少跳转；
- 通过收纳式状态卡片和固定快控条，在不堆满设备的前提下保持一眼可控；
- 兼顾 ESP32-P4X 的性能与内存限制；
- 适配横屏触控与固定墙面中控场景。

## 2. 产品定位

定位为 OpenVela AI Smart Home Panel，即集成以下能力的一体化家庭智能终端：

    触摸交互 + 家庭设备控制 + 场景控制 + 语音交互
    + 端侧 AI 感知 + Agent 智能服务 + 家庭网关能力

与传统面板相比，本方案不只是设备遥控器，而是家庭环境中的智能交互节点：

    用户
     ├ 触摸
     ├ 语音
     └ 无感感知
          ↓
      智能中控面板
          ↓
      ┌───┼───┐
     UI  Agent  Event
      └───┼───┘
          ↓
    设备 / 场景 / AI / Home Assistant

## 3. 整体视觉风格

### 3.1 设计关键词

自然、温暖、简洁、沉浸、克制、智能。

避免传统工业控制面板的大量边框、高饱和颜色、密集按钮、复杂表格与过多数字
参数，改用：

    大卡片 + 大留白 + 弱边界 + 图片场景 + 轻量动画 + 少量高亮色

形成更接近消费电子产品的视觉体验。

### 3.2 参考交互原则

参考高端中控屏的空间化交互，但以本项目的设备、Agent 和端侧 AI 能力为中心：

- **空间优先**：首页先回答“我在哪个家庭/房间”，再展示该空间的高频场景与状态；
- **分层收纳**：首屏只露出重要状态与高频设备，完整设备清单下沉到设备页；
- **快控常驻**：灯光、空调、窗帘等高频操作保留一条固定快控区，避免反复进入详情；
- **渐进精调**：点按执行常用动作，长按或进入详情页再显示亮度、色温、风速等参数；
- **状态优先于装饰**：颜色、动效和阴影用于传达开关、告警、执行中与离线状态；
- **可打断**：安防告警、Agent 风险确认和系统故障可提升优先级，但普通建议不阻塞操作。

### 3.3 色彩体系

推荐以深色主题作为默认主题。

背景色采用深灰或暖黑，而不是纯黑，页面间通过亮度差区分层级：

    #161819   页面背景
    #1D1F20   次级背景
    #222425   分组背景

卡片颜色：

    主卡片    #252829
    次级卡片  #2C2F30
    浮层      rgba(255,255,255,0.08)

卡片尽量避免明显描边，以阴影、透明度与亮度区分。

强调色按设备类型使用低饱和功能色，颜色用于表达状态而非装饰：

    灯光   暖黄
    空调   淡蓝
    安防   绿
    报警   红
    Agent  蓝紫渐变

### 3.4 质感与性能边界

可用半透明卡片、柔和阴影、渐变和预制模糊背景塑造玻璃感，但不使用实时全屏模糊、
大面积 alpha 叠加或全屏粒子效果。主题壁纸限量内置并按需加载；不得复用参考产品的
壁纸或图标资产。

目标是复杂交互页稳定 **30 FPS**，而不是全局 60 FPS。设计时优先保证触摸反馈、
设备状态变化和页面可读性；动画仅作用于小区域且可在资源紧张时降级或关闭。

### 3.5 统一视觉令牌（`light-calm`）

网页 Demo、QuickApp 和 LVGL 模式采用同一组语义令牌，而不是在各页面复制具体颜色。
首期主主题为柔和浅色；深色仅作为后续完整夜间主题，不能与浅色页面混用。

| 类别 | 令牌/规则 | 首期取值 |
| --- | --- | --- |
| 页面与容器 | `canvas` / `surface` / `card` | 暖灰白 / 暖白 / 纯白 |
| 文字 | `text` / `subtext` | 深灰绿 / 中灰绿 |
| 边界与层级 | `line` / `shadow` | 轻边框 + 单层弱阴影，不使用玻璃拟态或实时模糊 |
| 圆角 | `radius-card` / `radius-control` | 17px / 11px |
| 功能卡背景 | `weather` / `comfort` / `safe` / `service` | 雾蓝 / 暖杏 / 鼠尾草绿 / 淡紫，均为低饱和色 |
| 状态 | `active` / `danger` | 柔和绿表示开启和安全；红色只用于风险与失败 |
| 一级导航 | 固定 64px，选中胶囊底色 | 图标 20~22px、标签 11px、有效触控区不小于 68×56px |

允许天气、空调、安防和 Agent 卡按语义使用不同低饱和背景，但卡片圆角、文字层级、
图标规格、按钮、阴影与反馈动效必须相同。摄像头实时预览可以显示深色画面，然而预览
外围的页面和控制组件仍遵守 `light-calm`。

一级页面标题只保留“设备”“场景”“安防”“更多”“系统设置”等明确名词；不重复展示
“家庭守护中”“按空间查看”等营销或说明性眉题。空间筛选、布防状态等信息应由房间
筛选条、状态标签和卡片本身表达，减少首屏文字噪声。

## 4. 页面信息架构

    第一层：全屋 / 当前空间总览（首页）
    第二层：照明、冷暖新风、遮阳、影音、环境、安防等系统控制（设备）
    第三层：单个设备的精细控制（设备详情）

场景与安防为一级快捷入口；能耗、Agent、设置和服务能力收纳在“更多”中，必要时可由
首页状态卡或主动事件直接进入。底部导航固定提供不超过 5 个入口：

    首页 | 设备 | 场景 | 安防 | 更多

底部导航高度固定为 64px，单个入口的有效触控区域不小于 68×56px；图标使用 20~22px，
标签使用 11px。当前项采用低饱和圆角底色与文字/图标变色共同表达，不只依赖颜色；
设备开关、温度等具体操作不放入底栏。

## 5. 首页设计

首页是最重要的页面。设计原则不是展示全部设备，而是：

> 展示当前家庭最重要的信息和最常用操作。

首页采用“左侧固定环境大卡 + 右侧两行异构功能卡”的卡片画布布局。以下仅参考提供图片的
信息密度、卡片比例和排列关系；不使用其品牌、图标、图片、文案或编辑控件。

    ┌─────────────────────────────────────────────────────────┐
    │ 我的家                    麦克风 / 摄像头 / 勿扰 / 网络 / 时间 │
    ├──────────────┬──────────┬────────────────┬──────────────┤
    │              │ 场景卡   │ 空调伴侣       │ 摄像头缩略卡 │
    │ 天气环境大卡 ├──────────┼────────────────┼──────────────┤
    │ 时间/天气    │ Agent 卡 │ 音乐播放卡     │ 家庭状态卡   │
    │ 湿度/位置    │          │                │              │
    ├──────────────┴──────────┴────────────────┴──────────────┤
    │ 首页                 设备              场景    安防  更多 │
    └─────────────────────────────────────────────────────────┘

在 1024×600 设计画布中，顶部栏和底部导航固定；主体区左右留白 28 px，卡片间距 10 px。
首页顶部不设置“全屋 / 客厅 / 主卧 / 厨房”房间 Tab，以避免首屏与卡片信息竞争；房间信息
直接显示在对应设备或场景卡内，空间筛选仅保留在设备页。右上角依次呈现麦克风可用、
摄像头可用、勿扰模式、家庭网络连接与当前时间等只读系统状态。其中麦克风、摄像头图标
只说明能力/隐私状态，不表示正在录音或正在预览。
天气环境卡跨两行，右侧第一/第二行各放置一组卡片。首期卡片顺序固定，不提供首页删除、
添加或拖动重排模式；用户个性化属于后续独立需求，不能与首页主流程耦合。

### 5.1 时间与天气

左侧天气环境大卡显示时间（大字号）、日期与天气：

    10:28
    9月24日 星期三
    26°C 多云

天气只显示温度、天气状态与简单图标，并可收纳湿度、空气质量和城市；不在首页展示
气压、风速等非必要信息。该卡是环境入口，点击后进入环境/设备页，不承担设置或编辑功能。

### 5.2 右侧卡片职责

右侧六个格位按“高频控制优先、摘要次之、低频服务下沉”分配，单卡只服务一个明确任务：

| 格位 | 默认卡片 | 主要内容与操作 |
| --- | --- | --- |
| 第一行左 | 场景卡 | 回家、观影等一个高频场景；点按执行，完整场景列表进入场景页。 |
| 第一行中 | 空调伴侣 | 房间、运行状态、设定温度、开关和 `− / +`；精细模式进入设备详情。 |
| 第一行右 | 摄像头缩略卡 | 最近缩略图、在线状态和进入安防页入口；首页不启动连续视频预览。 |
| 第二行左 | Agent 卡 | 问候、家庭摘要和对话入口；不在首页展开长对话。 |
| 第二行中 | 音乐播放卡 | 专辑/节目摘要、当前房间与播放/上一首/下一首；无播放时降级为媒体入口。 |
| 第二行右 | 家庭状态卡 | 门窗、会议/日程、设备离线或 AI 提醒等一项重要状态；异常优先替换普通摘要。 |

卡片内直接承载低风险高频控制，取代独立的首页快控条：例如空调卡内温度调节、场景卡
的一键执行和音乐卡的播放控制。灯光、窗帘、新风等未展示在首页的设备，进入设备页后
再进行控制。门锁、撤防和其他高风险操作不放入任何首页卡片。

### 5.3 家庭状态与异常

家庭状态只显示异常或重要状态，例如“门窗全部关闭”“客厅 26°C”“3 个设备正在运行”。
状态卡默认收纳，每类只显示数量、摘要和异常；点击后进入对应页面并保留当前空间筛选。
异常状态可临时占用第二行右侧状态卡，不新建全屏阻塞弹窗。

### 5.4 卡片交互与性能边界

首页卡片为固定布局，不支持编辑、删除、添加或拖动重排。卡片主体点按进入设备详情；
卡内明确标出的开关、`− / +` 等小型控件只执行对应的高频主动作。首期不依赖长按，
避免触摸屏长按与页面滚动或误触发生歧义。卡片状态以原生服务的最终确认更新，执行中
仅在本卡显示局部加载。

卡片背景使用自有渐变、简化几何图形或低成本预制素材；不使用实时 Blur、全屏动态壁纸。
摄像头卡只展示缩略图/在线状态，真实画面进入安防页后由原生预览路径承担。

## 6. 设备页面

设备页用于查看和管理全屋设备，以地点/房间作为唯一的第一层筛选维度；设备类型不再
作为首页筛选入口，仅通过图标、名称和详情中的能力项区分。推荐顶部房间栏 + 设备卡片：

    ┌─────────────────────────────────────┐
    │            设备                      │
    │ 全部  客厅  卧室  厨房  卫生间        │
    │                                     │
    │ 客厅 │   主灯       空调  窗帘  摄像头 │
    │ 卧室 │   床头灯     家庭音响           │
    │ 厨房 │   厨房主灯                     │
    │ 卫生间│  排风设备                      │
    └─────────────────────────────────────┘

### 6.1 房间筛选

顶部房间 Tab 固定为：全部 / 客厅 / 卧室 / 厨房 / 卫生间。后续可按实际户型增加
玄关、阳台或书房，但不以设备功能类别替换这一层。用户先回答“要控制哪个地方”，
再从该地点的设备卡进入精调，符合墙面中控的空间认知。

### 6.2 房间摘要与设备能力

房间被选中后，卡片按常用程度排序：照明、空调、窗帘、摄像头等类型仍保留为设备属性，
用于图标、状态和二级页能力组合，而非作为一级导航。每个设备同时具有 `room` 与 `type`
字段，例如 `客厅 / light / 客厅主灯`，使原生服务能按空间订阅状态，又不会让 UI 重回
功能分类。

## 7. 设备卡片设计

卡片至少包含设备图标、设备名称、当前状态、快速控制入口：

    💡 客厅主灯     已开启 70%        ●
    ❄ 客厅空调     26°C 制冷中        ●
    ▤ 客厅窗帘     开启 50%

统一卡片形式以降低学习成本。卡片主体点按打开设备详情；独立绘制的开关仅执行开关，
不能以整张卡片切换设备状态。卡片只显示一个主参数，避免同时展示多行复杂属性；离线、
执行中和告警必须有明确状态。

### 7.1 二级页承载方式与统一规则

首期网页原型采用右侧抽屉式二级页：宽度约为屏宽的 65%，保留首页或设备页作为背景，
以减少“进入设置后失去上下文”的感觉。摄像头的全屏预览、门锁授权记录等内容密集任务
可从抽屉进一步进入全屏页面。

二级页固定为“顶部身份栏 → 主控区 → 模式或参数区 → 低频设置”四段；顶部显示返回、
设备名、房间、在线状态和收藏。所有设备能力都映射到统一的 `getDeviceDetail`、
`setDeviceProperty` 与 `subscribeDeviceState` 语义，禁止页面直接依赖 GPIO、Wi-Fi 或摄像头驱动。
连续视频帧不经 QuickApp JavaScript：摄像头抽屉只放控制与状态，全屏预览由 Native Monitor
承接并在返回时恢复快应用页面。

## 9. 空调二级页面

以温度为核心，下方为模式，右侧为设置：

    26°C
    -      +
    制冷中
    模式：制冷 / 制热 / 除湿 / 送风 / 自动
    设置：风速 3档 / 风向 上下扫风 / 定时 未设置

比传统空调遥控器更直观。

## 10. 窗帘二级页面

核心三个动作：打开、暂停、关闭；另有 0~100% 开合程度并支持拖动：

    窗帘  ██████████░░░░  65%

## 11. 场景页面

场景页采用大图片卡片，卡片内容为场景图片、名称与简短说明：

    回家模式 / 离家模式 / 观影模式 / 睡眠模式 / 起床模式 / 阅读模式

示例：

    观影模式
    关闭主灯、打开氛围灯，关闭窗帘并开启电视。

点击即可执行。场景编辑是低频能力，首期采用列表或网格选择设备和动作；拖拽仅用于
“生成/调整场景”的独立编辑页，不在首页常驻，也不要求全屏实时特效。

## 12. 安防页面

内容分为摄像头、门锁、人体传感器、门窗传感器、烟雾报警器，采用左侧摄像头
画面 + 右侧状态卡片：

    客厅摄像头   实时画面
    门锁         已上锁
    人体传感器   无人
    窗户         全部关闭
    烟雾报警器   正常

首页仅显示最近缩略图、摄像头在线状态和告警摘要；进入安防页后才启动预览。实时预览
由原生视频路径渲染，初始按 5~10 FPS 设计；视频区域不叠加大面积半透明控件，AI 框和
告警文本按低频检测结果更新。

## 13. AI 感知能力展示

这是本项目相对普通中控屏的重要差异。UI 不直接暴露底层模型名称
（YOLO / Pose / Face Recognition / AED），统一表现为用户能理解的状态：

    客厅有人 / 老人已进入卧室 / 检测到跌倒风险 / 检测到陌生人 / 检测到玻璃破碎声音

底层模型统一转换为 Smart Home Event，UI 只展示 Event。

## 14. Agent 页面

Agent 可作为独立入口，也可通过语音唤起，采用沉浸式设计：中央显示动态波形
与 我在听...，下方给出建议命令：

    打开客厅灯
    把空调调到 26 度
    我想看电影
    现在室内温度是多少
    启动回家模式

返回结果采用对话式卡片，例如 已为你打开客厅灯，亮度调整至 60%。涉及危险操作
时增加确认步骤，例如 是否确认打开门锁？

## 15. 主动智能提醒

Agent 不应只等待用户操作，主页可主动展示提醒：

    客厅无人超过 30 分钟，是否关闭客厅灯？
    检测到卧室 CO2 较高，建议打开新风。
    门窗仍未关闭，当前已进入睡眠模式。

提醒采用小卡片，不使用弹窗阻塞用户。

## 16. 能耗页面

展示今日/本周/本月用电与设备耗电排行：

    今日用电 12.8 kWh，较昨日 -12%
    空调 4.2 / 热水器 2.1 / 电视 1.3 / 其他 5.2 kWh

图表尽量简单，避免复杂 BI 风格。

## 17. 设置页面

首期网页 Demo 采用“系统摘要 + 设置分类条 + 单一主内容卡”的布局：网络、AI 服务和
系统健康位于顶部摘要；下方用分类条在智能服务、工具与权限、Skills 与自动化、系统健康
之间切换，一次只展示一个设置域。这样 1024×600 屏幕无需以长页面承载全部高级设置，
也不会让内容被固定底栏遮挡。显示、声音、网络、设备管理后续可作为同层分类增加，
不单独再造一套页面风格。

### 17.1 智能服务

展示并受控配置后端预设、模型名、连接测试、请求超时和 API 密钥的安全存储状态。
API 密钥不得回显、不得写入 QuickApp 包或普通日志；QuickApp 只显示“已配置/未配置”，
实际编辑、校验和 Apply 由原生 `system.smarthome` 服务执行，配置在下一次 Agent 对话生效。

### 17.2 工具与 Skills

工具列表展示名称、用途、可用状态以及“受保护”标识；门锁、安防等高风险工具只显示
确认策略，不能在普通设置中任意解除限制。Skills 显示名称、摘要、加载状态和数量，
管理员可在 Agent 空闲时发起 reload；不提供设备端正文编辑器，也不允许 LLM 自写或删除 Skill。

### 17.3 系统健康

系统健康页展示网络/Wi-Fi、Agent/Model API、摄像头预览、存储、版本和可选 MCP 状态。
默认以“在线/正常/告警”的摘要呈现；原始日志、工具 Schema、请求参数、堆内存等仅进入
管理员或开发者诊断页，避免暴露敏感信息或干扰普通用户。

### 17.4 网络设置

包含 Wi-Fi、Bluetooth、Matter、Zigbee、MQTT、Home Assistant。若使用
ESP32-C6 协处理器，可增加无线协处理器状态，但不向普通用户暴露底层技术细节，
可显示 无线连接 已连接，进入开发者模式后再显示详细信息。

## 18. 显示设置

亮度、自动亮度、深色模式、屏幕休眠、屏保、主题，推荐默认使用自动亮度。

## 19. 待机页面

墙面中控长期运行，待机页尽可能简洁：

    10:28
    9月24日 星期三

搭配低亮度动态背景，可支持天气、室内温度与一句欢迎语，避免显示大量设备。

## 20. UI 动效设计

原则：动效用于表达状态，而不是展示性能。过渡时长建议 200~300 ms。

    设备开启   灰色 → 暖黄渐变
    页面跳转   轻微 Fade + Slide
    Agent      波形动画
    空调       环形温度动画

复杂交互页以稳定 30 FPS 为验收目标；不以 60 FPS 作为交付承诺。页面切换使用轻量
Fade/Slide，设备开关、温度环和 Agent 波形仅刷新自身局部区域。全屏模糊、全屏半透明
浮层、实时壁纸和与摄像头同屏的重型动效均不纳入首期范围，实际帧率上限见附录 C。

为便于实现，UI 抽象为通用组件，页面只负责组合：

    HomeCard / DeviceCard / SceneCard / StatusCard / AlertCard
    SpaceSwitcher / RoomTab / DeviceTab / BottomNavigation / QuickControlBar
    Slider / Switch / Dialog / Toast / LongPressAction / SceneEditor

## 23. UI 与业务层解耦

不推荐按钮直接调用 GPIO 或 MQTT，建议经事件总线：

    UI → home_ui_event → home_app → Device Manager → MQTT / Matter / HA

示例：

    home_ui_emit(HOME_EVENT_DEVICE_SET, device_id, value);

UI 不需要知道设备究竟通过 MQTT、Matter、BLE、Zigbee 还是 Wi-Fi 控制。

## 24. 推荐整体页面关系

    Home
     ├ Devices → Light / AC / Curtain → Detail
     ├ Scenes
     ├ Security
     ├ Agent
     ├ Energy
     └ Settings

最大页面深度不超过 3 层：首页 → 设备 → 设备详情，尽量不出现第四层。

## 25. 项目最终 UI 特征

目标不是传统工业控制面板，而是可以放在家庭墙面上的消费电子产品：大画面、
大卡片、强空间感、少文字、少参数、轻交互、强状态表达，并结合端侧 AI、
智能 Agent、设备控制与主动事件形成差异化。

产品可概括为：

> 以家庭空间为中心，以场景为主要交互方式，以设备控制为基础，
> 以 AI 感知和 Agent 为智能核心的 OpenVela 智能家居中控面板。

交互从 用户找设备 → 点击设备 → 调参数，升级为 用户选择场景 + 系统主动感知
+ Agent 自动协调设备，从而实现从控制面板到家庭智能服务终端的升级。

## 附录 A：与现有 smart_home UI 资产的关系

现有 demos/smart_home 已有一套实机验证过的 LVGL UI（约 6020 行），其信息架构
为 Panel / Chat / Settings 三屏，设计规范为 466x466 圆屏 + Light Premium 浅色。
本方案的 IA 与视觉与之冲突，需要明确取舍：

| 维度 | 现有 UI | 本方案 |
| --- | --- | --- |
| 主题 | 浅色（Light Premium） | 深色（暖黑） |
| 目标屏 | 466x466 圆屏（模拟器）与多平台 | 1024x600 横屏（P4X） |
| IA | 面板 / 对话 / 设置 | 首页 / 设备 / 场景 / 安防 / 能耗 / 设置 + Agent |
| Agent 呈现 | Chat 屏内对话与工具卡片 | 独立 Agent 页（沉浸式波形） |
| 组件化 | 按屏分文件 | 组件库 + 页面组合 |

建议：

- 以本方案作为 P4X 的目标规范，并同步在旧规范文档中标注其适用范围，避免两份
  规范同时生效；
- 现有 UI 的成熟资产应保留复用，特别是 Chat 的工具调用卡片与 thinking 链事件
  展示——在本方案的 IA 中，其自然归宿是 Agent 页；
- 现有 agent/tools/skills/device/net 等 C 层实现与本方案无冲突，可直接复用；
  本方案第 23 节的事件总线与现有 agent 事件机制方向一致，应统一为一套事件面。

## 附录 B：实现路线（LVGL 与快应用的取舍）

结论：P4X 采用两种互斥的**构建时主 UI 模式**。当前默认模式仍是原生 LVGL（C），按本
方案第 21、22 节的组件化结构落地；QuickApp 是独立的候选模式，须完成 P4X 运行时、资源
和 JS-Native Feature 验证后才可选用。二者不在同一固件中作为可自由切换的双主界面，
也不与原生 LVGL 在同一页面混绘。候选分层与决策门见
《ESP32-P4X-SmartHome快应用UI与原生服务分层方案》。

配置实现以现有 `SMART_HOME_DEMO_UI_BACKEND` choice 为唯一入口：保留
`SMART_HOME_DEMO_UI_LVGL`，新增依赖 `QUICKAPP && QUICKAPP_VAPP` 的
`SMART_HOME_DEMO_UI_QUICKAPP`。P4X 分别使用 `configs/smart_home/`（LVGL 基线）和
计划新增的 `configs/smart_home_quickapp/`（QuickApp 验证）。两种配置共享 Device
Manager、State Store、cAGENT、Vision 与网络服务，只替换 UI 入口和资源包；不能同时
启动原生 `smart_home_lvgl` 主循环与 QuickApp VAPP。

若后续采用 QuickApp 承担复杂产品页面，真实设备、传感器、Agent 与 AI 状态必须经
`system.smarthome` Native Feature 读取和订阅；QuickApp 不直接访问驱动、MQTT 或
摄像头设备。实时画面只能作为与 QuickApp 共用 UIKit/LVGL 根的受控原生预览组件，
或在进入监控时页面级切换到 Native Monitor；不得另起独立 LVGL 应用叠加在 QuickApp
页面之上。

依据：

1. openvela 的快应用运行时渲染在 LVGL 之上（frameworks/graphics/uikit/Kconfig
   中 UIKIT depends on GRAPHICS_LVGL），因此快应用提供的只是编写模型，不是
   更好的渲染器；运行时性能严格更差（多出 QuickJS 解释与 Yoga 布局两层）。
2. 全工作区范围内，QUICKAPP 仅在 goldfish 模拟器与 smartspeaker 参考板的
   defconfig 中启用，没有任何 ESP32 板级配置启用过；P4X 属于零基础。
3. 快应用依赖链很长（LIBUV、PROTOBUF_C、QUICKJS/WAMR、UIKIT、
   UIKIT_FONT_MANAGER、LIB_YOGA、LV_USE_LIBPNG、UTILS_CURL、LIB_PNG、
   FEATURE_FRAMEWORK、LIBASH），移植到 P4X 的工作量与 C6 Wi-Fi 适配同量级。
4. 现有 cAGENT、tools、skills、device 均为 C 实现。教程提供的 `@system.velaclaw`
   实际对接 openvela `ai_agent`，并不自动调用 cAGENT；P4X 若采用快应用，必须实现
   `system.smarthome` Native Feature，将 Agent、真实状态和受控工具收敛在原生服务。
5. 当前 P4X SmartHome 工程尚未完成快应用 RPK 打包、部署和真机资源基线验证，交付形态
   未闭环；不能以模拟器样例或 Mock 传感器数据替代。

共同前置（两条路线都需要，且已在 goldfish 验证过，风险低）：

    P4X defconfig 打开 LV_USE_FREETYPE（中文字体）、LV_USE_LIBPNG（场景图与图标）、
    LV_USE_FLEX 与 LV_USE_GRID（卡片布局）；当前 P4X 只配置了 Montserrat 12/16/20。

分期建议：

    P0 能力补齐与基线：字体/图片/布局开关；完成空间首页静态视觉稿与 30 FPS 基线
    P1 主题与组件库：theme/colors.h、styles.c、SpaceSwitcher、QuickControlBar、widgets/*
    P2 页面：首页 → 设备 → 详情 → 场景 → 安防 → 能耗 → 设置 → 待机
    P3 业务解耦：home_ui_event 事件总线接入现有 device/agent
    P4 与端侧 AI 汇合：安防页接摄像头、Agent 页接 cAGENT、提醒接主动事件

## 附录 C：性能与资源现实

1. 帧率：P4 为双核 400 MHz RISC-V，无 GPU，LVGL 为软件渲染。1024x600 即
   61 万像素/帧，60 FPS 意味着约 3700 万像素/秒的合成能力，叠加圆角、阴影与
   alpha 混合后急剧恶化。复杂交互页以稳定 30 FPS 为验收目标；小面积动效
   （波形、环形温度、开关渐变）可做；全屏切换与全屏半透明浮层需谨慎。
2. 内存带宽：摄像头通路已占用约 111 MB/s 内存流量，显示帧缓冲为 2457600 字节。
   全屏图片素材（1024x600 RGB565 约 1.2 MB/张）需要资产预算表，并与摄像头
   三缓冲（约 3.7 MB）共同核算 PSRAM 余量。
3. 摄像头预览：建议限制刷新率（5~10 fps）并避免在其上叠加 alpha 层，否则会与
   推理和视频通路争抢带宽。
4. 存储：Flash 为 16 MB，LittleFS 位于偏移 0x800000、大小 1 MB。图片与字体
   资源需与固件体积一并核算。
5. 事件与 Agent 的并发限制：主动提醒接入前需要先改造
   smart_home_agent_run_service 的单槽提交实现，详见端侧目标检测方案第 6.4 节。

## 附录 E：参考设计提炼与落地边界

华为全屋智能中控屏 S2 的公开产品页体现了“空间全屋交互 → 系统重点控制 → 单品精细
控制”的分层，以及场景快控、长按精调和主题壁纸等体验。本方案吸收其产品方法，而非
复制其视觉资产或实现依赖。

| 参考体验 | 本项目落地方式 | 不纳入首期的部分 |
| --- | --- | --- |
| 空间化首页 | `SpaceSwitcher` 切换全屋/房间，首页按空间组织场景与状态 | 挂墙/桌面/手持的空间自动识别 |
| 收纳式全屋管理 | 首页仅展示摘要、异常与高频控制，完整列表下沉到设备页 | 首页同时常驻全部设备 |
| 一键快控与长按精调 | `QuickControlBar` 提供低风险默认动作；长按进入系统/设备详情 | 未确认的高风险动作直达执行 |
| 场景编排 | 先采用列表/网格编辑；拖拽放入独立 `SceneEditor` 页面 | 全屏高频拖拽特效和复杂物理动画 |
| 玻璃感主题与壁纸 | 深色分层、预制模糊背景、小阴影、少量自有壁纸 | 实时全屏 Blur、参考产品的壁纸/图标/文案 |
| 安防画面与 AI 结果 | Vision Service 独占取帧；原生预览组件或 Native Monitor 显示，QuickApp 只收状态/事件 | 将视频原始帧传给 JS、或另起独立 LVGL 应用叠加在 QuickApp 页面 |

实现评审应按以下优先级验收：空间首页的信息层级和触摸响应、设备/场景操作正确性、
安防与 AI 告警可读性，最后才是主题与动效。任何视觉效果都不得牺牲 30 FPS 复杂交互
页目标、摄像头稳定性或设备控制可靠性。
