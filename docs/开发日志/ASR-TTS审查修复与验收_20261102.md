## 修复范围

1. **V9 语音输入键盘**：先创建共享键盘，再构建 ASR/TTS 面板并传入有效指针；
   focus 回调防御空键盘。原顺序一直把 NULL 存入语音控件。
2. **配置任务生命周期**：创建 pthread 前保存测试/保存动作标志，线程接管 job 后
   调用方不再访问 job。工作线程可能在 `pthread_create()` 返回前清零并释放 job。
   设置测试期间阻止聊天页开始 ASR；保存密钥期间阻止并发应用模型配置。
   同时修复仅开启 TTS 时对 ASR 专属字段的无条件引用。
3. **24 kHz 云端 TTS**：按 WAV 实际采样率解析 PCM16 LE 单声道；24 kHz 响应
   经低通滤波和 2/3 重采样后输出 16 kHz PCM，再进入现有播放器。
   不修改 ES8311/I2S 驱动时钟，也不将 24 kHz 数据直接标记成 16 kHz。
   16 kHz 数据维持原采样率；其他采样率仍交给播放器处理，未声称全部支持。
4. **错误回传**：新增 `smart_home_tts_synth_ex()`，保留旧 synth 接口；区分凭据、
   本地资源、网络/容量、HTTP 状态、响应解析和播放阶段。设置页显示准确阶段，
   自动播报 worker 的失败由 LVGL 线程取回并显示聊天错误气泡。
   主动停止产生的 `-EINTR` 不显示故障；重新初始化服务清除旧错误。
   同进程内 TTS 共用 HTTP 缓冲用互斥锁保护，忙时立即返回明确错误。
5. **LLM 密钥入口**：启用 ASR 或 TTS 的构建中，模型设置页增加“保存 LLM 密钥”，
   调用现有异步保存 helper，仅写 `model_api_keys`。ASR/TTS 仍分别使用自己的映射。
   保存成功清空输入框，并提示重新应用模型配置；不改变“应用配置”的运行期语义。

同时补齐 Make/CMake 的 TTS 重采样源文件接线，收紧 WAV fmt/data 块截断检查。
既有 ASR 配置版本兼容、V9 语音开关、HTTP 响应头容量修复保持在基线中。

## 重采样的边界

滤波器为 24 kHz 输入下的 33 抽头、7.2 kHz 截止频率 Hamming 窗 sinc，
两个分数相位，Q15 系数各自归一化到 32768，64 位整数累加和饱和输出。
输出样本数为 `floor(input_samples * 2 / 3)`，两端复制边缘样本；无运行期浮点。
一秒输入 24000 个样本输出 16000 个样本，时长误差小于一个输出采样周期。

转换额外分配输出 PCM（约为输入 PCM 字节数的 2/3），成功后释放原响应缓冲。
分配失败归入本地资源错误，不继续播放；需要板端确认剩余堆、耗时与实际音质。
这次没有改动云端 API 请求协议，也没有通过真实 MiMo 网络服务验证。

3. 先运行本地固定音频，确认硬件基线正常：

4. 测试云端合成：

   ```text
   tts_smoke speak "你好，这是语音播报测试"
   ```

   ```text

   tts_smoke: synth ok: bytes=... rate=16000
   [player] configure ok rate=16000 ch=1 bits=16
   tts_smoke: speak complete
   ```

   人声应自然、音调和语速正常；不能只凭 synth ok 判定出声。
5. 运行 `asr_smoke recognize /data/hi_openvela.pcm` 验证固定语音，随后在聊天页
   点击麦克风说话、再次点击结束录音；应显示识别结果并触发 LLM，开启自动播报时
   继续合成并播放。完整 ASR→LLM→TTS 路径仍需这次板端日志和听感确认。
6. 分别将一个语音服务临时配置为无效测试密钥：应显示鉴权/权限错误；恢复后可

失败时保留从启动到出错的完整串口日志、实际配置名称，以及构建日志。出现失响应

## TTS HTTP 超时诊断补充

针对板端 `ret=-7 status=200 body_len=75676` 增加应用侧诊断。请求预算、TLS I/O
超时仍为 30000 ms；不调整 HTTP 结束判定、不将超时当成成功、不记录请求正文。
只修改 TTS 应用源码和宿主测试，未修改 cAGENT 端口、apps/webclient 或驱动。
本轮未构建或烧录，板端效果待用户确认。

新增日志：

| 字段或日志 | 含义 |
| --- | --- |
| `[tts][tls] ... elapsed_ms=` | 从本次 HTTP 请求起点到连接/握手等 TLS 日志事件的单调时间 |
| `[tts] headers:` | 应用收到最终响应头回调的状态、数量及时间 |
| `[tts] header:` | 仅输出 Content-Length、Transfer-Encoding、Connection、Content-Type、Content-Encoding；不输出 Cookie 等其他头，单个值最多 160 字节 |
| `[tts] receive:` | 正文首次交付，以及此后每累计 64 KiB 或经过 5 秒且有新数据时输出；不是每包打印 |
| `elapsed_ms` | 从请求开始到传输调用返回的总耗时，含连接、TLS、等待和接收 |
| `headers_seen` / `headers_cb_ms` | 是否发生响应头回调及其相对时间 |
| `first_body_ms` / `last_body_ms` | 首次、末次正文交付的相对时间 |
| `body_idle_ms` | 有正文时，末次正文交付至传输返回的间隔；无正文时为 0 |
| `callbacks` | 正文回调次数；为 0 时首末正文时间均为 0，表示未观察到正文 |
| `length_known` / `expected_len` | 是否解析到合法 Content-Length 及其声明值；未知时 expected_len 为 0 |
| `length_state` | short：少于声明长度；matched：等于；over：多于；unknown：未提供；invalid：非法/溢出或重复长度头；transfer-encoded：存在 Transfer-Encoding，不以长度头判断 |
| `deadline_expired` | 返回时是否已超过 30 秒请求预算，不代表已确定是哪个下层超时路径 |

当前 transport 会在正文首次交付时或请求成功结束时，才调用应用 headers 回调。
因此 `headers_cb_ms` 不等于网络收到首个响应头的时间；`headers_seen=0` 也不能排除
下层已经收到响应头。first/last_body_ms 是应用交付时间，不是网卡收包时间。
chunked 的结束块和 trailer 在 webclient 内处理，应用日志不声称能识别其完成。

判读顺序：

1. `length_state=short`：未观察到声明长度的全部正文，结合首包、末包时间检查
   等待和下载。`headers_cb_ms` 很晚可能包含服务端合成等待，也可能包含网络延迟。
2. `length_state=matched` 且 `ret=-7`、`body_idle_ms` 很大：字节数已匹配，重点
   检查结束判定、等待断连或清理耗时；仍保留超时，不凭字节数直接播放。
3. `transfer-encoded/unknown/invalid`：不依据 Content-Length 推断完整性，结合
   编码头和后续传输层调查。HTTP 200 不等于完整正文或音频可解析。
