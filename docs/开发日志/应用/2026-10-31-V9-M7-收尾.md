## 目标配置编译尝试（2026-10-31）

尝试运行 build.sh smart_home_service_lab，configure.sh 报该配置目录不存在。原因是 openvela 构建树解析的是主工作树 contest2026_031_niudanxianqianchong，而 V9 分支与新增 defconfig 位于 worktrees/contest2026_031_niudanxianqianchong-lvgl-v9。目标编译前需要先把 V9 分支合并/复制到主工作树，或为该 worktree 建立独立构建树；这一步属于用户的最终构建流程。

## 目标编译验证结果（2026-10-31，smart_home 配置）

绕过路径问题：构建期间临时把构建树的软链接（board、packages/demos/smart_home）指向 V9 worktree，编译结束立即还原，不改主工作树文件。

```sh
./build.sh ../worktrees/contest2026_031_niudanxianqianchong-lvgl-v9/board/esp32p4/esp32p4-function-ev-board/configs/smart_home -j8
```

结果：LD nuttx 成功，生成 nuttx.bin；Host 回归 8/8 通过。

| 项 | 数值 |
| --- | --- |
| nuttx.bin | 1,435,404 B（1.37 MiB） |
| nuttx ELF | 3,070,896 B |
| irom_seg | 919,308 B / 64 MB（1.37%） |
| sram_seg | 247,416 B / 978,880 B（25.28%） |
| drom_seg | 1,395,188 B / 64 MB（2.08%） |

编译期发现并修复两个真实缺陷（Host 独立 CMake 构建覆盖不到）：

1. 23d00fe：三个 V9 源文件在 demos/smart_home/Makefile 里只写了路径、漏掉 `CSRCS +=` 前缀，make 报“缺失分隔符”，目标构建根本没进入编译阶段。
2. d344ec3：`pthread_attr_setaffinity_np` 只在 CONFIG_SMP 下声明与链接，摄像头上电代码未加条件编译，非 SMP 配置链接期报未定义引用。

注意：build.sh 收尾会把 `nuttx/defconfig` 回写配置目录，用相对路径参数时该步会打印 `cp` 失败，不影响已生成的固件。

## smart_home_service_lab 仍无法链接（外部阻塞）

该配置启用 SMART_HOME_MCP_BRIDGE / SMART_HOME_NODE_GATEWAY，Kconfig 会 `select CAGENT_ADDONS`，而 `packages/cagent_addons` 仍按 cAGENT V1 API 编写：

- `include/cagent_addons/remote_tool.h` 引用已不存在的 `<cagent/types.h>`（当前 cAGENT 只有 `include/agent/`）。
- 去掉该 include 后 `src/glue/remote_tool.c` 继续报 V2 结构差异：`agent_string_view_t` vs `char *`、`group_id`→`group`、`timeout_ms`/`remote_execute` 成员不存在、`AGENT_ERROR_NOTFOUND`→`AGENT_ERROR_NOT_FOUND`。

这与 `tests/lvgl/README.md` 已记录的“Node 附加模块仍依赖 V1 的 cagent/types.h”一致，属于 cAGENT→ai_agent 迁移的未完成部分，与 V9 UI 无关。因此在附加模块迁移完成前：

- 用 `smart_home` 配置可完整编译链接 V9 界面代码（结果见上表）。
- MCP/Node 两个 V9 配置弹窗的源码分支（`#ifdef CONFIG_SMART_HOME_MCP_BRIDGE` 等）尚未进入目标构建，仍只经 Host 编译。
- `smart_home_service_lab` 保留为迁移完成后的验证配置，届时重跑即可。
