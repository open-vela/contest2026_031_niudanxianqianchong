# 米家链路七层排障闭环：从"controls 恒空"到 Agent 真实控制摄像头

排障日期：2026-09-20（单日闭环）。
适用对象：`demos/smart_home/src/miloco/`、`src/ui/lvgl/smart_home_lvgl_panel.c`、
esp-hosted WLAN 驱动、以及一切"大响应 + 嵌入式网络 + 堆敏感"的链路。

## 背景与结论

米家（Miloco）链路此前停留在"网关在线、设备可见"，但 controls 恒空、
控制抽屉弹不出、agent 无法控制。本日排障共拆解 **七层叠放的问题**，
最终达成完整闭环：**UI 手动控制（抽屉 8 条控件）+ Agent 工具控制
（LLM→miot_device_list→miot_device_control→摄像机真实执行）**，
且顺带验证了 cAGENT TLS 路径在真机上稳定（deepseek 握手/请求/响应全通）。

七层的特殊性：**每一层都是下一层暴露的前提**——修好点击才看到抽屉
被杀，修好抽屉才稳定看到 spec 失败，修好网络才暴露缓冲不够，修好
缓冲才暴露解析冻死，修好解析才暴露 UTF-8 截断。定位手段必须跟着
问题层级逐层切换（代码审查 → 竞态分析 → 网络抓包对账 → 本机 curl
对照 → 内存地图 → 宿主黄金数据单测）。

## 问题总览

| # | 层级 | 问题 | 根因 | 修复提交 |
| --- | --- | --- | --- | --- |
| 1 | UI | 米家卡片完全不可点 | if/else 之后一句无条件 `clear_flag(CLICKABLE)` 抹掉全部可点击性 | `de0cca5` |

| 3 | UI | 抽屉弹出即被杀（0~5 秒） | worker 每 5s 无条件 revision++ → 1s 定时器先重建抽屉、再被 rebuild_device_cards 显式 close | `cc9fd2e` |
| 4 | 驱动 | 大响应整帧丢弃（`no packet buffer`×2/轮） | esp-hosted RX 配额硬编码 8，17KB spec=12 个 TCP 段撞墙 | `c09467b`（8→32） |
| 5 | 服务 | 17,426B 响应装不进 16KB 缓冲 | `MILOCO_RESPONSE_BYTES` 尺寸过小 | `c09467b`（16K→32K） |

## 逐层详述

### 第 1 层：卡片点击修复（`de0cca5`）

`create_miloco_card` 在 `if (control_count > 0)` 正确设置 CLICKABLE 并
注册回调之后，第 1918 行一句无条件 `lv_obj_clear_flag(card,
LV_OBJ_FLAG_CLICKABLE)` 把所有米家卡片的可点击性全部抹掉。表现为
"抽屉完全弹不出"。一行删除修复。

### 第 2 层：spec 拉取重试（`7c83d5e`）

原设计只在设备**首次出现**时拉一次 spec，且 `fetch_spec_for` 返回值
被丢弃——恰好首次拉取发生在网关刚连、网络未稳的高危窗口，失败一次
即永久空 controls（agent 与 UI 都无法控制）。

修复：`control_count==0` 的在线设备每轮重试，上限 12 次（防 spec
恒空时打爆 backend），重试打 syslog。记账表为 service 本地静态数组，
**不动 miloco.h 共享结构体**（避免陈旧对象全量重编陷阱）。

后续实测证明：重试机制工作正常但救不了第 4/5 层的确定性失败——
"重试救偶发，救不了确定性"，两层配合才闭环。

### 第 3 层：抽屉被轮询刷新杀死（`cc9fd2e`）

三方打架，外部 AI 分析定位方向正确，本仓库核实关键细节后简化修复：

1. `parse_device_list` **无条件** `revision++`（每 5 秒必涨）；
2. UI 的 1 秒定时器：先 `sheet_refresh` 重建抽屉 → 再 `refresh_cards`
   → `rebuild_device_cards` 里显式 `miloco_sheet_close_impl` 把刚重建
   的抽屉删掉；
3. 关键细节：**抽屉挂在 `screen_panel` 上，`lv_obj_clean(panel_grid)`
   根本删不到它**——那句显式 close 是唯一杀手。修复 = 删掉那一行
   （而非重排刷新顺序），抽屉生命周期由 sheet_refresh 全权管理
   （设备消失时 build 静默 return 自然关闭）。

同提交：revision 改为**真变才涨**（按字段比较防结构体 padding，含
reachable 恢复的首次成功），消除每 5 秒全网格重建（白闪/滚动重置）；
controls 空的卡片也允许点击，抽屉显示"暂无可控项"占位。

### 第 4 层：esp-hosted RX 配额（`c09467b`）——真机日志定案

现象对账表是定位关键：

| 响应 | 体积 | TCP 段数 | 结果 |
| --- | --- | --- | --- |
| /api/miot/status | 307B | 1 | 每轮成功 |
| /api/miot/device_list | 632B | 1 | 每轮成功 |
| 手环 spec | 186B | 1 | 成功 |
| **摄像机 spec** | **17,426B** | **~12** | **`no packet buffer`×2/轮，永不完成** |

`ESP_HOSTED_WLAN_RX_QUOTA`（驱动内 `#define`，非 Kconfig）= 8：
netdev 框架的流量控制（配额用尽后 `netpkt_alloc` 拒绝）→ 丢包 →
TCP 重传 → 再撞墙 → 3 秒超时窗口内 12 段永远凑不齐。

修复 8→32。注意 `chips/esp32p4/.../esp_hosted_wlan.c` 与
`nuttx/arch/.../espressif/esp_hosted_wlan.c` 是**硬链接**（同 inode），
改一份即两份生效。

### 第 5 层：响应缓冲（`c09467b`）

本机 curl 实测 spec=17,426B > `MILOCO_RESPONSE_BYTES`(16KB)——网络
修好也会截断。32KB 走 PSRAM bulk 堆无压力。**curl 实测数字直接决定
修复尺寸**，这是"先测量再修"的典型样本。

### 第 6 层：cJSON 分配风暴 → 轻量解析（`56d4366`）

网络与缓冲修好后，冻点**前移**到 `done len=17426` 之后——解析窗口。
排除法：NUL 终止 ✓（客户端每字节补 '\0'）、栈数组 ~900B ✓、
"SRAM 不够"单独不成立（mm 双区回退 + NULL 返回是优雅失败）。

根因：cJSON 整树 = **上千次小 malloc + free**，~130KB 瞬时树主要落
SRAM 堆区（用户堆多区 first-fit 小分配优先 SRAM），与 LVGL 运行时
小分配（`LV_USE_CLIB_MALLOC=y` 共堆）竞争。

修复：新增 `smart_home_miloco_specscan`——对已知结构的一次线性扫描，
**零堆分配**（输出直接写固定数组），提取规则与旧实现逐条等价
（黑名单/prop 可写/action/bool/enum+4 档/prop.2.1 电源位/截断语义）。
开发中踩到：`value_range` 数组含浮点（`[0.0,270.0,90.0]`），数字扫描
分支补小数与科学计数法。

**宿主黄金数据单测**是本层质量保证：把真实的 17,426B spec 喂给扫描器，
逐项核对 8 条控件（开关/夜视三档/时间水印/宽动态/微光全彩/人形检测/
录制三档/云台动作），不可写项正确跳过。**有真实响应文件时，宿主单测
优先于上板**——上板一轮十分钟，宿主一轮十秒。

### 第 7 层：UTF-8 字节截断（`bf74693`）

agent 调 miot_device_list 成功后，二轮请求被 deepseek 拒绝：
`400 invalid unicode code point at messages[3].content column 4047`
（messages[3] 即工具结果）。根因：`desc[24]` 字节截断把
"摄像机控制 夜视功能"(28B) 切到 23B 恰好断在"功"中间，非法序列随
工具结果进入请求 JSON。

**潜伏 bug 首爆**：截断逻辑一直存在，但此前 controls 恒空、desc 从未
进过 agent 请求。修复：`copy_bounded`/`copy_text` 统一 UTF-8 字符
边界回退（续字节 `10xxxxxx` 序列内向前退）。宿主验证"夜视功能→夜视"
"时间水印→时间"全部干净回退 + 自定义 UTF-8 校验器全绿。

## 方法论沉淀

1. **测量先于修复**：本机 curl 拿到 17426B 与 spec 结构，同时定案
   第 5 层尺寸与解析兼容性；真机日志对账表定案第 4 层。
2. **黄金数据宿主单测**：真实响应文件驱动的单元测试，比上板快两个
   数量级，且能在修复前发现 value_range 浮点这类结构意外。
3. **修复即推进**：七层洋葱中每修一层，冻点/错误点**前移**——
   "错误位置前移 = 进度"，不要因"修了还错"而否定上一层的正确性。
4. **共享头文件不动原则**：重试记账、扫描器输出全部走本地结构，
   避免触发"头文件变更→全量重编"的陈旧对象陷阱。
5. **潜伏 bug 在链路打通日集中爆发**：第 1/7 层都是"从未被真正执行
   过的代码路径"，与语音链路首编排障的结论一致——**从未运行过的
   代码不可信任**。
6. **外部 AI 分析要核实再吸收**：第 3 层的外部分析方向正确但修复
   方案偏繁琐；核实"抽屉父对象"这一个事实后，修复从三步简化为一行。
