# ESP32-P4X DSI 黑屏：DBI 配置排障闭环

本文记录 ESP32-P4X Function EV Board 搭配 1024×600 EK79007 面板时，
MIPI-DSI Host、DPI、Bridge 和 DMA 均表现正常但屏幕始终黑屏的问题，以及最终
通过严格补齐 ESP-IDF DBI 配置完成点亮的过程。

## 1. 最终结论

黑屏的根因不在色条 buffer、PSRAM、cache clean、DW-GDMA、DPI timing 或 D-PHY
是否发送视频，而在 **DSI command/DBI 配置缺失**：

- Host 的 `cmd_mode_cfg` 保持复位值，Generic 和 DCS 命令默认使用 HS；
- 已点亮的 ESP-IDF 实现通过 `esp_lcd_new_panel_io_dbi()` 明确要求所有面板控制
  命令使用 LP；
- NuttX 实现虽然能够把 EK79007 初始化命令写入 Host FIFO，并打印“writes
  accepted”，但这只代表 Host 接受了 packet，不能证明面板已正确接收命令；
- EK79007 没有可靠完成初始化和退出休眠，因此后续 Host pattern 与 DMA 视频流
  即使正常发送，屏幕仍只有背光、没有画面。

严格补齐 ESP-IDF DBI 配置后，以下两条命令均已在同一块实板、同一块屏和同一条
FPC 上显示成功：

```text
nsh> dsi_probe pattern 10
nsh> dsi_probe video 10
```

这同时验证了面板控制链路、Host 内建 pattern 链路以及 framebuffer/DMA 连续扫描
链路。

## 2. 现象

修复前执行：

```text
nsh> dsi_probe pattern 10
nsh> dsi_probe video 10
```

两种模式均表现为：

- GPIO26 背光能够开启；
- D-PHY PLL 锁定，clock lane 和两条 data lane 存在活动；
- DPI timing、Bridge 和 Host 寄存器均已配置；
- DMA 模式的帧计数约以 60 Hz 持续递增；
- 没有 DMA error、Bridge underrun 或 PLL lock loss；
- 屏幕始终黑屏。

同一硬件运行 `~/Project/espidf_lcd` 时能够正常显示色条，因而可以排除面板、FPC、
LCD adapter 供电和背光硬件损坏。

## 3. 分层排除过程

| 层次 | 证据 | 结论 |
| --- | --- | --- |
| 面板与接线 | 同板、同屏、同 FPC 的 ESP-IDF 示例可显示 | 硬件基础链路正常 |
| D-PHY | PLL lock 保持为 1；高密度采样发现 clock/data lane 持续活动 | HS 视频确实从 PHY 发出 |
| DPI/Bridge | timing、像素格式和流控寄存器已生效；无 underrun | 视频时序链路未发现阻塞 |
| DMA | PSRAM framebuffer 分配成功；帧计数持续递增；无 DMA error | buffer 被持续扫描，不是“一帧未发” |
| Host pattern | 断开 Bridge 像素输入后启用 Host 内建 pattern，仍然黑屏 | 问题不依赖 framebuffer 内容、cache 或 GDMA |
| 面板命令 | Host FIFO 接受写入，但 DCS read 无返回，且 DBI 速度配置与 ESP-IDF 不一致 | 面板可能没有真正执行初始化命令 |

`pattern` 与 `video` 的共同前置条件只有 Host/PHY、面板复位和 EK79007 DCS 初始化。
当两条独立像素路径都黑屏时，应优先检查共同的面板控制链路，而不是继续修改两套
像素生产路径。

## 4. 与 ESP-IDF DBI 路径的关键差异

ESP-IDF 的 `esp_lcd_new_panel_io_dbi()` 在创建 DBI IO 时执行以下配置：

1. 关闭 TE acknowledge；
2. 开启 command acknowledge；
3. Generic 0/1/2 参数短写使用 LP；
4. Generic 长写使用 LP；
5. Generic 0/1/2 参数短读使用 LP；
6. DCS 0/1 参数短写使用 LP；
7. DCS 长写使用 LP；
8. DCS 短读使用 LP；
9. Maximum Return Packet Size 命令使用 LP。

原 NuttX 实现只配置了 command mode、clock lane、PHY switch time、CRC/ECC、
EoTp 和超时参数，没有配置上述 DBI 传输模式。P4 rev3 Host 中
`MIPI_DSI_LL_TRANS_SPEED_HS` 的值为 0，恰好与相关寄存器复位值相同，所以初始化
命令实际走了默认 HS 路径。

此外，原实现开启了 RX EoTp，而 ESP-IDF 对应初始化路径没有开启它。为缩小变量，
本次同时移除了该配置。

## 5. 修复内容

修复位于：

```text
chips/esp32p4/common/espressif/esp_mipi_dsi.c
  └── esp_mipi_dsi_configure_command_mode()
```

增加的核心配置为：

```c
mipi_dsi_host_ll_enable_te_ack(host, false);
mipi_dsi_host_ll_enable_cmd_ack(host, true);

/* Generic short/long write and short read all use LP. */
/* DCS short/long write and short read all use LP. */
/* Maximum Return Packet Size command also uses LP. */
```

完整实现逐项调用 P4 HAL 的 DBI speed-mode API，没有直接写 magic register。配置后
增加以下日志：

```text
INFO: MIPI-DSI DBI configured cmd_mode_cfg=010f7f02 command_ack=1 transfer=LP
```

`cmd_mode_cfg=0x010f7f02` 的组成如下：

| 字段 | 寄存器位 | 结果 |
| --- | --- | --- |
| TE ACK | bit 0 | 0 |
| Command ACK | bit 1 | 1 |
| Generic LP 模式 | bits 8–14 | 全部为 1 |
| DCS LP 模式 | bits 16–19 | 全部为 1 |
| MRPS LP 模式 | bit 24 | 1 |

该值是本次真机测试时判断 DBI 配置是否真正落入硬件寄存器的首要证据。

## 6. 修复后的调用链

```text
dsi_probe
  → board_mipi_dsi_host_initialize()
    → esp_mipi_dsi_host_initialize()
      → esp_mipi_dsi_configure_command_mode()
        → Command ACK = enabled
        → Generic / DCS / MRPS = LP
  → GPIO27 面板硬件复位
  → ek79007_panel_setup()
    → EK79007 DCS 初始化命令经 LP 发送
  → pattern 模式：Host 内建色条 → D-PHY → 面板
  → video 模式：RGB565 framebuffer → DW-GDMA → Bridge → DPI Host
                  → D-PHY → 面板
```

DBI 配置解决的是两条显示路径共同依赖的“面板先正确启动”条件；它不改变现有
RGB565 profile、1024×600 timing、色条内容、DMA 描述符或板级 GPIO。

## 7. 实板验收结果

### Host 内建 pattern

```text
nsh> dsi_probe pattern 10
```

结果：**屏幕成功显示 Host 内建 pattern**。

该结果证明：

- EK79007 已正确完成初始化；
- 面板已进入可显示状态；
- DPI Host、D-PHY lane 与面板视频接收链路可用；
- 不依赖 framebuffer、cache clean 或 DW-GDMA 也能显示。

### DMA 色条

```text
nsh> dsi_probe video 10
```

结果：**屏幕成功显示 RGB565 DMA 色条**。

该结果进一步证明：

- PSRAM framebuffer 内容有效；
- cache 同步和 DMA 可见性满足当前扫描要求；
- DW-GDMA、Bridge、DPI Host 和面板组成的连续视频链路完整可用。

因此，MIPI-DSI 固定色条阶段已经从“Host PASS、视觉待确认”提升为
**真机视觉 PASS**。

## 8. 复测要求

重新构建和烧录后，先确认启动日志中存在：

```text
INFO: MIPI-DSI DBI configured cmd_mode_cfg=010f7f02 command_ack=1 transfer=LP
```

随后依次执行：

```text
nsh> dsi_probe pattern 10
nsh> dsi_probe video 10
```

两种模式都必须满足：

- 画面在测试时间内可见；
- 无 PHY PLL lock loss；
- 无 Bridge underrun；
- 无 DMA error；
- 测试结束后能够关闭背光并停止视频，不发生复位或资源泄漏。

`DCS GET_POWER_MODE` 在当前面板/adapter 上仍可能没有返回数据。只要 DBI 配置、
初始化写、Host pattern 与 DMA 视频均已通过真机视觉验收，该只读诊断不应阻塞
显示链路验收。

## 9. 排障经验

1. **Host FIFO 接受命令不等于面板执行命令。** “write accepted”只能证明软件把
   packet 交给 Host，不能代替面板侧 ACK 或最终画面。
2. **复制初始化命令表不等于对齐参考实现。** 必须同时对齐 DBI IO 创建时隐含的
   command ACK、LP/HS speed mode、TE 和 EoTp 配置。
3. **命令面和视频面必须分开验证。** DMA 帧计数、PHY 活动和无 underrun只能证明
   视频生产链路运行，面板仍可能因未退出休眠而黑屏。
4. **Host pattern 是重要隔离工具。** 它能绕过 framebuffer、cache 和 DMA；若它
   与 DMA 视频同时黑屏，应优先检查共同的面板初始化和 D-PHY 配置。
5. **视觉结果是显示驱动的最终验收门。** `HOST PASS`、`frames > 0`、无错误位都
   不能替代实屏可见。
