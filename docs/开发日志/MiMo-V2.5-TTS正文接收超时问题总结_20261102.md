## 1. 当前结论

本地测试音与一条 MiMo 短句都能通过扬声器播放，用户确认短句“你好”清楚可辨。
同一句较长文本的两次请求都收到 HTTP 200，但正文未接收完整，随后返回
`AGENT_ERROR_TIMEOUT (-7)`。这两次失败均未进入音频解码、重采样和播放阶段。

因此，当前需要定位的是 **HTTP/TLS 正文接收中途停顿**。已知数据不支持把这两次
无声解释为扬声器故障、24 kHz 重采样失败，或“正文收齐后一直等待连接关闭”。
但尚不能在板端接收实现、C6/SDIO、热点网络、远端服务之间确定具体责任层。

本记录中的“长句”仅指相对“你好”更长的约 11 个字符，不能据此推断触及模型
长文本限制。单次响应字节数较大，是排查变量，不是已经证实的触发阈值。

## 3. 当前实现与官方协议核对

当前调用路径：

```text
聊天 LLM 回复 → 自动播报队列 → TTS HTTP 请求
  → 收齐 JSON → Base64 解码 → WAV 解析
  → 必要时 24 kHz 转 16 kHz → 播放器 → I2S/ES8311 → 扬声器
```

`tts_smoke speak` 直接验证从 TTS 合成开始的路径，绕过聊天与 LLM 队列。
当前模式是整包接收后播放，不是边接收边播放；正文下载失败时不会输出部分语音。

核对官方资料的日期为 2026-11-02。官方非流式示例将待合成文本放在 `assistant`
消息内，使用 WAV 输出，并解码 `message.audio.data`；`mimo_default` 是有效预置音色。
当前 [请求构造](../../demos/smart_home/src/voice/smart_home_tts.c) 与这些要求一致。
来源：[MiMo-V2.5-TTS 官方指南](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/audio/speech-synthesis-v2.5)。

实际请求形态示意，不含任何凭据：

```json
{
  "model": "mimo-v2.5-tts",
  "messages": [
    {"role": "assistant", "content": "你好，这是语音播报测试"}
  ],
  "audio": {"format": "wav", "voice": "mimo_default"}
}
```

端点为 `https://api.xiaomimimo.com/v1/chat/completions`，当前未请求流式。
已有一条短句的完整成功和听感确认，也支持这套请求与解析形态具备基本可用性。

## 5. 如何理解这次超时

第一次失败的关键日志：

```text
[tts] header: Content-Length: 143907
[tts] header: Connection: close
[tts] http: ret=-7 status=200 body_len=109092 elapsed_ms=42970
  ... last_body_ms=12010 body_idle_ms=30960
  ... expected_len=143907 length_state=short deadline_expired=1
```

第二次失败也显示类似现象：末次正文在 12.850 s，之后约 30.390 s 没有正文交付。
这表示应用没有观察到后续正文，不等于已经证明网络线上没有任何报文。
TLS 可能在等完整记录，底层也可能在处理重传、流控或其他事件，仍需下层证据。

当前客户端将请求期限、TLS I/O 超时配置为 30000 ms。应用回调中的期限检查不能
打断一个已经开始的阻塞等待，因此请求实际可能在 43 s 左右才返回；并不代表期限
被配置成了 43 s。这个实现行为需要与正文停顿分别分析。

几个诊断边界：

- HTTP 200 只证明已收到成功状态，不能证明正文完整或可播放。
- `length_state=short` 表示实收量小于合法 Content-Length；`matched` 仅表示字节数相符，不能替代协议和音频校验。
- 应用 `headers_cb_ms` 是回调时间；当前 transport 在首次正文交付或成功结束时才回调响应头，不等于网络首个响应头到达时间。
- `first_body_ms`、`last_body_ms` 是正文交付到应用的时间，不是 Wi-Fi 网卡收包时间。
- 进度日志经过节流，只有首次、此后累计 64 KiB 或经过 5 秒且有新数据时打印，缺少中间日志不代表接收量没变化。
- 当前主机配置的 TTS 响应上限是 1048576 B；两次失败响应均小于该上限。没有证据表明命中了这个应用层容量限制。

此前考虑过“完整正文后等待 EOF”的可能性；本次两条完整失败记录均为 `short`，
所以该解释不适用于这两次样本。也不代表现有 webclient 的所有结束判定路径均已验证。

## 6. 原因假设与优先级

以下为排查优先级，不是已确认的故障归属。

| 假设 | 支持线索 | 缺少的证据／验证 |
| --- | --- | --- |
| 板端较大响应接收路径存在压力或停顿 | 短响应成功，两条较大响应均中途停止；停止位置不同 | C6/SDIO 收包和丢包统计、IOB/队列余量、TCP 窗口与重传、TLS 读取等待 |
| 热点或到服务端的网络路径不稳定 | 现场关联曾失败，放开接入后成功；复位后又未关联 | 同一热点下电脑请求对照、AP 状态、路径和代理设置 |
| 服务端或中间网关停止发送 | 收到 200 和部分正文后停止交付 | 电脑相同请求的完整下载、时间和响应头，必要时服务端请求标识 |
| 请求字段、音色或凭据错误 | 当前代码符合所核对的非流式形态，且短句成功 | 如出现 4xx 或不同响应结构，再回到该方向检查 |
| 重采样／播放器失败 | 短句已完整通过并经用户听感确认 | 这两次失败尚未进入这些阶段，不足以用它们解释此次超时 |

不能从 3 次样本推导“短句总成功、长句总失败”，也不能将 76 KB 或 109 KB 当成
固定容量阈值。相同文本两次生成的响应大小不同，本身不等于协议错误。

## 7. 建议的后续对照顺序

| 阶段 | 操作 | 观察指标与判定目的 |
| --- | --- | --- |
| A：网络前置条件 | 确认板端关联、IP、DNS；记录热点、出站路径和代理状态 | 网络未就绪时停止后续云端测试，不把关联失败计为 TTS 接收故障 |
| B：电脑直连 | 电脑通过同一热点，对相同短句和较长句各请求 3 次非流式 TTS | HTTP 状态、Content-Length、实收长度、首包及总耗时；判断远端与热点路径能否稳定完成 |
| C：板端静态下载 | 局域网准备固定 50／150／300 KiB 内容，分别用 HTTP、HTTPS 下载，每点先做 3 次 | 使用 RAM 或丢弃 sink，校验长度和摘要，不写 LittleFS；区分基础收包、TLS 和公网路径 |
| D：并发对照 | 保持网络、请求文本和预算不变，分别关闭与开启 UI／天气服务 | 比较成功率、接收停顿、CPU、堆和网络缓冲，验证调度或并发压力影响 |
| E：针对性诊断 | 根据前述结果给最可疑层加计数与时间记录 | 定位具体等待、丢包、重传或队列压力，再设计修复 |

每个阶段记录原始日志；修改后重复原来失败的输入和对照组。每点 3 次只是初步
诊断门槛，不等于稳定性验收。不要同时修改超时、IOB、SDIO 配额、UI 和流式协议。

建议补充的底层字段包括：SDIO/RX 包数及错误、NETPKT/IOB 分配失败与余量、TCP
重传/窗口状态、每次 TLS read 的请求量和返回量、WANT_READ/WANT_WRITE 等待时间。
只记录计数、长度、时间及错误码，不记录密钥或正文。

## 8. 超时与流式改造的取舍

官方 FAQ 建议合理设置连接、读取超时，考虑退避重试，并对长响应考虑流式；没有
将本工程的 30 秒规定为统一要求。来源：[MiMo API 接入 FAQ](https://mimo.mi.com/docs/zh-CN/quick-start/faq/api-integration)。

将预算延长可作为受控对照，观察是否存在较长重传后恢复；但它不能单独解释为什么
这两次约第 12 秒停止正文交付。需要区分连接、首包等待、接收空闲和总请求期限。
TTS 请求重试还需考虑重复计费，以及未来流式播放后重复播报的问题。

官方当前支持 `mimo-v2.5-tts` 低延迟流式，示例使用 `stream=true`、`pcm16` 和
`delta.audio.data`，按 24 kHz PCM16 LE 单声道处理。
来源：[MiMo 流式调用示例](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/audio/speech-synthesis-v2.5)。

流式适合作为后续降低首声延迟和整包内存占用的改进。当前解析器读取完整 JSON
的 `message.audio.data` 并解析 WAV，所以不能只修改一个 stream 参数：需要增量
事件解析、按实际协议处理 Base64 分块、带跨块状态的重采样、有界播放缓冲以及取消、
失败与欠载策略。它也不会自动消除底层接收停顿或 Base64 传输开销。

建议先定位并修复现有非流式接收问题，再单独验证流式；若并行试验，使用独立分支
与单独验收标准，保留非流式对照。

## 9. 需要单独处理的额外异常

接管期间出现过 Wi-Fi 关联失败；热点允许接入后完成了上述 3 次云端对照。
随后清理自建测试文件时发生失响应，复位后 UI 与 NSH 恢复，但 Wi-Fi 再次未关联。
因此最后交接状态不是“网络始终正常”，不能以中间一次成功代替重连稳定性验收。

NSH 准备与删除测试文件时均出现过失响应，已经停止继续执行这类写操作。
主机当时的 INIT_STACKSIZE、BOARD_INITTHREAD_STACKSIZE、SYSTEM_NSH_STACKSIZE
均为 2048；NSH 曾报告 1976 B 容量、1940 B 使用（98.1%）。这是栈压力线索，尚未
通过故障现场栈回溯、PC 或其他证据确认根因，也不等于 TTS 工作线程栈不足。

测试时经历多次 USB 复位，最初用户运行现场未保留；三次 TTS 对照具有独立完整记录。
自建小文件 `/data/printf_probe`、`/data/tts_diag_t.pcm` 可能残留，未宣称清理成功；
未覆盖原有音频、模型或资源，未修改服务密钥。串口已释放。

这两类异常分别跟踪，不与“HTTP 200、正文 short、TTS 超时”合并成一个未经证明的根因。
