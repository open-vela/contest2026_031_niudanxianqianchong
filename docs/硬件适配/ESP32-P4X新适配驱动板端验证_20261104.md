### 1.1 一个必须记录的测量陷阱

ESP32-P4 的 USB Serial/JTAG 会在**每次打开串口时**由 DTR/RTS 触发复位。本次最初用"一条命令开一次端口"的方式测试 `graphics_probe all 100`，导致每轮只跑到 32 轮就被复位截断，而退出码仍为 0。改用常驻端口 + Unix socket 转发（`console.py`）后，才拿到完整的 100 轮结果。

后续所有长测试都必须使用常驻控制台，不能以"命令返回"当作"测试完成"。

## 2. PPA 与 2D-DMA

### 2.1 被测配置

`smp_smart_home` 配置，`.config` 关键项：

```text
CONFIG_ESP32P4_DMA2D=y
CONFIG_ESP32P4_PPA=y
CONFIG_ESP32P4_SMP=y
CONFIG_ESP32P4_SMP_GRAPHICS_CPU0=y
CONFIG_LVX_USE_DEMO_CONTEST2026_031_GRAPHICS_PROBE=y
```

这是**最难的一种组合**：PPA 与 SMP 共存，图形操作被限制在 CPU0，同时 CPU1 在跑 idle/中断。它比单核 `ppa` 配置更能暴露 DMA2D 与跨核调度的冲突。

### 2.2 五项功能

```text
nsh> graphics_probe copy
graphics case: copy src=auto dst=auto fg=unused
graphics: cpu=0 rounds=1 bytes=49152 src=0x48266f80 fg=0 dst=0x4825af40
graphics memory: src=psram fg=unused dst=psram
graphics copy: PASS (0)

nsh> graphics_probe fill
graphics fill: PASS (0)

nsh> graphics_probe srm
graphics srm: PASS (0)

nsh> graphics_probe blend
graphics case: blend src=auto dst=auto fg=auto
graphics: cpu=0 rounds=1 bytes=49152 src=0x48266f80 fg=0x48272fc0 dst=0x4825af40
graphics memory: src=psram fg=psram dst=psram
graphics blend: PASS (0)

nsh> graphics_probe convert
graphics convert: PASS (0)
```

覆盖内容：

- `copy`：RGB565 二维复制，带偏移、不同 stride、跨 128 行描述符边界逐像素校验，另检查目标外区域、busy、错误任务号、非法参数、取消与重新提交；
- `fill`：RGB565 填充与目标外区域校验；
- `srm`：固定角度旋转、镜像、0.5/1/2 倍 Q4 缩放；
- `blend`：不透明背景上前景 alpha 0/255/128 的双图层混合；
- `convert`：RGB888/ARGB8888 转 RGB565，UYVY 转 RGB565。

注意所有缓冲区都落在 PSRAM（`src=psram dst=psram`），即 DMA2D 通过 cache 一致性路径访问外部 PSRAM，这是比内部 SRAM 更严格的条件。

### 2.3 压力与资源

```text
nsh> graphics_probe all 100
graphics round 100/100
graphics copy/fill/srm/blend/convert: PASS (0)   ← 每轮 5 项，共 500 项
```

100 轮统计：`PASS=656 FAIL=0`（656 含此前单项与 32 轮遗留记录，100 轮本体 500 项全部 PASS）。

再追加 50 轮前后对比 `free`：

```text
轮前：Umem used=2465220  Kmem used=13572
轮后：Umem used=2465220  Kmem used=13572
```

**完全无变化**，无 DMA 描述符或 IOB 泄漏。整个过程未出现超时、异常复位或桥 underrun。

## 3. 麦克风与扬声器（ES8311）

### 3.1 驱动就绪

```text
INFO: ES8311 kheap: stage=i2s-before total=192076 used=8236 free=183840
INFO: ES8311 kheap: stage=i2s-after  total=192076 used=9252 free=182824
INFO: ES8311 ready: i2c=0 addr=0x18 i2s=0 out=/dev/audio/pcm0 in=/dev/audio/pcm_in0
```

I2C0 地址 0x18 探测成功，I2S0 双向设备节点 `pcm0` / `pcm_in0` 均已注册。

### 3.2 扬声器

```text
nsh> audio_smoke play 3
audio_smoke: play 3 s, 16 kHz mono PCM16
audio_smoke: play complete, bytes=96000
```

96000 = 3 × 16000 × 2，字节数精确。

```text
nsh> audio_smoke play 2
audio_smoke: play complete, bytes=64000
```

64000 = 2 × 16000 × 2，精确。

### 3.3 麦克风

```text
nsh> audio_smoke record 5 /data/verify_rec1.pcm
audio_smoke: record complete, bytes=160000
nsh> audio_smoke record 10 /data/verify_rec3.pcm
audio_smoke: record complete, bytes=320000
```

两次字节数均等于 `秒数 × 16000 × 2`，无丢帧。

采样时钟精度（用 NSH 内建 `time` 测量）：

```text
nsh> time "audio_smoke record 5 /data/verify_t5.pcm"
audio_smoke: record complete, bytes=160000
5.1000 sec
```

5 s 录音实测 5.1 s，偏差 2%，属于启动/收尾开销，采样时钟本身无漂移。

### 3.4 录音内容真实性

只核对字节数不足以证明麦克风工作——全零数据也能得到相同长度。因此抽查了文件内容：

```text
nsh> hexdump /data/verify_rec1.pcm count=512
00d0: d3 ff c6 ff ac ff a7 ff 9a ff 8a ff 7b ff 8f ff
00e0: a0 ff 98 ff 98 ff a9 ff c2 ff aa ff 93 ff b2 ff
...
01f0: d2 ff d5 ff d0 ff e1 ff e7 ff e7 ff fc ff ee ff
```

判据：

- 是 16-bit 小端有符号采样，`d3 ff` = -45，`e7 ff` = -25，`15 00` = +21；
- 相邻样本持续小幅变化，不是恒定值（排除"通道常通但无信号"）；
- 正负值交替出现，均值接近 0（排除直流偏置饱和）；
- 中段（skip=80000）与首段统计特性不同，说明数据随时间变化，不是缓冲重复。

结论：录到的是真实交流音频信号。

### 3.5 完整回路与稳定性

```text
nsh> audio_smoke playfile /data/verify_rec1.pcm 5
audio_smoke: play /data/verify_rec1.pcm, 160000 bytes, 16 kHz mono PCM16
audio_smoke: play complete, bytes=160000
```

录制文件可直接回放，**ADC → LittleFS → DAC 完整回路打通**。

连续三次 3 s 录音（针对此前"第二次录音卡死"的历史缺陷）：

```text
verify_loop1.pcm  96000
verify_loop2.pcm  96000
verify_loop3.pcm  96000
```

三次全部一次成功，无卡死、无残留任务。本次验证的是**已合入主线的 I2S 描述符预分配 + 超时修复**版本。

## 6. esp-nn（TFLM P4 后端）

### 6.1 主线适配方式

esp-nn **不在** `packages/esp-nn/`，而是主线已有的三处接线，`ef35c97` 提交：

| 组件 | 位置 | 作用 |
| --- | --- | --- |
| 上游源码 | `third_party/esp-nn/` | 44 个 `.c`，含 P4 PIE 内核 |
| TFLM adapter | `third_party/tflm-espnn-adapter/kernels/{conv,depthwise_conv,mean}.cc` | 版本化 kernel，含两处 P4 scratch 修复 |
| 软链脚本 | `scripts/link_esp_nn.sh` | 把 `apps/mlearning/esp-nn/esp-nn` 与三个 kernel 指向本仓 |

构建前先校验链接：

```text
$ ./scripts/link_esp_nn.sh --check
[esp-nn-link] OK: 源码链接与 conv.cc depthwise_conv.cc mean.cc 的 kernel 覆盖均正确
```

工具链用仓内预置的乐鑫 `riscv32-esp-elf`（`scripts/setup_toolchain.sh` 安装，`--check` 通过），**不需要外部下载**：

```text
$ ./scripts/setup_toolchain.sh --check
OK:   compiler 14.2.0 (crosstool-NG esp-14.2.0_20260121) 14.2.0
OK:   multilib rv32imac_zicsr_zifencei/ilp32
OK:   xespv PIE opcodes assemble
installation is usable
```

注意 multilib 是 `rv32imac_zicsr_zifencei/ilp32`（soft-float），这是该工具链的预期配置，不是缺陷。

### 6.2 构建与配置

唯一启用 esp-nn 的配置是 `smart_home_kws`：

```text
CONFIG_TFLITEMICRO_ESP_NN=y
CONFIG_ESP32P4_ESPRESSIF_TOOLCHAIN=y
CONFIG_ARCH_RV_ISA_VENDOR_EXTENSIONS="xespv"
CONFIG_TFLITEMICRO_ESP_NN_CONV2D_OUTPUT_TENSOR_MASK=0xa8000000
CONFIG_TFLITEMICRO_ESP_NN_DEPTHWISE_CONV2D_OUTPUT_TENSOR_MASK=0x50000000
CONFIG_TFLITEMICRO_ESP_NN_TRACE=y
```

构建产物确认 PIE 指令确实进入固件：

```text
$ objdump -d nuttx/nuttx | grep -c "esp\."
58
```

kernel 覆盖也生效——`apps/mlearning/tflite-micro/kernels/esp_nn/conv.cc` 是指向 adapter 的软链，其目标文件引用 `esp_nn_conv_s8_esp32p4`。

### 6.3 板端结果

```text
nsh> kws_smoke
[kws_smoke] arena_reserved=393216 address=0x4825c780 backend=esp-nn \
            conv_mask=0xa8000000 dw_mask=0x50000000
[kws_smoke] stage=allocated arena_used=210452
[kws_smoke] stage=params scale=177180 zp=-20
[kws_smoke] stage=features ready
[kws_smoke] warmup 1 took 2380000 us
... (5 次 warmup 均为 2380000 us)
[kws_smoke] invoke_us warmup=5 repeat=50 min=2380000 p50=2380000 \
            mean=2382200 p95=2390000 max=2390000
[kws_smoke] output wake=0.2305 hard_neg=0.7617 other_speech=0.0000 \
            background=0.0078 silence=0.0000
```

判据：

- `backend=esp-nn`：编译期后端为 ESPNN 而非 reference；
- 50 次推理 `p50=2.38 s`、`p95=2.39 s`，抖动 < 1%，说明走的是确定性定点内核而非动态路径；
- 同一固件复跑一次，`p50` 仍为 2380000 us，`mean` 2382200 → 2382800 us，五分类输出概率逐位相同，结果可重复；
- 该 2.38 s 与仓库既有记录「P4 mask 覆盖 58.3% MAC，实测 3.68 s → 2.38 s」**独立吻合**，是 esp-nn 真实生效的交叉证据；
- 推理输出五分类概率和为 1（0.2305+0.7617+0.0000+0.0078+0.0000 = 1.0000），数值链路自洽。

### 6.4 一个证据边界

`backend=esp-nn` 来自编译期宏 `CONFIG_TFLITEMICRO_ESP_NN` 的回显（`kws_infer.cc:32`），它只能证明**固件编入了 ESPNN 后端**，不能单独证明运行时每个算子都真正走了 PIE 内核。

`CONFIG_TFLITEMICRO_ESP_NN_TRACE=y` 本应打印 `[espnn-trace] Conv2D ... selected=1`，但本次串口 `grep -c "espnn-trace"` 为 0，固件 `strings` 中也找不到该字符串——trace 分支未产生可观测输出。这一点没有查清，因此本次把**「与历史 2.38 s 基线吻合」**作为主要证据，把 trace 缺失记为待查项，而不是宣称逐算子已验证。

## 7. 未覆盖项

以下内容本次没有验证，不能据此判定通过：

- PPA 的 `blend` 保留像素 alpha 模式（README 列为"仍需补充板端专项验收"）；
- PPA 在 CPU1 上运行（当前设计限定 CPU0）；
- PPA 与摄像头预览并发的实际帧率收益；
- 音频在 24 kHz / 48 kHz 采样率下的表现（ES8311 24 kHz 查表顺序缺陷仍未修）；
- 录音与播放同时进行（全双工）；
- WiFi 与音频、PPA 同时高负载；
- PSRAM 探针 `smp_psram`（需 `smp_psram` 配置，本次未构建）；
- esp-nn 逐算子的 trace 级确认（见 §6.4），以及与 reference 后端的同镜像对照测速。

## 9. 结论

在 ESP32-P4 revision v3.2 实板上，PPA/2D-DMA、ES8311 麦克风与扬声器、SMP 双核、esp-nn 四项适配均通过板端验证。

其中前三项在"PPA + SMP + PSRAM + LittleFS + 显示 + 音频 + WiFi"全功能同时启用的重负载配置下保持稳定，PPA 100+50 轮压测无内存泄漏；SMP 跨核调度、跨核调用与双核 Flash 并发 50 轮 0 错误。

esp-nn 经 TFLM P4 后端在 `kws_smoke` 上完成 50 次推理，p50=2.38 s，与仓库历史基线独立吻合。逐算子 trace 未取得输出，该层的验证强度低于其余三项，已在 §6.4 记录边界。
