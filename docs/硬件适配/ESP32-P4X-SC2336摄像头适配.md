## 1. 目的与范围

本文记录 `ESP32-P4X Function EV Board` 搭配 SC2336 MIPI-CSI 摄像头
模组，在 OpenVela/NuttX 中的适配设计、已验证硬件参数、测试方法与当前
问题。

当前阶段目标是先打通传感器控制和 RAW8 采集链路：

```text
SC2336 -> P4 MIPI-CSI Host -> DMA -> RAW 帧缓冲
```

ISP 转 RGB565、向 LVGL 预览以及注册正式 `/dev/video0` 设备属于后续阶段，
不应与底层 SCCB、CSI 和 DMA 首次验证混在一起。

## 4. 当前调用和数据流

### 4.1 传感器探测

```text
nsh: csi_probe sensor
  -> board_sc2336_csi_power_acquire()
     -> esp_mipi_csi_power_acquire()，申请 LDO channel 3 / 2500mV
     -> 等待 10 ms
  -> board_sc2336_probe()
     -> esp_i2cbus_initialize(I2C0)，取得共享总线引用
     -> esp32p4_sc2336_probe()
     -> 分别读取 0x3107、0x3108
  -> 打印 0xcb3a
  -> 释放本次总线引用和 CSI 电源资源
```

当前 `sc2336_read_register()` 在一次 `I2C_TRANSFER` 中提交两条消息，
第一条 `flags=0`，第二条 `flags=I2C_M_READ`。依照本地 NuttX API 和 P4
下层实现，其时序为：

```text
START -> 0x60(W) -> reg_high -> reg_low -> STOP
START -> 0x61(R) -> value -> master NACK -> STOP
```

这与 ESP-IDF `i2c_master_transmit_receive()` 使用 repeated START 的时序
有区别。本轮结果证明当前含 STOP 的读法在这些测试中可以读回正确 ID。
若后续验证 repeated START，应将第一条消息设置为 `I2C_M_NOSTOP`，第二条
不设置 `I2C_M_NOSTART`；不能仅因两条消息放在一次 transfer 中就称其为
repeated START。

`split` 使用两个独立的 `I2C_TRANSFER`，第一段写寄存器指针成功后才发起
读取。它与正式两消息读的总线锁范围不同，只作为分段诊断使用。

`sensor` 不启动传感器 stream，不初始化 CSI Host、ISP 或 DMA。它只用于验证
“D-PHY 供电 + SCCB 读事务”这条最短硬件链路。

### 4.2 RAW 采集目标调用链

```text
nsh: csi_probe raw [frames]
  -> 申请 D-PHY LDO（channel 3，2500mV）
  -> 初始化 I2C0，探测 SC2336 产品 ID
  -> 写入 SC2336 RAW8 profile，stream on
  -> 初始化/配置 P4 CSI Host 与 DMA
  -> 接收 RAW8 帧
  -> 检查帧数、长度、CRC32、非全零和非固定值
  -> 输出 CSI ECC/CRC、DMA、FIFO、Bridge 等错误计数
  -> 按反序释放 CSI、stream、I2C 和 LDO
```

为定位 `stream on` 后没有收帧或命令未返回的问题，CSI 初始化会按顺序输出
`begin`、`lock`、`phy_clock_enable`、`host_bridge_clock_reset`、
`hal_initialize`、`bridge_configure` 和 `complete`。若初始化返回错误，日志会
同时输出最后阶段和 `ret`。这些日志只描述软件执行位置，不表示对应物理链路
已经验收。

启动路径会输出帧缓冲 Cache Clean、DMA 时钟复位、DMA 通道配置、LLI Cache
Clean、DMA IRQ 安装、Bridge 错误轮询配置、IRQ 使能和 Bridge 使能。当前
ESP32-P4 的动态 IRQ 分配在本次真机中只能完成第一路申请：先后顺序互换后，
第二路都不返回。因此临时单帧验证路径只注册 GDMA IRQ；CSI Bridge 的错误事件
不注册 CPU 中断，而是在 DMA 完成、帧超时和统计读取时从粘滞 `int_raw` 读取、
清除并计数。DMA 准备失败会记录阶段与 `ret`，GDMA IRQ 成功时会记录 CPU
interrupt 编号。只有 `MIPI-CSI start: stage=complete` 出现后，Bridge 才已
使能并开始等待传感器数据。

该轮询路径用于推进 P2.3 单帧链路，不能替代正式的 Bridge 错误中断：错误的
发现时机最多延迟到下一次 DMA 完成、等待超时或读取统计。动态 IRQ 分配器的
第二路申请问题仍须独立修复，才能恢复双 IRQ 的正式设计。

期望数据流为：

```text
SC2336 RAW8
    |
    | MIPI CSI-2，2 lane，DT=0x2a
    v
ESP32-P4 CSI Host / D-PHY
    |
    v
DMA RAW 帧缓冲（1024 x 600 x 1）
    |
    +--> csi_probe：长度、CRC、数据分布和硬件错误统计
    |
    `--> 后续 ISP：RAW Bayer -> RGB565 / YUV -> 显示或 AI
```

## 5. 构建与运行

使用独立 `csi_probe` 配置构建：

```bash
./build.sh \
  contest2026_031_niudanxianqianchong/board/esp32p4/esp32p4-function-ev-board/configs/csi_probe \
  -j2
```

烧录并进入 NSH 后按以下顺序测试：

```text
nsh> csi_probe pointer
nsh> csi_probe split
nsh> csi_probe sensor
nsh> csi_probe sccb
nsh> csi_probe write
nsh> csi_probe raw
nsh> csi_probe raw 10
```

| 命令 | 验收目标 |
| --- | --- |
| `csi_probe pointer` | 写 `31 07` 并 STOP，返回成功；仅改变寄存器指针 |
| `csi_probe split` | pointer 写成功，再独立读取 `0x3107=0xcb` |
| `csi_probe sensor` | D-PHY LDO ready，且稳定读出 `product_id=0xcb3a` |
| `csi_probe sccb` | 读 ID -> 写 `0x0100=0x00`（停流）-> 再读 ID 全部成功 |
| `csi_probe write` | 写 `0x0103=0x01` 软件复位 -> 等待 5 ms -> 写停流 -> 读回 `0xcb3a`；会改变 sensor 状态 |
| `csi_probe raw` | profile 配置与 stream on 成功，至少采到一帧合法 RAW 数据 |
| `csi_probe raw 10` | 不少于 10 帧，帧长度正确，数据非全零/非固定值，CSI 和 DMA 错误计数为零 |

`raw` 若失败，应按阶段定位：先确认 profile 写表及 stream 控制成功，再检查
CSI 初始化、DMA 和帧接收；不能把 SCCB 阶段错误直接归因于 CSI PHY 或 ISP。

## 6. 修复原因、真机结果与证据边界

### 6.1 已修复：硬件命令未完整初始化

修复前，`esp_i2c_sendstart()` 中的 `restart_cmd`、`write_cmd`、`end_cmd`
是未整体初始化的自动变量。地址 WRITE 只设置了 `byte_num=1`、`ack_en=1`
和 `op_code`，没有设置 `ack_exp`。实际 HAL 直接把整个 `cmd.val` 写入硬件，
因此 ACK 检查启用时，期望电平可能来自无关的寄存器或栈内容。

`ack_exp=0` 表示期望收到 ACK，`ack_exp=1` 表示期望收到 NACK。错误地设置
为 1 时，传感器正常回应 ACK 也可能触发控制器 ACK 检查错误。

本次对修复前本地 ELF 的反汇编进一步定位了 `pointer` 与 `split` 的差异：
地址命令的构造等价于 `(s4 & 0xffffc600) | 0x00000901`，保留了 bit9，
即 `ack_exp`。两条板级调用路径恰好为 `s4` 分配了不同用途：

| 修复前调用路径 | 进入 I2C 时的 `s4` | 地址 WRITE 命令 | ACK 期望 |
| --- | --- | --- | --- |
| `pointer` | 常量 `0x00000003` | `0x00000901` | 0，ACK |
| `split` 第一段 | `g_readytorun` 地址 `0x4ff463e8` | `0x4ff44b01` | 1，NACK |

上述地址和寄存器分配只适用于当时分析的本地 ELF，重新链接后可能变化。
关键缺陷是未初始化字段进入硬件命令，不能依赖某个调用路径恰好提供零值。
这也解释了增加日志或改变调用路径后故障表现可能变化，以及为什么 reset、
重试、调整后续读事务不能消除这个缺陷。

修复位于
[`esp_i2c.c`](../../chips/esp32p4/common/espressif/esp_i2c.c)：

- START 路径的 RESTART、WRITE、END 全部改为聚合初始化，遗漏成员确定为零。
- 地址和数据 WRITE 均明确设置 `ack_en=1`、`ack_exp=0`。
- `esp_i2c_startrecv()` 的 READ、END 同样完整初始化，保留末字节发送 NACK。
- 保留原有 SCCB 消息 flags、引脚、频率及诊断流程，便于前后对比。

修复后现有 P4 配置的编译、链接和 `nuttx.bin` 打包通过；修改行通过
`nxstyle` 检查，`.config` 未改变。反汇编确认地址 WRITE 命令固定为
`0x00000901`，不再依赖调用方遗留值。该轮构建未提交或推送代码。

### 6.2 2026-09-07 修复后真机验证

证据来源为用户在修复后回传的 NSH 日志（本次会话附件 `pasted-text.txt`）。
日志顺序为 `pointer` → `split` → `sensor` → `sccb`，各执行一次：

| 命令 | 本轮结果 | 已覆盖的行为 |
| --- | --- | --- |
| `pointer` | 1/1 PASS | 写入寄存器指针 `0x3107`，返回 0 |
| `split` | 1/1 PASS，读回 `0xcb` | 原先失败的第一段 pointer 写通过，随后独立读也通过 |
| `sensor` | 1/1 PASS，ID=`0xcb3a` | 读取 `0x3107`、`0x3108` 得到正确产品 ID |
| `sccb` | 1/1 PASS，首尾 ID 均为 `0xcb3a` | 读 ID → 写 `0x0100=0x00` → 再读 ID 闭环通过 |

关键原始日志摘录：

```text
csi_probe: PASS sccb_pointer register=0x3107
SC2336 split diagnostic: stage=pointer_write result=0
SC2336 split diagnostic: stage=read_data result=0 value=0xcb
csi_probe: PASS sccb_split register=0x3107 value=0xcb
csi_probe: PASS sensor=SC2336 product_id=0xcb3a
SC2336 SCCB diagnostic: stage=stream_off result=0
csi_probe: PASS sccb first_product_id=0xcb3a second_product_id=0xcb3a
```

所提供日志中的 START 首次中断均为 `raw=0x00000008`，打印的
`nack=0 timeout=0 arbitration_lost=0`，未见重试或失败记录。
`bytes=0` 是地址命令刚结束时的快照，不表示完整事务没有传输数据。

结合源码缺陷、修复前后的机器码差异及本轮读回结果，可确认命令初始化修复
解决了已复现的 SCCB 阻塞。当前状态应写为“SCCB 基础读写闭环本轮通过”，
不再写成“仅写事务失败”或“仍阻塞于 split 第一段”。

### 6.3 2026-09-07 软件复位写序列真机验证

随后用户在同一 NSH 环境执行了一次 `csi_probe write`，结果如下：

```text
write 0x0103=0x01 -> wait 5ms -> write 0x0100=0x00 -> read product ID
power: D-PHY LDO channel=3 voltage=2500mV ready
SC2336 write diagnostic: stage=soft_reset result=0
SC2336 write diagnostic: stage=stream_off result=0
SC2336 detected: address=0x30 product_id=0xcb3a
csi_probe: PASS sccb_write product_id=0xcb3a
```

两次写事务和之后两字节产品 ID 读取的首 IRQ 快照均为
`raw=0x00000008 nack=0 timeout=0 arbitration_lost=0`。这证明当前固件中，
软件复位 `0x0103=0x01`、等待 5 ms、写停流 `0x0100=0x00`、再读取
`0xcb3a` 的顺序在本次真机执行中完整通过。

该结果进一步确认 I2C 地址 WRITE 的 ACK 期望值已正确初始化；但它仅是一次
运行，不能替代重复执行、断电冷启动或实际 CSI 出帧验证。

### 6.4 2026-09-07 CSI 初始化与动态 IRQ 分配定位

用户提供的完整 `csi_probe raw` 日志已确认以下软件阶段全部返回成功：

```text
MIPI-CSI initialize: stage=phy_clock_enable source=6
MIPI-CSI initialize: stage=host_bridge_clock_reset result=0
MIPI-CSI initialize: stage=hal_initialize result=0
MIPI-CSI initialize: stage=bridge_configure result=0
MIPI-CSI initialize: stage=complete frame_bytes=614400
```

随后 DMA 启动同样通过帧缓冲 Cache Clean、DMA 时钟复位、通道配置和 LLI
Cache Clean。第一次动态 IRQ 申请能完成并返回 `cpuint=4`；将注册顺序改为
Bridge 在前时，Bridge 成功、GDMA 停在 `dma_irq_setup`；此前 GDMA 在前时，
GDMA 成功、Bridge 停在 `bridge_irq_setup`。因此当前证据指向 ESP32-P4 NuttX
动态 IRQ 分配的第二次申请路径，而不是 SC2336、MIPI lane、RAW8 profile、CSI
Host/Bridge 初始化或特定中断源号。

为继续验证 RAW 数据通路，代码已改为临时只申请 GDMA IRQ，并把 Bridge 错误
状态改为从 `int_raw` 轮询。最新真机日志已出现 `dma_irq_setup result=0`、
`bridge_error_polling result=0`、`irq_enable` 与
`MIPI-CSI start: stage=complete`，说明该临时路径已经执行到 Bridge 使能。
但 `esp_mipi_csi_wait_frame()` 在第一帧 1 秒后返回 `-ETIMEDOUT`，尚无 DMA
完成事件。因此该结果只说明软件控制面已启动，不能说明传感器 MIPI 数据已进入
Host 或 DMA。超时时会采样 CSI Host 状态和 Bridge 的粘滞 `int_raw`；
`csi_probe` 也会在资源清理前打印该统计快照，供下一轮定位。

最新回传的超时快照为：

```text
stats: frames=0 dma=0 bridge(overrun=0 fifo=0 discard=0 size=0)
stats: csi(ecc=0 crc=0 phy=0 packet=0) last(dma=0x00000000 bridge=0x00000000 host=0x00000000)
```

这说明首帧等待期间没有 GDMA 完成事件，也没有 DMA、Bridge 或 CSI Host 已采样
到的错误。它排除了当前已启用接收端立即报告协议或 FIFO 故障的情形，但不能
证明传感器确实发送了 MIPI 高速数据。

为将“没有 DMA DONE”进一步定位到接收链路的具体一段，超时快照现增加三行：

```text
stats: host(main=... phy_fatal=... packet_fatal=... phy=...)
stats: phy(rx=... stopstate=...) bridge(raw=... enable=... buffer=...)
stats: dma(channel=... transferred_64bit=... fifo_64bit=... source=...)
```

Host 没有 `int_raw`；上述 `host` 是读取即清除的事件状态，采样仅发生在超时
边界。`phy.rx` 的 bit 17 表示时钟 lane 处于 HS 活动状态，`phy.stopstate` 的
bit 0、1、16 分别表示两条数据 lane 与时钟 lane 的 Stop 状态。`bridge.raw`
是粘滞原始中断状态，bit 5 表示 Bridge DMA 配置已更新；`bridge.buffer` 包含
FIFO 深度。`dma.transferred_64bit` 为已完成的 64-bit 传输单元数，完整 RAW8
帧应为 76800。所有新增字段均为诊断快照，不改变 Bridge 或 DMA 的配置。

已对照本机已通过的 ESP-IDF P4X SC2336 工程。其通用 `example_sensor_init()`
将 `xclk_pin`、`reset_pin`、`pwdn_pin` 全部设为 `-1`；该工程使用的精确
SC2336 模式是 `MIPI_2lane_24Minput_RAW8_1024x600_30fps`，模式表声明
XCLK 为 24 MHz、串行 lane 速率为 288 Mbps。它能出图而不操作 P4 的这些 GPIO，
因此本板不应凭空增加 MCLK、RESET 或 PWDN 的 GPIO 时序代码：24 MHz、复位和
传感器供电应由模组或板级固定电路处理；仅凭软件源无法进一步区分其物理来源。

同一对照工程向 P4 CSI Host 传入 `lane_bit_rate_mbps=200`。该字段会被
`mipi_csi_hal_init()` 用于选择 D-PHY HS 频率档，不等同于模式表的 288 Mbps
串行速率。OpenVela 已将 Host 配置改为 200，并在日志中分别输出
`sensor_rate` 与 `phy_rate`。这是当前最有依据的接收端差异；重新编译后应先
运行一次 `csi_probe raw`，再用新的超时统计判断是否进入 DMA。

本轮随后使用 Host 200 Mbps/lane 的真机结果仍为首帧超时：
`phy.rx=0x00010000`、`stopstate=0x00010003`、Bridge 使能为 1，FIFO 深度为 0。
这表示采样瞬间三条 lane 均处于 Stop 状态，不能证明整个等待期间都没有 MIPI
输出；仅修改 Host 速率未解决超时。

进一步复核发现，首次启动路径遗漏 `dw_gdma_ll_channel_enable(..., true)`，
仅完成中断中存在下一帧重启调用。代码现已在 LLI/IRQ 就绪后、Bridge 使能前
补齐首次 GDMA 通道使能，并打印 `dma_channel_enable channel=0 chen=... enabled=...`。
通道 0 的 CHEN bit 0 预期为 1；高位写使能位不参与判断。该回读只记录瞬时状态，
硬件完成或错误可能使通道自动关闭，最终仍须结合 DMA 中断与帧结果判定。
此修复待用户编译和真机验证，不能将此前的 `start: complete` 当作通道已启动证据。

### 6.5 本轮尚未覆盖

- 各命令只提供了一次结果，不能据此声明长期稳定、冷启动稳定或全场景通过。
- `csi_probe write` 仅提供一次通过记录，尚未完成重复运行和断电冷启动统计。
- `sccb` 验证了停流写事务成功和之后仍能读取 ID；没有读回 `0x0100`，也没有
  观测停流前后视频输出，不能扩展为传感器实际停流效果已实测。
- 最新 `csi_probe raw` 日志确认产品 ID、RAW8 profile 写表、stream on、CSI
  初始化、单 GDMA IRQ、Bridge 错误轮询和 Bridge 使能均成功；首帧等待 1 秒后
  返回 `-ETIMEDOUT`；超时快照的 DMA、Bridge、CSI 错误和最近状态均为零，
  不能证明已收帧。
- 临时单 IRQ 轮询路径已在真机走到等待首帧并完成状态快照；即使单帧通过，也
  不能据此宣布双 IRQ 错误处理或连续采集已经完成。
- 没有 `raw 10` 日志，不能认定连续帧、ISP 或 LCD 预览已经通过。
- 成功日志仍显示 `sr=0x3700c001`，bit0 与本地 `resp_rec` 字段的字面定义

  推翻实际 ID 读回结果，也不能将旧的 NACK 中断直接等同于设备真实 NACK。
- 原始粘贴中部分行首不完整，包括 `si_probe sccb`；后续诊断标题和 PASS

本轮日志未附带板上固件 hash；验证记录依据本次修复后的用户反馈顺序关联，
后续重复验证应同时保存固件版本、命令次数和完整串口日志。

### 6.6 ESP-IDF 对照结论

此前同一块板、同一模组和同一控制参数，在 ESP-IDF 对照工程中提供过
以下 PASS 记录：

```text
I2C0 SDA=7 SCL=8 addr=0x30 freq=100000
MIPI D-PHY LDO: channel=3 voltage=2500mV
read product ID: 0xcb3a
write 0x0100=0x00: acknowledged
read product ID again: 0xcb3a
```

这证明该硬件组合在记录中的条件下可以完成此序列，有助于把排障重点放到
OpenVela 驱动；不能全面排除所有时刻的供电、接线或电气问题。本轮 OpenVela
也完成了同类读写闭环，接下来应验证软件复位、重复运行和 RAW 采集。

## 7. SCCB/I2C 排障原则

1. 保留当前含 STOP 的读法作为本轮已通过的基线。建议先交替运行 `pointer`、
   `split`、`sensor`、`sccb` 各 10 次，再断电重启 3 次、每次重复该序列；这些
   是后续建议次数，不是已完成统计。
2. `csi_probe write` 已单次通过；应重复验证软件复位 → 停流 → 读 ID，并统计
   断电冷启动结果。随后进入 `raw`，单帧通过后再运行 `raw 10`。
3. 若 SCCB 再次失败，记录命令原始值、`ack_en/ack_exp`、中断状态、timeout、
   arbitration lost、状态机状态和 SDA/SCL 电平，必要时采集第九时钟波形。
   静态 SDA/SCL 为高不等于完整电气时序已经合格。
4. 仅在 I2C 总线错误后调用标准 `I2C_RESET` 恢复总线，并确认初始化与释放引用
   计数对称；避免在每次正常传输前强制 reset。
5. 若需对齐 ESP-IDF 的读事务，另行验证 `I2C_M_NOSTOP` 和 repeated START，
   同时保留当前通过结果作为对照；本轮日志不支持“SC2336 必须 repeated START
   才能读 ID”的结论。
6. 正常 START 与首 IRQ 快照使用 `i2cinfo()`，默认不打印；仅在启用
   `CONFIG_DEBUG_I2C_INFO` 时恢复。错误、NACK、超时和仲裁丢失的现有错误路径
   保持输出，避免正常 SCCB 写表淹没 CSI 诊断。

## 8. 与 LCD/PSRAM 对照工程的关系

ESP-IDF 的“SC2336 -> CSI -> ISP -> EK79007 DSI LCD”对照例程确认了 PSRAM：

```text
Found 32MB PSRAM device
SPI SRAM memory test OK
Adding pool of 32768K of PSRAM memory to heap allocator
```

其 DSI 显示初始化仍会因以下能力组合返回零而失败：

```text
MALLOC_CAP_SPIRAM | MALLOC_CAP_DMA
```

这是 ESP-IDF P4 DSI 帧缓冲分配的能力标记问题，不是 PSRAM 未启用，更不是
OpenVela 的 SCCB NACK 根因。该问题应在 ESP-IDF 对照工程中独立处理；不能用
它解释此前的 OpenVela I2C 写失败，也不能将该例程视为完整 LCD 预览验收证据。
