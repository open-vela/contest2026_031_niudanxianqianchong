## 3. 文件职责与调用链

以下路径均相对本仓库：

| 文件 | 职责 |
| --- | --- |
| `app/csi_probe/csi_probe_main.c` | 命令分派、申请/释放供电、打印阶段和诊断结果 |
| `app/csi_probe/README.md` | 命令与构建说明 |
| `board/esp32p4/esp32p4-function-ev-board/src/esp32p4_camera.c` | 板级 I2C 引用、相机锁、SC2336 与 CSI 装配 |
| 同目录 `esp32p4_sc2336.c/.h` | 寄存器读写、ID、RAW profile、stream 控制和诊断 helper |
| 同目录 `esp32p4_bringup.c` | 在对应配置开启时调用 `board_i2c_init()` |
| `board/esp32p4/esp32p4-function-ev-board/include/board.h` | 板级接口、接线参数 |
| `chips/esp32p4/common/espressif/esp_i2c.c` | 总线锁、引用计数、硬件命令/FIFO、IRQ 状态机与 reset |
| `chips/esp32p4/common/espressif/esp_mipi_csi.c` | D-PHY/CSI/DMA 实现 |
| `chips/esp32p4/include/esp_mipi_csi.h` | CSI 芯片层接口 |

```text
csi_probe pointer / split
  -> board_sc2336_csi_power_acquire()
     -> esp_mipi_csi_power_acquire() -> LDO
     -> 等待 10 ms
  -> board_sc2336_sccb_pointer_test() / board_sc2336_sccb_split_test()
     -> nxmutex_lock(g_sc2336_lock)
     -> esp_i2cbus_initialize(0) -> 获取共享总线引用
     -> esp32p4_sc2336_write_register_pointer(..., 0x3107)
        -> I2C_TRANSFER(i2c, &msg, 1)
           -> esp_i2c_transfer() -> 总线锁/FIFO/频率
           -> esp_i2c_sendstart() -> START + 地址 WRITE + END
           -> IRQ / esp_i2c_process()
           -> 地址检查成功后 senddata() -> STOP -> 完成
     -> 仅 split：上一步成功后调用 read_register_data()
        -> 独立 I2C_TRANSFER(... I2C_M_READ ..., 1)
     -> 释放本次总线引用、解锁
  -> 释放本次 CSI 电源资源
```

`pointer` 与 `split` 第一段调用同一个 helper，参数均为 I2C0、`0x30`、
100 kHz、`0x3107`、`flags=0`、长度 2。`split` 不会提前提交后续读消息。
因此，尚未执行的读事务不能直接解释第一段地址检查失败。

## 4. 诊断命令与副作用

| 命令 | 测试序列 | 边界 |
| --- | --- | --- |
| `sensor` | 读取 `0x3107`、`0x3108` | 不启动 CSI；历史成功不代表当前稳定 |
| `pointer` | 写 `31 07` 并 STOP | 改变寄存器指针，不写控制寄存器；单次调用、不重试 |
| `split` | pointer 写并 STOP，再独立读一个字节，期望 `CB` | 诊断用分离事务；当前失败日志未进入读取阶段 |
| `sccb` | 读 ID → `0x0100=0` → 再读 ID | 会停流 |
| `write` | `0x0103=1` → 等待 5 ms → `0x0100=0` → 读 ID | 会软件复位和停流，改变 sensor 状态 |
| `raw [1-10]` | 探测/profile/stream/CSI/DMA/帧统计 | SCCB 稳定后再验收；RAW 文件保存尚属后续工作 |

| 问题/尝试 | 结果与可保留结论 |
| --- | --- |

## 6. 最有价值的现场证据

最新相邻测试的关键字段：

```text
split / stage=pointer_write:
  flags=0000 fifo0=60 busy=0 sda=1 scl=1
  first IRQ raw=00000400 bytes=0 sr=4600c010
  result=-5

pointer / stage=register_address（随后两次）:
  flags=0000 fifo0=60 busy=0 sda=1 scl=1
  first IRQ raw=00000008 bytes=0 sr=3700c001
  result=0
```

`bytes=0` 配合当前驱动的“地址单独执行”实现，把失败定位到地址命令阶段。
`fifo0=60` 是软件准备写入 FIFO 的值，不是逻辑分析仪捕获到的线上字节。
`raw=400` 是控制器的 NACK/ACK 检查错误事件；在核实 ACK 比较配置前，不能
直接将它等同于“SC2336 一定把第九位拉高”。

还有一个此前未充分关注的矛盾：本地 P4 `i2c_struct.h` 把状态寄存器 bit0
定义为 `resp_rec`，0 表示收到 ACK，1 表示收到 NACK。上面失败的
`4600c010` bit0 为 0，而成功的 `3700c001` bit0 为 1。该快照的更新时间
仍需核对，但这使 ACK 期望值配置成为首要检查对象。总线空闲时 SDA/SCL
都为高，只能证明采样时的静态电平，不能证明完整波形与时序正确。

## 7. 首要候选原因：硬件命令未完整初始化

**源码缺陷已确认；是否解释全部真机现象尚未验证。**

当前 `esp_i2c_sendstart()` 中：

```c
i2c_ll_hw_cmd_t restart_cmd;
i2c_ll_hw_cmd_t write_cmd;
i2c_ll_hw_cmd_t end_cmd;

restart_cmd.op_code = I2C_LL_CMD_RESTART;
write_cmd.byte_num = 1;
write_cmd.ack_en = 1;
write_cmd.op_code = I2C_LL_CMD_WRITE;
end_cmd.op_code = I2C_LL_CMD_END;
```

这些自动变量没有整体初始化；尤其 `write_cmd.ack_exp` 未赋值。
实际使用的第三方 HAL 中，`i2c_ll_hw_cmd_t` 包含 `ack_en`、`ack_exp`、
`ack_val`、`done` 和保留位。`i2c_ll_master_write_cmd_reg()` 直接将整个
`cmd.val` 写入硬件寄存器，并不会替调用者补齐默认值。

因此，启用 ACK 检查时，期望的 ACK 电平没有被确定设置。这属于明确的
硬件配置可靠性问题。不同调用路径、栈内容、编译优化或日志修改可能改变
未初始化字段的实际值；这是一种能够解释“同一 helper 在 pointer 成功、
split 失败”的机制，比继续推断未执行的读事务更有源码依据。

进一步说，若期望值误设为 1，控制器可能把真正的 ACK 当成不符合期望，
也可能把真正的 NACK 当成满足期望。因此在确认此字段前，历史 pointer
PASS 也不应作为“摄像头必然 ACK 了所有字节”的最终证据。

`esp_i2c_startrecv()` 的 `read_cmd`、`end_cmd` 同样仅部分赋值，应一起
审计。相比之下 `esp_i2c_senddata()`、`esp_i2c_sendstop()` 使用聚合
初始化，未列出的成员有确定的零值。

建议的最小修复方向是完整初始化所有硬件命令，地址/数据 WRITE 明确
`ack_en=1`、`ack_exp=0`，再按事务需要设置 READ 的 `ack_val`。本次仅记录，
没有修改驱动。修复后必须以真实读回 `CB3A` 和写后再读闭环作为验收，
不能只观察错误日志消失。

## 8. NuttX/OpenVela 接口核查与其他候选项

1. **总线引用架构本身成立。** `esp_i2cbus_initialize()` 使用引用计数，
   已有引用时返回同一个控制器；`uninitialize()` 仅在引用归零时关闭外设。
   `/dev/i2c0` 的持有者与相机各自获取、释放自己的引用属于合理模式。
   不应为了相机诊断强制销毁仍被其他用户持有的共享总线。

2. **SC2336 寄存器打包暂未见直接错误。** 当前读使用两条消息，写使用
   `[reg_high, reg_low, value]`，地址参数传 `0x30`。NuttX 不要求创建
   ESP-IDF 式 SCCB device handle 才能访问设备；将 bus、addr、frequency
   放入设备私有结构是后续封装方向，不是当前地址错误的必要修复条件。

3. **一次 transfer 与 repeated START 不能混为一谈。** 本地
   `nuttx/include/nuttx/i2c/i2c_master.h` 明确说明 repeated START 需要前一条
   消息 `I2C_M_NOSTOP`，后一条不设 `I2C_M_NOSTART`。当前 SC2336
   `msg[0].flags=0`，本地 P4 下层会发 STOP；它并非严格等价于 IDF
   `transmit_receive()`。这是后续需对齐的事务语义，但解释不了当前
   split 第一段地址检查失败。

4. **split 的锁不是整条总线的跨调用锁。** 相机锁覆盖两个 helper，
   控制器锁则只覆盖各自的 `I2C_TRANSFER`。其他总线客户端仍可在两个
   transfer 之间进入；这是分离诊断的限制，不能用它替代正式组合读。
   `board_sc2336_probe()` 也没有取得与其他诊断相同的相机锁，属于并发
   路径待完善项；当前顺序执行 NSH 的日志没有证明发生了并发竞争。

5. **电源/时钟/电气时序仍是次级候选。** 内部上拉和 10 ms 等待在源码中
   已存在，不能再称为“未开启”。DPHY 电源不等同于 sensor 全部电源，
   24 MHz 输入是否来自模组及其实际稳定性需结合板卡资料/测量确认。
   先修正确定的命令初始化缺陷，再判断是否仍需这些硬件检查。

6. **错误恢复与日志需收敛。** `I2C_RESET` 不能修正每次重新构造时再次
   带入的错误命令字段。当前中断路径打印较多，应考虑在 IRQ 内只存快照，
   在线程中输出；这是避免时序扰动的后续改进，尚无证据认定它是唯一根因。

## 9. 接手后的建议顺序与验收

1. 保存当前 diff 和构建配置，记录待烧录固件对应的源码版本。
2. 优先修复/检查 `esp_i2c_sendstart()` 和 `esp_i2c_startrecv()` 的完整命令
   初始化；需要诊断时，记录提交前 command 原始值及 `ack_en/ack_exp`。
3. 由用户重新编译烧录。冷启动和交替命令顺序都测试 `pointer`、`split`、
   `sensor`，各重复若干次并记录次数；不能把“连续成功”写成没有统计依据
   的长期稳定性结论。
4. 取得真实 `CB/CB3A` 后，对齐组合读 repeated START；验证 `sccb` 的
   读 ID→停流→读 ID，再独立验证 `write` 的软件复位序列。
5. 若仍报错，对照 command 期望 ACK、SR 接收 ACK 与逻辑分析仪第九时钟
   电平，区分设备真实 NACK、控制器配置错误与采样/时序问题。
6. SCCB 验收后再进行 profile、stream、`raw`、`raw 10`。检查帧数、
   614400 字节长度、数据变化、CRC32 和 CSI/DMA 错误计数；后续另行验收
   RAW 保存、ISP、LCD 预览和正式视频节点。

本次交接新增的关键发现是硬件命令未完整初始化。它应先于继续新增诊断命令
或更改传感器寄存器表得到验证。
